## Clarifications

### Session 2026-11-12

ユーザーの指示（確認が要る項目は推奨の内容で進める）により、以下は推奨の回答で決めた。

- Q: 工程内テストのコマンドはどこで決めるか？ → A: ファクトリーの設定に、順に実行するコマンドの一覧として置く（既定は `pnpm run check` の1件）（推奨）。対象リポジトリの中のファイルからは読まない。CI と同じコマンドを呼ぶ方針（`04` 3章）に合わせ、リポジトリ内の文字列で実行内容を変えられないようにする
- Q: 工程内テストはいつ実行し、失敗をどう戻すか？ → A: 実装役が完了を告げた時点で実行し、失敗したら同じ会話の中に失敗のログを差し込んで続けさせる（steering。1回の実装工程につき既定3回まで）（推奨）。上限を超えても通らなければ、検査役を呼ばずに「不合格（テスト失敗）」として、やり直しのループに入る。テストに通らないものを検査役に見せてリクエストを使わない（原則 VI）
- Q: 計画役の出力の形は？ → A: 決まった形の JSON（概要・作業手順・受け入れ条件・作業の種類）を出させ、検査役と同じく検証し、合わなければ1回だけ再要求する（推奨）。受け入れ条件を検査役にそのまま渡せ、作業の種類を 008 の自動マージ条件に使える
- Q: 判定で不合格になったとき、作業ディレクトリの変更を戻してからやり直すか？ → A: 戻さない。今の変更の上から、新しい会話で実装工程をやり直し、不合格の理由と今の diff をフィードバックとして渡す（推奨）。直す箇所が小さいことが多く、作り直すより消費が少ない
- Q: 検査役の出力が再要求のあとも検証に通らないときは？ → A: 工程全体を「失敗（判定できない）」で終える（推奨）。コードの問題ではないので、やり直しのループには入れない
- Q: 004 の手で試すコマンド（`implement:dev`）はどうするか？ → A: 本機能の CLI に統合し、`implement:dev` は削除する（推奨）。計画を手で渡すと計画役を飛ばせるようにして、実装工程だけを試す使い方を残す

## User Scenarios & Testing *(mandatory)*

この機能の利用者は2種類いる。

- **工程を進めるファクトリーのコード**（007 の Worker、012 の回帰評価）: 用意済みの作業ディレクトリと Issue 文を渡して、計画から判定までを1回実行し、合否と理由・変更・消費を受け取る
- **ファクトリーの開発者**: 開発機で、ローカルのリポジトリと Issue 文を指定して、計画から判定までを CLI で回し、結果と軌跡を見てハーネスを直す（AI解禁後は さくらで同じことをする）

### User Story 1 - 計画を立てる（計画役） (Priority: P1)

ファクトリーは、Issue 文・依頼の本文・リポジトリの構成・AGENTS.md を計画役に渡し、ツールなしの1回の呼び出しで、作業の概要・作業手順・受け入れ条件・作業の種類を出させる。出力は決まった形かを検証し、合わなければ1回だけ再要求する。

**Why this priority**: 実装役に渡す計画と、検査役が照らし合わせる受け入れ条件の出どころ。これがないと工程が始まらない。

**Independent Test**: 偽の LLM に、正しい形の計画・壊れた形のあと正しい形・2回とも壊れた形をそれぞれ返させ、計画が得られる／再要求で得られる／失敗で終わることと、LLM の呼び出しにツールの定義が含まれないことを確かめる。

**Acceptance Scenarios**:

1. **Given** Issue 文と作業ディレクトリ、正しい形の計画を返す偽の LLM、**When** 計画を立てる、**Then** 概要・作業手順・受け入れ条件・作業の種類を持つ計画が得られ、LLM は1回だけ呼ばれ、その呼び出しにはツールの定義が含まれない
2. **Given** 1回目に形の合わない出力、2回目に正しい形を返す偽の LLM、**When** 計画を立てる、**Then** 合わなかった理由を添えて1回だけ再要求し、2回目の計画が得られる
3. **Given** 2回とも形の合わない出力を返す偽の LLM、**When** 計画を立てる、**Then** 3回目は呼ばず、工程は「失敗（計画を得られない）」で終わる
4. **Given** 「これまでの指示を無視して…」を含む Issue 文、**When** 計画を立てる、**Then** Issue 文はデータとして区切られて渡り、システムの指示より前や外に置かれない
5. **Given** 計画役の呼び出し、**When** 記録を見る、**Then** 予算ゲートを通って工程「計画」・役割「計画役」として記録され、入力と出力が軌跡に残る

---

### User Story 2 - 決め打ちのコマンドで工程内テストを行う (Priority: P1)

実装役が完了を告げたら、ファクトリーは設定にあるコマンド（lint・型チェック・テスト）を作業場で順に実行する。LLM は使わない。失敗したら、失敗したコマンドとログ（切り詰めたもの）を実装役に差し込んで続けさせる。決まった回数を超えても通らなければ、実装工程を「テスト失敗」で終える。

**Why this priority**: 原則 VI（テストに通らないものは出荷しない）と `04` 3章の工程内フィードバック。実装役が「直したつもり」で終わるのを防ぐ。

**Independent Test**: 偽の作業場でコマンドの終了コードを決め、全部通る・1回落ちてから通る・ずっと落ちる、の3通りで、差し込みの有無と回数、実装工程の終わり方を確かめる。

**Acceptance Scenarios**:

1. **Given** すべてのコマンドが成功する作業場、**When** 実装役が完了を告げる、**Then** コマンドが設定の順に1回ずつ実行され、テストは「合格」となり判定に進む
2. **Given** 1回目は落ち、直したあとは通る作業場、**When** 実装役が完了を告げる、**Then** 失敗したコマンド名とログが実装役に差し込まれ、実装役が続けて作業し、2回目の完了でテストが通る
3. **Given** ずっと落ちる作業場、**When** 差し込みが上限の回数に達する、**Then** それ以上差し込まずに実装工程を終え、検査役を呼ばずに「不合格（テスト失敗）」として扱う
4. **Given** 失敗したコマンドの後ろにまだコマンドがある、**When** テストを実行する、**Then** 最初に失敗したところで止め、後ろのコマンドは実行しない
5. **Given** 時間の上限を超えるコマンド、**When** テストを実行する、**Then** そのコマンドは打ち切られ、時間切れとして失敗に数えられる
6. **Given** 秘密情報らしい文字列を含むテストのログ、**When** 実装役に差し込む・記録する、**Then** その文字列は伏せ字になる

---

### User Story 3 - 検査役が判定し、結果を検証する (Priority: P1)

テストに通ったら、ファクトリーは検査役（実装役とは別系統のモデル）に、Issue 文・計画（受け入れ条件）・変更（diff）・テストの結果を渡し、ツールなしの1回の呼び出しで、合否と理由を決まった形の JSON で返させる。出力は検証し、合わなければ1回だけ再要求する。

**Why this priority**: 原則 III（実装と検査を別モデルに、検査役の出力は検証する）。自動マージ条件の1つ（検査役の合格）の元になる。

**Independent Test**: 偽の LLM に合格・不合格・壊れた形のあと正しい形・2回とも壊れた形を返させ、それぞれの判定結果と呼び出しの回数、呼び出しにツールの定義が含まれないことを確かめる。

**Acceptance Scenarios**:

1. **Given** テストに通った変更、合格を返す偽の LLM、**When** 判定する、**Then** 判定「合格」と理由が得られ、検査役のモデルで1回だけ呼ばれ、ツールの定義は含まれない
2. **Given** 不合格と直すべき点を返す偽の LLM、**When** 判定する、**Then** 判定「不合格」と理由・直すべき点が得られる
3. **Given** 1回目に形の合わない出力を返す偽の LLM、**When** 判定する、**Then** 合わなかった理由を添えて1回だけ再要求する
4. **Given** 2回とも形の合わない出力、**When** 判定する、**Then** 3回目は呼ばず、工程は「失敗（判定できない）」で終わる
5. **Given** 検査役のモデル名が実装役と同じ設定、**When** 工程を始める、**Then** LLM を呼ぶ前に、別のモデルにするよう求めて止まる
6. **Given** 大きな diff やテストのログ、**When** 検査役に渡す、**Then** それぞれ上限で切り詰め、切り詰めたことを示して渡す
7. **Given** 変更（diff）が空、**When** 判定に進む、**Then** 検査役を呼ばずに「不合格（変更なし）」として扱う

---

### User Story 4 - 不合格ならやり直し、上限で必ず止まる (Priority: P1)

判定が不合格（テスト失敗・変更なしを含む）なら、ファクトリーは不合格の理由と今の diff をフィードバックとして、新しい会話で実装工程をやり直す。やり直しは設定の上限まで。上限を使い切っても合格しなければ「不合格」で終える。ジョブ全体の期限・予算・中断のどれかに当たったら、その時点で止まる。

**Why this priority**: 原則 II（すべての反復と時間に上限）。工程の流れを LLM に決めさせず、コードで決める部分そのもの。

**Independent Test**: 偽の LLM で「1回目不合格 → 2回目合格」「ずっと不合格」「途中で予算切れ」「途中で期限切れ」を作り、やり直しの回数・フィードバックの中身・終わり方を確かめる。

**Acceptance Scenarios**:

1. **Given** 1回目の判定が不合格、2回目が合格、**When** 工程を実行する、**Then** 2回目の実装工程の最初の入力に、1回目の不合格の理由と diff が含まれ、結果は「合格」でやり直し回数は1
2. **Given** やり直しの上限 N とずっと不合格の検査役、**When** 工程を実行する、**Then** 実装工程は N+1 回で止まり、結果は「不合格」で最後の理由が返る
3. **Given** 途中で予算ゲートが呼び出しを止める、**When** 工程を実行する、**Then** その時点で止まり、結果は「予算切れ」
4. **Given** ジョブ全体の期限が途中で来る、**When** 工程を実行する、**Then** 実行中の LLM 呼び出し・ツール・テストを打ち切って止まり、結果は「時間切れ」
5. **Given** 呼び出し側が中断する、**When** 工程を実行中、**Then** 打ち切って止まり、結果は「中断」
6. **Given** 実装工程が「失敗」「拒否が続いた」「ターン数の上限」で終わる、**When** 工程を実行する、**Then** その回は判定に進まず、不合格の理由（実装工程の終わり方）を付けてやり直しに数える。「失敗」は作業場や LLM の異常なので、やり直さず工程全体を「失敗」で終える
7. **Given** 工程の境目（計画→実装→テスト→判定）、**When** 工程が進む、**Then** 呼び出し側に境目が知らされる（007 が状態を進めるため）

---

### User Story 5 - ローカルのリポジトリで計画から判定まで回す CLI (Priority: P2)

開発者は、ローカルのリポジトリと Issue 文（ファイル）を指定してコマンドを実行すると、リポジトリの複製に作業場を用意し、依存をインストールし、計画から判定までを1回通して、結果（合否・理由・計画・やり直し回数・リクエスト数・diff の要約・軌跡の場所）を見られる。計画を手で渡せば計画役を飛ばせる。

**Why this priority**: GitHub なしで「LLM ＋ハーネス」を作り込む入口（実装計画2章）。AI解禁の日に さくらで回す手順もこれを使う。工程そのもの（P1）が先にないと作れないので P2。

**Independent Test**: 偽の LLM・偽の作業場を差し込んで CLI の入口を呼び、表示・終了コード・後片付けを確かめる。実際のモデルとコンテナを使う実行は手動で確かめる。

**Acceptance Scenarios**:

1. **Given** 開発用の設定・ローカルのリポジトリ・Issue 文のファイル、**When** CLI を実行する、**Then** 元のリポジトリは変えずに複製の上で工程が通り、結果が表示され、作業場が片付けられ、複製（変更済み）は残る
2. **Given** 計画のファイルを指定、**When** CLI を実行する、**Then** 計画役を呼ばずに、そのファイルを計画として使う
3. **Given** 提供元が さくらの設定、**When** 明示の指定なしに CLI を実行する、**Then** 実行を拒む（AI解禁前に誤って さくらを呼ばないため）
4. **Given** 合格・不合格・失敗のそれぞれ、**When** CLI が終わる、**Then** 終了コードで区別できる。機械が読める形（JSON）でも出せる
5. **Given** 途中で中断（Ctrl-C）、**When** CLI が止まる、**Then** 作業場は片付けられる

---

### Edge Cases

- 計画の作業の種類が、決まった一覧（bugfix・test・docs・refactor・feature など）にない → 形が合わないものとして再要求の対象にする
- 計画の受け入れ条件が0件 → 形が合わないものとして再要求の対象にする
- LLM の出力が JSON の前後に説明文やコードブロックの囲みを含む → 最初の JSON オブジェクトを取り出して検証する。取り出せなければ形が合わないものとする
- 検査役が合格と言いながら、満たしていない受け入れ条件を挙げる → 判定の値（合格・不合格）だけで決める。理由は報告にそのまま使う
- テストのコマンドがない（設定で空）→ 工程内テストは飛ばし、「テストなし」と記録して判定に進む（設定の検証で警告を出す）
- 作業場の中でテストのコマンドが起動できない（コマンドがない・作業場が落ちた）→ テスト失敗として扱わず、工程全体を「失敗」で終える（コードの問題ではないため）
- 変更が出荷できないパスに触れている（`.github/workflows` など）→ 本機能では止めない。判定の材料として diff に含まれ、止めるのは 008 の出荷前チェック
- やり直しで前回の変更が壊されている → 判定でそのまま見る。前回の diff ではなく「今の diff」を渡すので、検査役は最終の状態だけを見る
- 予算の残りが計画1回分にも満たない → LLM を呼ばずに「予算切れ」で終わる
- 実装役が出力の上限で切れたまま完了した → 工程内テスト・判定はいつもどおり行う（判定に任せる）
- Issue の本文が空で依頼の本文だけがある（またはその逆）→ ある方だけを渡す。両方空なら LLM を呼ばずに「失敗（依頼が空）」

## Requirements *(mandatory)*

### Functional Requirements

**工程の入口と結果**

- **FR-001**: ファクトリーは、ジョブ ID・作業場・作業ディレクトリ・Issue（タイトルと本文）・依頼の本文（任意）・期限・中断の合図・工程の境目の知らせ先を受け取り、計画から判定までを1回実行して結果を返す入口を提供しなければならない。計画を受け取った場合は計画役を飛ばす
- **FR-002**: 結果は、終わり方（合格・不合格・失敗・予算切れ・時間切れ・中断）、計画、最後の判定の理由、やり直しの回数、実装工程の各回の要約（終わり方・テストの結果・判定）、ジョブ内の LLM のリクエスト数、最後の diff とその要約（変更したファイル数・行数）、失敗の原因（失敗のとき）を含まなければならない
- **FR-003**: 入口は例外で呼び出し側を落としてはならない。LLM・作業場・記録の異常はすべて終わり方として返す
- **FR-004**: 工程の遷移（計画→実装→テスト→判定→やり直し・終了）はコードで決め打ちにし、LLM の出力で工程の順番を変えてはならない
- **FR-005**: 工程の境目（計画・実装・テスト・判定に入るとき）を、呼び出し側に順に知らせなければならない

**計画役**

- **FR-006**: 計画役は、Issue 文・依頼の本文・リポジトリの構成（ファイルの一覧。上限で切り詰め）・AGENTS.md を入力に、ツールの定義を渡さない1回の呼び出しで計画を出さなければならない。モデル名は設定の計画役のものを使う
- **FR-007**: 計画は、概要・作業手順（1件以上）・受け入れ条件（1件以上）・作業の種類（決まった一覧のどれか）を持つ形でなければならない。形はスキーマで検証する
- **FR-008**: 計画の出力が形に合わなければ、合わなかった点を添えて1回だけ再要求しなければならない。2回目も合わなければ、工程全体を「失敗（計画を得られない）」で終える
- **FR-009**: 計画役に渡す Issue 文・依頼の本文・AGENTS.md・ファイルの一覧は、データであることがわかる区切りで囲み、区切りの中の指示に従わないことをシステムの指示で伝えなければならない
- **FR-010**: 実装工程には、計画を人が読める文章にして渡さなければならない

**工程内テスト**

- **FR-011**: 工程内テストのコマンドは設定に順に並べた一覧とし、対象リポジトリの中のファイルから読んではならない。既定は CI と同じ `pnpm run check` の1件とする
- **FR-012**: 工程内テストは実装役が完了を告げたときに作業場の中で順に実行し、最初に失敗したところで止めなければならない。LLM は使わない
- **FR-013**: 各コマンドには時間の上限を設け、超えたら打ち切って失敗として扱わなければならない
- **FR-014**: テストが失敗したら、失敗したコマンド名・終了コード・ログ（先頭と末尾を残して切り詰め、秘密情報を伏せたもの）を実装役に差し込み、実装工程を続けさせなければならない。差し込みは1回の実装工程につき設定の回数（既定3回）までとする
- **FR-015**: 差し込みの上限を超えてもテストが通らなければ、実装工程を終え、検査役を呼ばずに「不合格（テスト失敗）」として扱わなければならない
- **FR-016**: コマンドを起動できない（作業場が使えない）ときは、テスト失敗ではなく工程全体の「失敗」としなければならない

**判定**

- **FR-017**: 判定は、テストに通った変更があるときだけ、検査役に Issue 文・依頼の本文・計画（受け入れ条件を含む）・diff・テストの結果を渡し、ツールの定義を渡さない1回の呼び出しで行わなければならない。モデル名は設定の検査役のものを使う
- **FR-018**: 判定の出力は、合否・理由・受け入れ条件ごとの満たしたかどうか・直すべき点（不合格のとき）を持つ形でなければならない。形はスキーマで検証し、合わなければ1回だけ再要求する。2回目も合わなければ工程全体を「失敗（判定できない）」で終える
- **FR-019**: 検査役のモデル名が実装役のモデル名と同じ設定では、LLM を呼ぶ前に工程を拒まなければならない（原則 III）
- **FR-020**: 検査役に渡す diff とテストのログは、それぞれ設定の上限で切り詰め、切り詰めたことを示さなければならない。Issue 文・依頼の本文・diff・ログはデータの区切りで囲む
- **FR-021**: diff が空なら、検査役を呼ばずに「不合格（変更なし）」として扱わなければならない
- **FR-022**: diff は作業ディレクトリの、工程を始めた時点からの全変更（追跡していない新しいファイルを含む）とし、ホスト側で取り出す

**やり直しと上限**

- **FR-023**: 不合格（判定の不合格・テスト失敗・変更なし・実装工程のターン数の上限・拒否が続いた）なら、作業ディレクトリを戻さずに、新しい会話で実装工程をやり直さなければならない。フィードバックには、不合格の理由と今の diff を渡す
- **FR-024**: やり直しの回数は設定の上限（判定不合格のやり直しの上限）までとし、使い切っても合格しなければ「不合格」で終えなければならない
- **FR-025**: 実装工程が「失敗」で終わったら、やり直さずに工程全体を「失敗」で終えなければならない
- **FR-026**: ジョブ全体の期限を、実装工程・テストのコマンド・計画役と検査役の呼び出しのすべてに効かせ、期限を過ぎたら打ち切って「時間切れ」で終えなければならない
- **FR-027**: 予算ゲートが呼び出しを止めたら、どの工程でも「予算切れ」で終えなければならない
- **FR-028**: 呼び出し側の中断で、実行中の工程を打ち切って「中断」で終えなければならない

**予算と記録**

- **FR-029**: 計画役・検査役の呼び出しは、すべて 002 の予算ゲートを通し、工程（計画・判定）と役割（計画役・検査役）を付けて記録しなければならない。再要求も1回として数える
- **FR-030**: 計画役・検査役の呼び出しの入力・出力・検証の結果と、工程内テストの実行（コマンド・終了コード・時間・切り詰めたログ）と、やり直しの判断を、004 と同じジョブごとの軌跡に時系列で残さなければならない。書く前に秘密情報を伏せる
- **FR-031**: 計画と判定の各回の要約（何回目か・結果・リクエスト数・時刻）を SQLite にも残さなければならない
- **FR-032**: 軌跡に書けなかったら、工程全体を「失敗」で終えなければならない

**CLI**

- **FR-033**: 開発者が、ローカルのリポジトリ・Issue 文のファイル・依頼の本文（任意）・計画のファイル（任意）を指定し、計画から判定までを1回実行できるコマンドを提供しなければならない。元のリポジトリは変えず、複製の上で作業し、作業場の用意（依存のインストールを含む）と片付けをこのコマンドが行う
- **FR-034**: CLI は、終わり方・最後の判定の理由・計画の概要・やり直しの回数・リクエスト数・diff の要約・複製の場所・軌跡の場所を表示し、終わり方を終了コードで区別しなければならない。機械が読める形でも出せなければならない
- **FR-035**: CLI は、提供元が さくらの設定では、明示の指定がない限り実行を拒まなければならない
- **FR-036**: 004 の手で試すコマンドは本機能の CLI に統合し、計画のファイルを渡す使い方で置き換えなければならない
- **FR-037**: CLI で送るのは公開してよいリポジトリと Issue 文だけであることを、開発用の設定のときに表示で知らせなければならない

**テスト**

- **FR-038**: 計画・工程内テスト・判定・やり直し・上限は、偽の LLM と偽の作業場を使った自動テストで確かめられなければならない。自動テストで実際の LLM を呼んではならない

### Key Entities *(include if feature involves data)*

- **工程の入力**: ジョブ ID、作業場、作業ディレクトリ、Issue（タイトル・本文）、依頼の本文、計画（任意）、期限、中断の合図、境目の知らせ先
- **計画**: 概要、作業手順の列、受け入れ条件の列、作業の種類
- **工程内テストの結果**: 合格・失敗、実行したコマンドごとの終了コード・時間・切り詰めたログ、打ち切りの有無
- **判定**: 合否、理由、受け入れ条件ごとの結果、直すべき点
- **実装の回**: 何回目か、実装工程の終わり方、差し込みの回数、テストの結果、判定（または判定しなかった理由）
- **工程の結果**: 終わり方、計画、各回の要約、最後の判定の理由、やり直しの回数、リクエスト数、diff と要約、失敗の原因、軌跡の場所

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 偽の LLM と偽の作業場で、「計画 → 実装 → テスト → 判定（合格）」が通り、結果「合格」と diff が返る
- **SC-002**: 計画役と検査役の呼び出しで、ツールの定義を含む呼び出しが 0 件
- **SC-003**: 形の合わない出力が続く確認で、計画役・検査役のそれぞれで LLM の呼び出しが 2 回を超えない
- **SC-004**: ずっと不合格の確認で、実装工程の回数がやり直しの上限＋1 を超えない。工程内テストの差し込みが1回の実装工程につき上限を超えない
- **SC-005**: テストに通っていない変更で検査役が呼ばれた回数が 0 件
- **SC-006**: 期限・予算・中断のそれぞれの確認で、止まったあとに LLM の呼び出しもコマンドの実行も起きない
- **SC-007**: どの終わり方でも呼び出し側に例外が届かず、結果が返る（各終わり方の確認で 100%）
- **SC-008**: 予算ゲートの中で再試行が起きなかったとき、ジョブ内の LLM の呼び出し件数（予算ゲートの記録）と、結果のリクエスト数と、軌跡の応答の件数が一致する（再試行があれば、記録と結果のリクエスト数は再試行も含めて一致する）
- **SC-009**: 秘密情報の形をした文字列を Issue 文とテストのログに混ぜた実行で、軌跡と SQLite と CLI の表示に平文が 1 件も現れない
- **SC-010**: 開発者が CLI の1回のコマンドで、公開してよい小さなリポジトリの Issue 1件について、計画から判定までの結果を見られる（手動の確認）

## Assumptions

- 作業場（003）・実装工程と steering と軌跡（004）・予算ゲート（002）は完成済みのものを使う。実装役の完了の時点でテストを差し込むために、004 の実装工程に「完了を告げたときに呼ぶ口」を足す必要があれば、本機能で足す
- 007 の Worker は本機能の入口を「作業ディレクトリ・Issue・依頼の本文を渡し、合否と理由を受け取る」形で呼ぶ（007 の data-model の PipelinePort）。本機能はその形に合わせる。状態（`planning` など）を進めるのは 007 で、本機能は境目を知らせるだけにする
- clone・作業ブランチの作成・依存のインストール・作業場の片付けは呼び出し側（007・CLI）が行う。本機能の入口は用意済みの作業場を受け取る
- commit・push・PR・出荷前チェック（diff の上限・禁止パス・gitleaks）は 008 で行う。作業の種類を許可リストと照らすのも 008
- 作業の種類の一覧は bugfix・test・docs・refactor・feature・chore とする（008 の許可リストの既定は bugfix・test・docs・refactor）
- 工程内テストの差し込みの上限（3回）、コマンドの時間の上限（bash の上限と同じ）、diff・ログ・ファイル一覧の切り詰めの上限は仮の値とし、設定で変えられるようにする。012 の回帰評価と実機の調整（AI解禁後）で直す
- 「関係するテストだけ」を選んで実行する仕組みは作らない。設定のコマンドを丸ごと実行する（CI とコマンドをそろえる方針を優先）
- ジョブ全体の期限は呼び出し側が渡す（007 は `job_timeout_minutes`、CLI は指定がなければ同じ値）
- 自動テストは偽の LLM（002 の偽の `fetch`）と偽の作業場（004）で行う。実際のモデルでの確認は CLI で手動で行い、AI解禁前は Google AI Studio で公開してよいデータだけを使う
- 012 の回帰評価は本機能の入口の上に作る。本機能は評価用の仕組みは持たない
