## Clarifications

### Session 2026-11-14

007・008 と同じく、人間の確認が要るものは、いったん推奨する内容で決めた（`/speckit-clarify` と PR で見直せる）。

- Q: CI が「通った」「落ちた」は何で決めるか？ → A: ファクトリーが push した commit に付いたチェックをすべて集めて決める（推奨）。すべて終わってから判断し、1つでも失敗（成功・中立・スキップ以外の終わり方）があれば「失敗」、すべて成功・中立・スキップなら「通過」。チェックの結果の知らせ（Webhook）は判断のきっかけにだけ使い、結果は毎回取り直す。知らせはワークフローごとに届くので、1件の成功の知らせだけで通過とみなさない
- Q: CI が通ったあと、ジョブはどこまで進めるか？ → A: `ci_waiting` のまま、PR がマージされた知らせを受けたら `merged` に進める（推奨）。マージされずに PR が閉じられたら `failed`（理由: PR が閉じられた）。CI が通ったあとは CI 待ちの時間切れを当てない（Draft PR は人間の確認を待つので、時間で失敗にしない）。`merged` から先（デプロイ）は 010
- Q: 時間切れ・やり直しの上限でファクトリーが諦めたとき、PR はどうするか？ → A: PR は閉じずに Draft に変えて人間に渡し、PR の本文に理由を書き足す（推奨）。ジョブは `failed` にして Issue に1回報告する。CI が後から通っても、自動ではマージされないようにする
- Q: やり直しの作業ディレクトリは何から作るか？ → A: 作業ブランチを取り直し、PR の変更全体（最初の基準からの差分）を、まだ commit していない変更として作業ディレクトリに戻してから実装工程を始める（推奨）。直した結果は作業ブランチに新しい commit として積んで push する（強制の push をしない）。検査役には PR の変更全体を見せる
- Q: やり直したあとの自動マージの振り分けはどうするか？ → A: 出荷前チェックを PR の変更全体でやり直す。auto-merge だった PR が条件を満たさなくなったら Draft に変える。Draft だった PR は、条件を満たしても Draft のままにする（推奨。一度人間に渡したものを機械が取り上げない）。秘密情報・CI の定義の変更で止まったら push しない（008 と同じ）
- Q: CI 失敗のやり直しと、新しい依頼のどちらを先に処理するか？ → A: CI 失敗のやり直しを先にする（推奨。始めたものを先に終わらせ、PR が開いたまま待つ時間を短くする）。やり直し1回ごとに、ジョブ全体の時間の上限を新しく数える

## User Scenarios & Testing *(mandatory)*

この機能の利用者は3種類いる。

- **依頼者**（対象リポジトリに書き込み権限のある開発者）: CI で落ちた PR を、人間が手を出さなくてもファクトリーが直してくれることを期待する。直せないときは、なぜ止まったかを知る
- **レビュアー**（Draft PR を受け取る人間）: CI の結果とやり直しの経緯を PR の本文で読み、引き取るか決める
- **運用者**: CI の初回通過率・やり直しの回数・時間切れを記録で追い、記事の検証に使う

### User Story 1 - CI の結果を受けて、待っているジョブを先へ進める (Priority: P1)

ファクトリーは、PR を作ったジョブを `ci_waiting` にしたまま次の依頼の処理に進む。対象リポジトリの CI が終わった知らせを受けたら、ファクトリーが push した commit のチェックをすべて取り直し、通過・失敗・まだ途中かを決める。通過したら PR の本文に CI の結果を書き足し、PR がマージされた知らせで `merged` に進める。

**Why this priority**: レベルB（`03` 0章）の「CI 通過後に自動マージ」をファクトリーの状態に反映する最初の一歩。008 までは `ci_waiting` のジョブは永久にそのまま残っていた。

**Independent Test**: 偽の GitHub に CI の結果を持たせ、署名付きの知らせを受付に送って、ジョブの記録・PR の本文・状態の移り変わりを確かめる。Worker が別のジョブを処理している間でも、CI の結果が処理されることを確かめる。

**Acceptance Scenarios**:

1. **Given** `ci_waiting` のジョブと、その commit のチェックがすべて成功した CI、**When** CI が終わった知らせを受ける、**Then** ジョブの記録に「CI 通過」が残り、PR の本文に CI の結果が書き足される。状態は `ci_waiting` のまま
2. **Given** CI が通ったジョブ、**When** PR がマージされた知らせを受ける、**Then** 状態が `ci_waiting` → `merged` に移り、PR の本文に「マージされた」が書き足される
3. **Given** ワークフローが2つあり、片方だけが終わった、**When** 終わった方の知らせを受ける、**Then** 通過とも失敗とも決めず、ジョブはそのまま待つ
4. **Given** Worker が別のジョブの実装工程を処理している、**When** CI の知らせを受ける、**Then** CI の結果の判断と PR の本文の更新は、Worker の処理を待たずに行われる
5. **Given** ファクトリーが push していない commit（人間が足した commit、前の push）の知らせ、**When** 受ける、**Then** そのジョブの状態を変えない
6. **Given** ファクトリーのジョブに対応しない作業ブランチの知らせ（人間の PR など）、**When** 受ける、**Then** 何もせずに受け取ったとだけ返す
7. **Given** マージされずに PR が閉じられた、**When** 知らせを受ける、**Then** `failed`（理由: PR が閉じられた）にし、Issue に1回報告する

### User Story 2 - CI の失敗をログ付きで実装役に戻して直す (Priority: P1)

ファクトリーは、CI が失敗したら、失敗したチェックの名前とログ（失敗した箇所の前後だけに切り詰め、秘密情報を伏せたもの）を取り、前回の変更と一緒に実装役に渡して、新しい会話で実装工程をやり直す。工程内テスト・判定を通ったら、作業ブランチに新しい commit を積んで push し、`ci_waiting` に戻る。やり直しには回数の上限がある。

**Why this priority**: `04` 3章のフィードバック（CI）。ファクトリー内のテストで見逃した失敗を、人間の手を借りずに直す。ハーネスの効き目（CI 初回通過率・やり直しで直った割合）は記事の検証の柱になる。

**Independent Test**: 偽の GitHub に失敗した CI とそのログを持たせ、偽の 005 の入口で、渡されたフィードバック（失敗したチェックの名前・切り詰めたログ・前回の diff）と、作業ブランチへの追加の push、状態の移り変わり（`ci_waiting` → `implementing` → … → `judging` → `pr_opened` → `ci_waiting`）を確かめる。

**Acceptance Scenarios**:

1. **Given** CI が失敗したジョブ（やり直しの回数が上限未満）、**When** 判断する、**Then** やり直しを待つ印を付け、Worker が次に取り出すときに CI のやり直しを新しい依頼より先に取り出す
2. **Given** やり直しを取り出した、**When** 実装工程を始める、**Then** 実装役への入力に、失敗したチェックの名前・切り詰めたログ・前回の diff（PR の変更全体）が区切られたデータとして入り、ログの中の指示に従わないよう伝えられる。会話は前回のものを引き継がない
3. **Given** 長いログ（数万行）、**When** 切り詰める、**Then** 失敗を示す行の前後を残し、上限の文字数以内になる。失敗を示す行が見つからなければ末尾を残す
4. **Given** ログに秘密情報らしい文字列が含まれる、**When** 実装役に渡す・記録する、**Then** 伏せ字になっている
5. **Given** やり直しの実装工程の前に工程内テストを回したら通った（ファクトリー内で再現しない）、**When** 実装役に渡す、**Then** 「工程内テストでは再現しない」ことが入力に書かれている
6. **Given** やり直しが判定に合格した、**When** 出荷する、**Then** 作業ブランチに新しい commit が1つ積まれ、強制せずに push され、新しい PR は作られない。状態は `judging` → `pr_opened` → `ci_waiting` と移り、やり直しの回数が1増える
7. **Given** やり直しで作業ディレクトリに前回からの変更がない（実装役が何も直さなかった）、**When** 出荷しようとする、**Then** push せずに `failed`（理由: CI の失敗を直せなかった）にする
8. **Given** やり直しの回数が上限に達したジョブの CI が失敗した、**When** 判断する、**Then** やり直さずに `failed`（理由: CI の失敗）にし、PR を Draft に変え、Issue に失敗したチェックの名前を含めて1回報告する
9. **Given** やり直しの実装工程・判定が失敗した（判定の不合格の上限、予算切れなど）、**When** 終わる、**Then** 005・007 の分類どおり `failed` にして Issue に報告し、PR を Draft に変える
10. **Given** やり直しの出荷前チェックで、PR の変更全体が自動マージの条件を満たさなくなった（diff が上限を超えたなど）、**When** 出荷する、**Then** auto-merge だった PR を Draft に変え、満たさなかった条件を PR の本文に書く。Draft だった PR は Draft のまま

### User Story 3 - CI を待ちすぎたら諦めて人間に渡す (Priority: P1)

ファクトリーは、PR を作って（または直して push して）から一定の時間（既定 30 分）が過ぎても CI の結論が出なければ、チェックの結果を一度取り直し、それでも決まらなければ `failed`（理由: CI 待ちの時間切れ）にして PR を Draft に変え、Issue に報告する。CI の知らせを取りこぼしたとき（ファクトリーの停止中など）も、この取り直しで拾う。

**Why this priority**: 原則 II（すべての待ちに上限を設ける）。CI が動かないリポジトリ・ワークフローの詰まり・知らせの取りこぼしで、ジョブが永久に残らないようにする。

**Independent Test**: 時計を進めて、時間切れの扱い（取り直し → 結論があればそれに従う、なければ失敗）を確かめる。再起動のあとに `ci_waiting` のジョブが残り、取り直しが行われることを確かめる。

**Acceptance Scenarios**:

1. **Given** CI 待ちの時間の上限を過ぎ、チェックがまだ途中（またはチェックが1つもない）、**When** ファクトリーが見回る、**Then** `failed`（理由: CI 待ちの時間切れ）にし、PR を Draft に変え、Issue に1回報告する
2. **Given** 時間の上限を過ぎたが、取り直したら CI が失敗していた（知らせを取りこぼしていた）、**When** 見回る、**Then** 時間切れではなく CI の失敗として扱う（やり直し、または上限なら失敗）
3. **Given** 時間の上限を過ぎたが、取り直したら CI が通っていた、**When** 見回る、**Then** CI 通過として扱い、失敗にしない
4. **Given** ファクトリーを再起動した、**When** 起動する、**Then** `ci_waiting` のジョブは失敗にならずに残り、CI の結論がまだないジョブのチェックを取り直す
5. **Given** CI が通って人間のマージを待っている Draft PR のジョブ、**When** 時間の上限を過ぎる、**Then** 失敗にしない

---

### User Story 4 - CI 連携の上限と切り詰めを設定で変える (Priority: P2)

運用者は、CI 失敗後のやり直しの回数の上限・CI 待ちの時間の上限・実装役に渡す CI のログの上限・見回りの間隔を、設定ファイルで変えられる。不正な値ではファクトリーは起動しない。

**Why this priority**: 記事の検証で、やり直しの上限と CI 初回通過率の関係を比べる。既定の値で P1 は動くので P2。

**Independent Test**: 設定の値を変えて、同じ CI の失敗の扱い（やり直す・諦める）とログの長さが変わることを確かめる。不正な値で起動しないことを確かめる。

**Acceptance Scenarios**:

1. **Given** やり直しの上限を 0 にした設定、**When** CI が失敗する、**Then** やり直さずに `failed`（理由: CI の失敗）にする
2. **Given** ログの上限を下げた設定、**When** ログを切り詰める、**Then** 新しい上限以内になる
3. **Given** 不正な設定（ログの上限が小さすぎる、見回りの間隔が 0）、**When** 起動する、**Then** 項目の名前を含むエラーで起動しない

---

### Edge Cases

- 同じ CI の結果の知らせが2回届く（GitHub の再送・ワークフローが複数） → 判断を2回しても、やり直しの印・失敗の報告・PR の本文の書き足しは1回だけ
- CI の知らせが、やり直しの実装工程の途中（状態が `implementing` など）に届く → 待っている状態ではないので無視する。push する commit が変わるので、前の commit の結果は使わない
- チェックが「キャンセル」で終わった（同じブランチへの次の push で打ち切られたなど） → 失敗として扱う。ただしファクトリーが push した最新の commit のチェックだけを見るので、古い commit のキャンセルは見ない
- 失敗したチェックのログを取れない（権限がない・ログが消えた・GitHub Actions 以外のチェック） → チェックが返した要約の文を使い、それもなければ「ログを取れなかった」とだけ書いてやり直す
- 失敗したチェックが多い（10 個以上） → 上限の個数までのログを渡し、残りは名前だけを書く
- CI のログに `@agent` やプロンプトのような文がある → データとして区切りの中に入れ、指示として扱わない（原則 IV）
- やり直しのあいだに、人間が作業ブランチに commit を push した → 作業ブランチを取り直すので人間の commit も含めて直す。ただし push は強制しないので、取り直したあとにさらに push されていたら push が拒否され、`failed`（理由: 出荷の失敗）にする
- やり直しのあいだに PR がマージ・クローズされた → push の前に PR の状態を確かめ、開いていなければ push せずに `failed`（理由: PR が閉じられた）にする
- 作業ブランチがリモートから消えていた → 取り直せないので `failed`（理由: 取得の失敗）にする
- やり直しの途中で再起動・停止 → 007 と同じく `failed`（再起動・停止で中断）にし、PR を Draft に変える
- 予算が尽きた状態で CI が失敗した → やり直しを取り出し、005 の予算ゲートが止めるので `failed`（理由: 予算切れ）になる
- CI が通ったあと、人間が Draft を解除して自分でマージした → マージの知らせで `merged` に進める（ファクトリーがマージしたかどうかは問わない）
- 008 で自動マージの状態を確定できなかった PR（`unsettled`） → CI の扱いは同じ。諦めるときに Draft への変更を試み、失敗したら記録に残す
- CI 待ちの時間の上限を過ぎたあとに CI の結果の知らせが届く → ジョブがすでに `failed` なら無視する

## Requirements *(mandatory)*

### Functional Requirements

**CI の結果の受信と判断**

- **FR-001**: ファクトリーは、対象リポジトリの CI が終わった知らせ（`check_suite` の完了）を、008 までと同じ受付（署名の検証のあと）で受けなければならない。依頼のコメントと同じく、受付は短い時間で応答し、重い処理を応答のあとに回す
- **FR-002**: 知らせは、リポジトリと作業ブランチの名前と commit で `ci_waiting` のジョブに結び付けなければならない。ファクトリーが最後に push した commit 以外の知らせ、ジョブに結び付かない知らせは、状態を変えずに無視する
- **FR-003**: CI の結論は、その commit に付いたチェックをすべて取り直して決めなければならない。すべて終わり、成功・中立・スキップだけなら「通過」、すべて終わり、それ以外の終わり方が1つでもあれば「失敗」、終わっていないものがある・チェックがないなら「途中」とする
- **FR-004**: CI の結論の判断・PR の本文の書き足し・時間切れの見回りは、LLM を使う工程（Worker）を待たずに行わなければならない（`ci_waiting` はワーカーを占有しない）
- **FR-005**: 同じ結論を2回判断しても、やり直しの印・失敗の報告・PR の本文の書き足し・状態の遷移が重複してはならない

**CI 通過とマージ**

- **FR-006**: CI が通過したら、ジョブの記録に残し、PR の本文に CI の結果を書き足さなければならない。状態は `ci_waiting` のままにする
- **FR-007**: PR がマージされた知らせ（`pull_request` の closed でマージ済み）を受けたら、`ci_waiting` → `merged` に移し、PR の本文に書き足さなければならない。マージは GitHub（ブランチ保護と auto-merge、または人間）が行い、ファクトリーはマージしない
- **FR-008**: マージされずに PR が閉じられたら、`failed`（理由: PR が閉じられた）にし、Issue に1回報告しなければならない

**CI 失敗のやり直し**

- **FR-009**: CI が失敗し、やり直しの回数が設定の上限未満なら、やり直しを待つ印を付けなければならない。上限に達していれば、やり直さずに `failed`（理由: CI の失敗）にする
- **FR-010**: Worker は、やり直しを待つジョブを新しい依頼より先に取り出し、`ci_waiting` → `implementing` に移してやり直しの回数を1増やさなければならない。やり直し1回ごとに、ジョブ全体の時間の上限を取り出した時刻から数え直す
- **FR-011**: やり直しでは、作業ブランチを取り直し、最初の基準（PR を作ったときの既定のブランチの commit）からの変更全体を、まだ commit していない変更として作業ディレクトリに戻してから、005 の入口を呼ばなければならない。計画は最初の出荷のときのものを使い、計画役を呼ばない
- **FR-012**: 実装役の最初の入力に、失敗したチェックの名前・終わり方・ログ（切り詰め・伏せ字済み）と、前回の diff（PR の変更全体）を、区切られたデータとして入れなければならない。会話は前回のものを引き継がず、新しく始める（`04` 3章）
- **FR-013**: ログは、失敗を示す行（エラーの印・失敗の印）の前後だけを残して、設定の上限以内に切り詰めなければならない。見つからなければ末尾を残す。行の先頭の時刻などの飾りは取り除いてよい
- **FR-014**: ログは、秘密情報を伏せてから実装役に渡し、記録しなければならない（001 のマスクと同じ判定）。ログ・チェックの名前・要約は Issue 本文と同じく「データ」として扱い、指示として扱ってはならない（原則 IV）
- **FR-015**: 実装工程を始める前に工程内テストを一度回し、通ったら「工程内テストでは再現しない」ことを実装役の入力に書かなければならない（LLM は使わない）
- **FR-016**: やり直しが判定に合格したら、作業ディレクトリの前回の push からの変更だけを、作業ブランチに新しい1つの commit として積み、強制せずに push しなければならない。新しい PR は作らない。前回の push からの変更がなければ push せずに `failed`（理由: CI の失敗を直せなかった）にする
- **FR-017**: やり直しの出荷前チェック（008 の6条件）は、自動マージの判断に使う条件（diff の大きさ・禁止パス・作業の種類・ラベル・判定）を PR の変更全体で、秘密情報のスキャンを新しい commit で評価しなければならない。秘密情報・CI の定義の変更で止まったら push しない（008 と同じ）
- **FR-018**: やり直しのあとの振り分けは、auto-merge だった PR が条件を満たさなくなったら Draft に変え、Draft だった PR は Draft のままにしなければならない（Draft から auto-merge に上げない）
- **FR-019**: push の前に PR がまだ開いていることを確かめ、開いていなければ push せずに `failed`（理由: PR が閉じられた）にしなければならない
- **FR-020**: push したら、状態を `judging` → `pr_opened` → `ci_waiting` と移し、CI 待ちの時間の上限を数え直し、PR の本文を書き直さなければならない（計画・結果は今回のもの、CI の経緯はそれまでのものを残す）

**時間切れと再起動**

- **FR-021**: CI 待ちの時間の上限（PR を作った・push した時刻から）を過ぎても結論がなければ、チェックを取り直し、結論があればそれに従い、なければ `failed`（理由: CI 待ちの時間切れ）にしなければならない。CI が通過したジョブには時間の上限を当てない
- **FR-022**: 起動時の掃除は `ci_waiting` のジョブを `failed` にしてはならない。起動したら、結論がまだない `ci_waiting` のジョブのチェックを取り直さなければならない（停止中に知らせを取りこぼしたときのため）
- **FR-023**: ファクトリーが諦めたとき（CI の失敗の上限、CI 待ちの時間切れ、やり直しの工程の失敗）は、PR を閉じずに Draft に変え、PR の本文に理由を書き足さなければならない。Draft への変更に失敗しても、ジョブの失敗の報告は行う

**レポート**

- **FR-024**: PR の本文の CI の欄に、CI の経緯（何回目の CI か・通過か失敗か・失敗したチェックの名前・やり直しの push・時間切れ・マージ）を書き足さなければならない。008 のまとめレポートのほかの部分は消さない
- **FR-025**: CI に関する失敗の報告（CI の失敗の上限・時間切れ・PR が閉じられた・直せなかった）は、007 の失敗の報告として Issue に1回だけ投稿し、PR への参照・やり直しの回数・失敗したチェックの名前を含めなければならない。ログの本文は Issue に書かない
- **FR-026**: CI の結果・やり直し・時間切れ・マージは、ジョブの記録に残さなければならない（CI 初回通過率・やり直しで直った割合を記録から集計できること）

**GitHub 層と設定**

- **FR-027**: CI の知らせ・マージの知らせの読み取り、チェックの結果とログの取得、PR の状態と本文の取得は、GitHub 層にまとめなければならない（原則 VII）。ほかの層に GitHub の型を出さない
- **FR-028**: CI 失敗後のやり直しの上限・CI 待ちの時間の上限（001 で既にある）・実装役に渡す CI のログの上限・見回りの間隔は、設定で変えられなければならない。不正な値ではファクトリーは起動しない

**テスト**

- **FR-029**: CI の結論の判断・ログの切り詰め・やり直し（ローカルの bare リポジトリへの追加の push）・時間切れ・マージ・受付は、GitHub と LLM を使わない自動テストで確かめられなければならない

### Key Entities *(include if feature involves data)*

- **ジョブ（Job）**: 007 の `jobs`。CI の待ちのために、最初の基準の commit・最後に push した commit・CI の結論（途中・通過・失敗）・CI 待ちの期限・知らせを受けた印を持つ。やり直しの回数は 001 の `ci_retries`
- **CI の結論（CI result）**: 対象の commit、結論（通過・失敗・途中）、チェックごとの名前・終わり方・ログを取るための手がかり
- **CI のフィードバック（CI feedback）**: 失敗したチェックの名前と終わり方、切り詰めて伏せ字にしたログ、工程内テストで再現したか、前回の diff
- **ジョブの記録（Job event）**: CI の結論、やり直しの開始、やり直しの push、時間切れ、マージ、PR を Draft に変えた・変えられなかった
- **設定**: `[limits].ci_retries`・`[limits].ci_wait_timeout_minutes`（001）、CI のログの上限、見回りの間隔

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: CI が失敗した確認セットで、やり直しの上限以内のジョブの 100% が実装工程をやり直し、上限を超えたジョブの 100% が `failed` になって Issue に1回だけ報告される
- **SC-002**: CI の知らせを受けてから、結論の判断（PR の本文の書き足し・やり直しの印）までが、Worker が別のジョブを処理していても 1 分以内
- **SC-003**: `ci_waiting` のジョブが、CI 待ちの時間の上限 ＋ 見回りの間隔を過ぎても結論なしで残る件数が 0（CI が通過してマージを待つジョブを除く）
- **SC-004**: 実装役に渡す CI のログが、100% 設定の上限以内で、秘密情報らしい値を含まない
- **SC-005**: 同じ知らせを2回送った確認セットで、やり直し・報告・PR の本文の書き足しが重複する件数が 0
- **SC-006**: やり直しの push で、強制の push・新しい PR の作成が 0 件
- **SC-007**: 再起動の前後で、`ci_waiting` のジョブが失敗にならずに残る割合が 100%
- **SC-008**: 記録から、ジョブごとの CI 初回通過・やり直しの回数・最後の結論を SQL だけで集計できる
- **SC-009**: 本物の GitHub での確認（テスト用のリポジトリ）で、CI が落ちる変更がやり直しの push を受け、通過したら auto-merge でマージされて `merged` になる

## Assumptions

- 008 までで、PR を作ったジョブは `ci_waiting` で止まり、`jobs.pr_number`・`jobs.branch` が入っている。008 の出荷の工程（commit・出荷前チェック・push・PR）と 007 の失敗の報告を使い回す
- `ci_waiting` → `implementing`・`ci_waiting` → `merged` の遷移は 007 の状態の表に既にある。やり直しの合格のあとは、008 と同じく `judging` → `pr_opened` → `ci_waiting` と進める（`pr_opened` は「PR を作った・更新した」の意味で使う）
- 対象リポジトリの CI は GitHub Actions を想定する。チェックの結果は GitHub のチェックの仕組みから取るので、Actions 以外のチェックも結論の判断に含める（ログは Actions のものだけ取れる）
- GitHub App の権限は `03` 5章のとおり Checks・Actions の読み取りを持ち、`check_suite`・`pull_request` の知らせを購読している。テスト用のリポジトリの App の設定は、本物での確認の前に運用者が足す
- `push`（main への反映）の受信とデプロイ、`merged` から先の状態は 010 で作る
- CI の結果の知らせは GitHub が失敗した配送を自動では再送しないので、時間切れの見回りと起動時の取り直しで取りこぼしを拾う
- CI 待ちの時間の上限は既定 30 分（`[limits].ci_wait_timeout_minutes`）、やり直しの上限は既定 2 回（`[limits].ci_retries`）。どちらも 001 で設定にある
- テストでは GitHub の API と LLM を呼ばない。本物の GitHub での確認は AI解禁のあと、テスト用のリポジトリで行う（やり直しは実装役の LLM を使うため）
