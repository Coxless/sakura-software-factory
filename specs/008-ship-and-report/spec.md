## Clarifications

### Session 2026-11-14

007 と同じく、人間の確認が要るものは、いったん推奨する内容で決めた（`/speckit-clarify` で見直せる）。

- Q: 秘密情報のスキャンで見つかったら、Draft PR にするか、push しないか？ → A: push しない。ジョブを `failed`（理由: 秘密情報の検出）にして Issue に報告する（推奨）。Draft PR でも push した時点でリモートに残り、公開リポジトリなら誰でも読める。見つかった値は報告にも書かない（ファイルと行だけ）。スキャン自体を実行できないときも、秘密情報がないと確かめられないので同じ扱いにする
- Q: CI の定義（`.github/workflows`）を変えた diff はどうするか？ → A: push しない。`failed`（理由: 出荷できない変更）にする（推奨）。App に Workflows の書き込み権限がないので、GitHub が push を拒否する（`04` 層8）。それ以外の禁止パスの変更は、Draft PR にして人間に渡す
- Q: PR を作ったあと、ジョブはどこで止まるか？ → A: `pr_opened` → `ci_waiting` に進め、Worker はそのジョブから離れて次のジョブに進む（推奨。`03` 3章の「`ci_waiting` はワーカーを占有しない」）。CI の結果を受けて先へ進めるのと、CI 待ちの時間切れは 009 で作る。再起動のときの掃除で `ci_waiting` のジョブを `failed` にしてはならない
- Q: まとめレポートはいつ・どこに書くか？ → A: PR を作った時点で、PR の本文にまとめレポートを書き、Issue には PR へのリンクと要約を1回コメントする（推奨）。CI・マージ・デプロイの結果は 009・010 で書き足す。失敗したときは 007 のとおり Issue に失敗の報告だけを書く
- Q: PR で Issue を閉じるか？ → A: 閉じない。PR の本文で Issue を参照するだけにする（推奨）。マージしたあとにステージングで失敗して戻すこと（010）があるので、Issue を閉じる判断は人間に残す

## User Scenarios & Testing *(mandatory)*

この機能の利用者は3種類いる。

- **依頼者**（対象リポジトリに書き込み権限のある開発者）: `@agent` で頼んだ作業が PR になり、自動でマージされるのか、人間の確認を待つのかと、その理由を知る
- **レビュアー**（Draft PR を受け取る人間）: なぜ自動マージにならなかったかを読み、PR を確認して先に進めるか決める
- **運用者**: どの条件で自動マージした・しなかったかを、記録とレポートで追い、記事の検証に使う

### User Story 1 - 判定に合格した変更を PR にする (Priority: P1)

ファクトリーは、判定に合格したジョブの変更を、ホストで commit して作業ブランチを push し、対象リポジトリの既定のブランチに向けた PR を作る。PR の本文には、計画の概要・テストの結果・判定の理由・消費したリクエスト数を書き、元の Issue を参照する。作業場（コンテナ）には GitHub のトークンを渡さない。

**Why this priority**: レベルB（`03` 0章）の最初の出荷の工程。007 では判定に合格しても `failed`（出荷の工程が未実装）で終えていたものを、PR にして先に進める。

**Independent Test**: ローカルの bare リポジトリを push 先にし、偽の GitHub と偽の 005 の入口（合格を返す）で、commit・push・PR の作成が行われ、状態が `judging` → `pr_opened` → `ci_waiting` と進むことを確かめる。

**Acceptance Scenarios**:

1. **Given** 判定に合格したジョブ、**When** 出荷の工程を進める、**Then** 作業ディレクトリの変更が作業ブランチに1つの commit として記録され、push され、既定のブランチに向けた PR が1つできる
2. **Given** PR を作った、**When** 状態を見る、**Then** `judging` → `pr_opened` → `ci_waiting` と移り、移るたびに記録が1件残る。Worker は次のジョブの処理に進む
3. **Given** PR の本文、**When** 読む、**Then** 元の Issue への参照・計画の概要・テストの結果・判定の理由・消費したリクエスト数・ジョブの番号を含み、Issue を閉じるキーワードを含まない
4. **Given** commit と push、**When** 実行する、**Then** ホストで行い、トークンは作業ディレクトリの git の設定・リモートの URL・コマンドラインの引数に現れない。作業ディレクトリの git フックは実行されない
5. **Given** commit の作成者、**When** 見る、**Then** ファクトリー（GitHub App のボット）として記録されている
6. **Given** push または PR の作成が失敗する、**When** 処理する、**Then** `failed`（理由: 出荷の失敗）にし、Issue に失敗の報告を1回書く

### User Story 2 - 出荷前チェックで自動マージか Draft かを決める (Priority: P1)

ファクトリーは、PR を作る前に出荷前チェックを行う。検査役の合格、diff の大きさが上限以内、禁止パスの変更がない、秘密情報のスキャンで何も見つからない、Issue に `no-auto-merge` ラベルがない、作業の種類が許可リスト内、の6つをすべて満たすときだけ auto-merge を有効にする。1つでも満たさなければ Draft PR にして人間に渡す。秘密情報が見つかったとき（スキャンできないときを含む）と CI の定義を変えたときは、push しない。

**Why this priority**: 原則 VI（auto-merge は6条件をすべて満たすときだけ）と `04` 層6。機械の条件で自動マージを絞ることが、人間のレビューを課さないレベルBの前提になる。

**Independent Test**: 6つの条件を1つずつ外したジョブを流し、満たすときだけ auto-merge が有効になり、外したときは Draft PR になり、どの条件で外れたかが記録されることを確かめる。秘密情報を含む diff では push されないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 6つの条件をすべて満たすジョブ、**When** PR を作る、**Then** 通常の PR として作り、auto-merge を有効にする
2. **Given** diff の行数（追加と削除の合計）が上限を超えるジョブ、**When** PR を作る、**Then** Draft PR にし、理由に「diff の大きさ（実際の行数 / 上限）」を書く
3. **Given** 禁止パス（`.github/workflows` 以外）を変更したジョブ、**When** PR を作る、**Then** Draft PR にし、理由に該当するファイルを書く
4. **Given** Issue に `no-auto-merge` ラベルが付いている、**When** PR を作る、**Then** Draft PR にし、理由にラベルを書く
5. **Given** 計画の作業の種類が許可リストにない（例: `feature`）、**When** PR を作る、**Then** Draft PR にし、理由に作業の種類と許可リストを書く
6. **Given** diff に秘密情報らしい値がある、**When** 出荷前チェックをする、**Then** push も PR の作成もせず、`failed`（理由: 秘密情報の検出）にし、Issue の報告にはファイルと行だけを書き、値を書かない
7. **Given** 秘密情報のスキャンを実行できない（スキャナーがない・異常終了）、**When** 出荷前チェックをする、**Then** 6 と同じく push しない
8. **Given** CI の定義（`.github/workflows`）を変更したジョブ、**When** 出荷前チェックをする、**Then** push せず、`failed`（理由: 出荷できない変更）にする
9. **Given** 複数の条件を満たさない、**When** PR を作る、**Then** 満たさなかった条件をすべて理由に書く（最初の1つで止めない）
10. **Given** auto-merge の有効化が GitHub の側で失敗する（リポジトリで auto-merge が無効、ブランチ保護がないなど）、**When** PR を作ったあと、**Then** PR を Draft に変えて人間に渡し、理由に「auto-merge を有効にできなかった」と GitHub の返した理由を書く。ジョブは `ci_waiting` に進める

### User Story 3 - まとめレポートで、自動マージした・しなかった理由を伝える (Priority: P1)

ファクトリーは、PR を作ったら、PR の本文にまとめレポートを書き、Issue に PR へのリンクと要約を1回コメントする。レポートには、6つの条件それぞれの結果（満たした・満たさない、その値）と、自動マージを有効にしたか Draft にしたかを書く。

**Why this priority**: 原則 VI（まとめレポートには「どの条件で自動マージした／しなかったか」を含める）と `04` 2章 実装メモ。Draft PR を受け取ったレビュアーが、何を見ればよいかがすぐ分かる。

**Independent Test**: 条件の組み合わせを変えたジョブで、PR の本文と Issue のコメントの文面を確かめる。秘密情報らしい値が伏せられていることを確かめる。

**Acceptance Scenarios**:

1. **Given** PR を作った、**When** PR の本文を読む、**Then** 6つの条件の表（条件・結果・値）と、「auto-merge を有効にした」か「Draft にした（理由）」が書かれている
2. **Given** PR を作った、**When** Issue を見る、**Then** PR へのリンク・自動マージか Draft か・ジョブの番号を含むコメントが1回だけ付いている
3. **Given** レポートの文面に秘密情報らしい文字列（判定の理由やテストのログの一部）が含まれる、**When** 投稿する、**Then** その値は伏せ字になっている
4. **Given** Issue へのコメントの投稿が失敗する、**When** 処理する、**Then** PR とジョブの状態はそのままにし（`ci_waiting`）、投稿の失敗を記録に残す
5. **Given** 出荷前に失敗したジョブ（秘密情報の検出・出荷できない変更・push の失敗）、**When** 報告する、**Then** 007 の失敗の報告を Issue に1回だけ書き、どの出荷前チェックで止まったかを含める

---

### User Story 4 - 自動マージの条件を設定で変える (Priority: P2)

運用者は、diff の大きさの上限・禁止パス・自動マージを許す作業の種類・自動マージを止めるラベルの名前を、設定ファイルで変えられる。設定が不正なら、ファクトリーは起動しない。

**Why this priority**: `04` 2章 実装メモ（自動マージの条件は `factory.toml` に置く）。記事の検証で、条件を変えて自動マージ率を比べる。既定の値で P1 は動くので P2 とする。

**Independent Test**: 設定の値を変えて、同じ diff の振り分けが変わることを確かめる。不正な値（負の上限、空のラベル名、知らない作業の種類）で起動しないことを確かめる。

**Acceptance Scenarios**:

1. **Given** diff の上限を 10 に下げた設定、**When** 20 行の diff を出荷する、**Then** Draft PR になる
2. **Given** 作業の種類の許可リストに `feature` を足した設定、**When** `feature` のジョブを出荷する、**Then** ほかの条件を満たせば auto-merge を有効にする
3. **Given** 不正な設定（上限が 0 以下、知らない作業の種類、空のラベル名）、**When** 起動する、**Then** 項目の名前を含むエラーで起動しない

---

### Edge Cases

- diff が空のまま判定に合格した → 005 は diff が空なら不合格にするので起きない。起きたら出荷せずに `failed`（理由: 内部エラー）
- 作業ブランチの名前がリモートにすでにある（前のジョブで残った、人間が作った） → 上書きの push をしない。`failed`（理由: 出荷の失敗）にする。名前はジョブの番号を含むので、通常は重ならない
- clone のあとに既定のブランチが進んだ → そのまま PR を作る。衝突があれば GitHub がマージを止め、auto-merge は待ったままになる（009 の CI 待ちの時間切れで扱う）
- Issue の `no-auto-merge` ラベルを、受付のあと・出荷の前に付けた → 出荷の時点のラベルを見る（PR を作る直前に Issue を取り直す）
- ラベルの取得が失敗する → 確かめられないので、満たさない（Draft）として扱う
- バイナリファイルの変更 → 行数には数えないが、ファイルの一覧には出す。禁止パスの判定は同じに行う
- ファイルの名前の変更・削除 → 変更前と変更後の両方のパスで禁止パスを判定する
- 作業ディレクトリに、実装役が作った git に無視されるファイルがある → commit に含めない（diff と同じ範囲だけを commit する）
- PR は作れたが auto-merge の有効化と Draft への変更の両方が失敗する → PR はそのまま残し、ジョブは `ci_waiting` に進め、レポートに「自動マージの状態を確定できなかった」と書く
- 秘密情報のスキャナーが、テスト用の偽の値（対象リポジトリの許可の設定にあるもの）を見つける → 対象リポジトリの許可の設定に従う。ファクトリーの側で許可を足さない
- 出荷の途中で停止の合図を受ける → push の前なら中断して `failed`（理由: 停止で中断）。push のあとなら PR の作成まで済ませてから止まる（停止の上限時間の中で）
- 出荷の途中でジョブ全体の時間の上限が来る → push の前なら `failed`（理由: 時間切れ）。push のあとは PR の作成までを続ける

## Requirements *(mandatory)*

### Functional Requirements

**出荷前チェック（層6）**

- **FR-001**: ファクトリーは、判定に合格したジョブの出荷の前に、出荷前チェックを行わなければならない。対象は、作業ディレクトリと既定のブランチの差分（判定に渡した diff と同じ範囲）とする
- **FR-002**: 自動マージの条件は次の6つとし、すべてを毎回評価して、それぞれの結果と値を記録しなければならない（最初に外れた条件で止めない）
  1. 検査役の判定が合格
  2. diff の行数（追加と削除の合計）が設定の上限以下
  3. 設定の禁止パス（glob）に当たるファイルの変更がない（名前の変更・削除では変更前と変更後の両方のパスで判定する）
  4. 秘密情報のスキャンで何も見つからない
  5. Issue に自動マージを止めるラベル（既定 `no-auto-merge`）が付いていない
  6. 計画の作業の種類が設定の許可リストに含まれる
- **FR-003**: 秘密情報のスキャンは、006 で入れた gitleaks（ローカル・CI・VPS で同じ版）で、出荷する変更を対象に行わなければならない。対象リポジトリに gitleaks の許可の設定があれば、それに従う。ただし使うのは変更の前（既定のブランチ）の設定だけとし、同じ変更で足した許可の設定・行ごとの許可のコメントは効かせてはならない。スキャンが実際に変更を走査したことを確かめられなければ、スキャンできなかったものとして扱う
- **FR-004**: 秘密情報が見つかったとき、またはスキャンを実行できなかったときは、push も PR の作成もしてはならない。ジョブを `failed`（理由: 秘密情報の検出）にし、報告には見つかったファイルと行と規則の名前だけを書き、値を書いてはならない
- **FR-005**: CI の定義（`.github/workflows` の下）を変更した diff は、push してはならない。ジョブを `failed`（理由: 出荷できない変更）にする
- **FR-006**: ラベルは、PR を作る直前に Issue を取り直して確かめなければならない。取得できないときは条件を満たさないものとして扱う

**commit・push・PR**

- **FR-007**: commit・push・PR の作成はホストで行わなければならない。作業場（コンテナ）に GitHub のトークンを渡してはならない（原則 IV）
- **FR-008**: commit は、判定に渡した diff と同じ範囲の変更だけを含む1つの commit とし、作成者はファクトリー（GitHub App のボット）にしなければならない。commit のメッセージには、計画の概要・Issue の参照・ジョブの番号を含める
- **FR-009**: commit と push で、作業ディレクトリの git フックと、作業ディレクトリの git の設定のうちコードを実行させうるもの（フックの場所・フィルター・認証の補助など）を使ってはならない
- **FR-010**: トークンは 007 と同じく環境変数で git に渡し、作業ディレクトリの git の設定・リモートの URL・コマンドラインの引数に書いてはならない
- **FR-011**: push は作業ブランチだけに行い、強制の push をしてはならない。既定のブランチに直接 push してはならない
- **FR-012**: PR は既定のブランチに向けて作り、本文で元の Issue を参照しなければならない。Issue を閉じるキーワードを使ってはならない
- **FR-013**: 6つの条件をすべて満たすときは、通常の PR として作り、auto-merge を有効にしなければならない。マージの判断は GitHub のブランチ保護（必須チェック）に任せ、ファクトリーが自分でマージしてはならない
- **FR-014**: 1つでも満たさないときは、Draft PR として作らなければならない
- **FR-015**: auto-merge の有効化が失敗したら、PR を Draft に変えて、GitHub の返した理由を記録とレポートに残さなければならない
- **FR-016**: push・PR の作成が失敗したら、`failed`（理由: 出荷の失敗）にして報告しなければならない。PR を作ったあとの失敗（auto-merge・Draft への変更・Issue へのコメント）では、ジョブを `failed` にしない

**状態と Worker**

- **FR-017**: PR を作ったら、状態を `judging` → `pr_opened` → `ci_waiting` と移し、PR の番号と自動マージの振り分け（auto-merge・Draft とその理由）をジョブに記録しなければならない
- **FR-018**: `ci_waiting` のジョブは Worker を占有してはならない。Worker は PR を作ったら次のジョブの処理に進む
- **FR-019**: 起動時の掃除（007）は、`ci_waiting` のジョブを `failed` にしてはならない（CI の結果は 009 で受ける）
- **FR-020**: 007 の「判定に合格したら `failed`（出荷の工程が未実装）」の扱いを、この出荷の工程に置き換えなければならない
- **FR-021**: 出荷の工程も、ジョブ全体の時間の上限と停止の合図に従わなければならない。push の前なら中断して `failed` にし、push のあとは PR の作成までを済ませる
- **FR-022**: 出荷の工程は LLM を呼んではならない（消費するリクエストは 0）

**まとめレポート**

- **FR-023**: PR の本文に、まとめレポート（計画の概要、受け入れ条件、作業の種類、テストの結果、判定の結果と理由、やり直しの回数、消費したリクエスト数、変更したファイルと行数、6つの条件の表、自動マージか Draft かとその理由、ジョブの番号）を書かなければならない
- **FR-024**: PR を作ったら、Issue に PR へのリンク・自動マージか Draft か（Draft なら満たさなかった条件）・ジョブの番号を含むコメントを1回だけ投稿しなければならない
- **FR-025**: レポートは、秘密情報を伏せてから投稿しなければならない（001 のマスクと同じ判定）。長い文（判定の理由・テストのログ）は上限で切り詰める
- **FR-026**: 出荷前に失敗したときは、007 の失敗の報告を Issue に1回だけ投稿し、止まった出荷前チェックの名前を含めなければならない

**GitHub 層と設定**

- **FR-027**: PR の作成・Draft への変更・auto-merge の有効化・ラベルの取得・push のための認証は、007 の GitHub 層にまとめなければならない（原則 VII）
- **FR-028**: diff の行数の上限・禁止パス・自動マージを許す作業の種類・自動マージを止めるラベルの名前は、設定で変えられなければならない。不正な値ではファクトリーは起動しない

**テスト**

- **FR-029**: 出荷前チェック（6条件の各組み合わせ、秘密情報、CI の定義）、commit・push（ローカルの bare リポジトリ）、PR の作成と振り分け（偽の GitHub）、レポートの文面は、GitHub と LLM を使わない自動テストで確かめられなければならない

### Key Entities *(include if feature involves data)*

- **出荷前チェックの結果（Ship check result）**: 6つの条件それぞれの名前・満たしたか・値（diff の行数と上限、当たった禁止パス、見つかった秘密情報のファイルと行と規則、ラベル、作業の種類）と、push してよいか（秘密情報・CI の定義で止めるか）
- **出荷の振り分け（Merge decision）**: auto-merge・Draft のどちらか、満たさなかった条件の一覧、auto-merge の有効化に失敗したときの GitHub の理由
- **ジョブ（Job）**: 007 の `jobs` に、PR の番号（と URL）、出荷の振り分けを足す
- **ジョブの記録（Job event）**: 出荷前チェックの結果、PR の作成、auto-merge の有効化・Draft への変更、レポートの投稿とその失敗
- **自動マージの設定**: diff の行数の上限、禁止パス、許可する作業の種類、自動マージを止めるラベルの名前（`factory.toml` の `[auto_merge]`）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 6つの条件のどれか1つを外した確認セットで、auto-merge が有効になる件数が 0。すべてを満たす確認セットでは、すべて auto-merge が有効になる
- **SC-002**: 秘密情報を含む変更・CI の定義を変える変更の確認セットで、リモートに push される件数が 0
- **SC-003**: 出荷した PR の 100% で、まとめレポートに6つの条件の結果と振り分けの理由が書かれている
- **SC-004**: PR・Issue のコメント・記録・ログのどこにも、GitHub のトークンと、見つかった秘密情報の値が現れない
- **SC-005**: 判定に合格してから PR ができるまでが、通常の大きさの変更（上限以内の diff）で 1 分以内
- **SC-006**: 出荷の工程で消費する LLM のリクエストが 0
- **SC-007**: PR を作ったジョブの 100% が `ci_waiting` で止まり、再起動のあとも `ci_waiting` のまま残る
- **SC-008**: 本物の GitHub での確認（テスト用のリポジトリ）で、条件を満たすジョブが auto-merge 予約付きの PR に、満たさないジョブが Draft PR になる

## Assumptions

- 判定に合格したジョブの入力は、007 の Worker が持つ作業ディレクトリ（作業ブランチ）と 005 の工程の結果（計画、判定の結果、テストの結果、diff とその統計、やり直しの回数、消費したリクエスト数）とする。出荷の工程は Worker の中で 005 の入口のあとに行い、作業場（コンテナ）は使わない
- CI の結果を受けて先へ進めること（`check_suite`）、CI 待ちの時間切れ、CI 失敗後のやり直しは 009 で作る。それまで `ci_waiting` のジョブは、CI が通れば GitHub の auto-merge でマージされ、ファクトリーの状態は `ci_waiting` のまま残る
- まとめレポートへの CI・マージ・デプロイの結果の書き足し、ステージングの URL は 009・010 で作る
- 対象リポジトリでは、運用者が auto-merge を有効にし、既定のブランチのブランチ保護で CI を必須チェックにしておく（`03` 5章 対象リポジトリの設定）。テスト用のリポジトリ（`Coxless/factory-sandbox`）の CI とブランチ保護は、本物での確認の前に用意する
- 自動マージの設定は `factory.toml` の `[auto_merge]`（001 で `max_diff_lines`・`forbidden_paths`・`allowed_work_types` は既にある）に、ラベルの名前を足す
- 禁止パス（`[auto_merge].forbidden_paths`）は、ツールの書き込み拒否（`[tools].deny_write_paths`）とは別の一覧のままにする。実装役は `bash` で禁止パスを書き換えられるので（`04` 2章 実装メモ）、出荷前チェックが diff で必ず検出する
- gitleaks は 006 で開発環境・CI・VPS に入っている（版とチェックサムは `scripts/install-gitleaks.sh`）
- GitHub App の権限は 007 のまま（Contents・Pull requests の読み書き）で足りる。auto-merge の有効化には、App が push できる権限があればよい
- テストでは GitHub の API を呼ばない。本物の GitHub での確認は、テスト用のリポジトリで手で行う。AI解禁の前は、判定まで進められないので、偽の 005 の入口に差し替えた確認用の起動で出荷の工程だけを試す方法を、計画で決める
