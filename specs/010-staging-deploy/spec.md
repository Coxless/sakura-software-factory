## Clarifications

### Session 2026-11-14

007〜009 と同じく、人間の確認が要るものは、いったん推奨する内容で決めた（PR で見直せる）。

- Q: どのリポジトリのどのブランチへの push をデプロイするか？ → A: 設定で指定した1つのステージング対象のリポジトリの、既定のブランチ（main）への push だけ（推奨）。ほかのリポジトリ・ブランチ・タグ・ブランチの削除の知らせは何もせずに受け取ったとだけ返す。ステージング対象のリポジトリを設定しなければ、デプロイの機能は止まっている（push はすべて無視）
- Q: push が続けて届いたら、どう処理するか？ → A: 届いた順に1件ずつデプロイする（推奨）。途中の push を飛ばさない。どの commit がいつ・どのイメージで出たかを1件ずつ記録に残し、記事と監査に使う。同じ commit の知らせが2回届いても1回だけデプロイする
- Q: デプロイとジョブはどう結び付けるか？ → A: push の先頭の commit が、ファクトリーのジョブの PR をマージした commit なら、そのジョブに結び付ける（推奨）。人間が直接 push した・人間の PR のマージなど、結び付かない push もデプロイする（ジョブなしの記録）。CI 待ちの見回りより先に push が届いたら、デプロイの工程でマージを確かめて `ci_waiting` → `merged` に進めてから始める
- Q: ヘルスチェックに失敗したら、何をするか？ → A: 直前に成功したデプロイのイメージに戻し、戻した後のヘルスチェックも確かめる（推奨）。そのうえで、push の変更を打ち消す revert PR を作る。revert PR は auto-merge を有効にせず、Draft でもない通常の PR にして人間がマージする（検査役の判定を通っていない変更なので、自動マージの6条件を満たさない）。ジョブは `rolled_back` にし、Issue に1回報告する。直前に成功したデプロイがなければ（最初のデプロイ）、ステージングを止めて同じく報告する
- Q: イメージのビルドに失敗したら、何をするか？ → A: ステージングは入れ替えないので、そのまま前の版が動き続ける（推奨）。デプロイを失敗として記録し、ジョブは `failed`（理由: デプロイの失敗）にして Issue に1回報告する。revert PR は作らない（ネットワークなど作業場の外の原因もありうるので、戻すかは人間が決める）
- Q: デプロイの途中でファクトリーが止まったら？ → A: 起動時に、途中だったデプロイを失敗（中断）として記録し、ジョブを `failed` にして報告する（推奨。007 の起動時の掃除と同じ考え方）。ステージングはそのとき動いていた版のまま残る。まだ始めていないデプロイは残して順に処理する。停止中に届かなかった push を拾うため、起動時に既定のブランチの先頭を取り直し、最後に記録したデプロイの commit と違えばデプロイを積む
- Q: デプロイが成功したら、何を知らせるか？ → A: PR の本文のデプロイの欄に、結果・commit・イメージ・ステージングの URL を書き足し、ジョブを `deployed` にする（推奨）。Issue にはコメントしない（PR へのリンクは 008 で投稿済み。Issue を閉じるかは、人間がステージングで確かめて決める）
- Q: デモ用の対象リポジトリはどこまで用意するか？ → A: `Coxless/factory-sandbox` に、`/healthz` を返す小さな HTTP サーバー、ステージング用の Dockerfile、`pnpm run check` を回す CI、main のブランチ保護（CI を必須チェック・auto-merge を有効）、AGENTS.md を足す（推奨）。ステージングは VPS解禁（12-03）まで、Workshop の中の Docker で compose を動かして確かめる

## User Scenarios & Testing *(mandatory)*

この機能の利用者は3種類いる。

- **依頼者**（対象リポジトリに書き込み権限のある開発者）: `@agent` で依頼した変更が、CI を通ってマージされたあと、ステージングで動いているのを確かめたい。戻されたときは理由を知りたい
- **レビュアー**（本番に出すかを決める人間）: PR の本文で、どの commit がどのイメージでステージングに出たか、戻されたかを読む。revert PR をマージするか決める
- **運用者**: デプロイの成功率・ロールバックの回数を記録から集計し、記事の検証に使う。ステージングの設定（対象のリポジトリ・ヘルスチェック・URL）を設定ファイルで変える

### User Story 1 - main への反映をステージングに自動で出す (Priority: P1)

ファクトリーは、ステージング対象のリポジトリの main に push があった知らせを受けたら、その commit からデモアプリのイメージを作り、ステージングを新しいイメージに入れ替えて、ヘルスチェックが通ることを確かめる。結果はデプロイの記録に残し、ファクトリーのジョブの PR のマージなら、ジョブを `merged` → `deploying` → `deployed` に進め、PR の本文にデプロイの結果とステージングの URL を書き足す。

**Why this priority**: レベルB（`01` 3章）の「CI 通過後に自動マージ → ステージングへ自動デプロイ」の最後の一歩。009 まででジョブは `merged` で止まっていた。

**Independent Test**: 偽の GitHub と記録した push の知らせ、ローカルの bare リポジトリ、偽のデプロイの実行器（ビルド・入れ替え・ヘルスチェックの結果を決められる）で、記録・状態の移り変わり・PR の本文を確かめる。本物の Docker を使う確認では、小さなデモアプリを実際にビルドして compose で入れ替え、ヘルスチェックの URL に届くことを確かめる。

**Acceptance Scenarios**:

1. **Given** `merged` のジョブと、その PR をマージした commit の push の知らせ、**When** 受ける、**Then** デプロイが記録され、ジョブが `merged` → `deploying` → `deployed` と移り、PR の本文のデプロイの欄に結果・commit・イメージ・ステージングの URL が書き足される
2. **Given** 人間が直接 main に push した、**When** 知らせを受ける、**Then** ジョブに結び付かないデプロイとして記録され、同じようにビルド・入れ替え・ヘルスチェックが行われる
3. **Given** ステージング対象ではないリポジトリ・main 以外のブランチ・タグ・ブランチの削除の知らせ、**When** 受ける、**Then** 何もせずに受け取ったとだけ返す
4. **Given** 同じ commit の push の知らせが2回届く、**When** 受ける、**Then** デプロイは1回だけ行われる
5. **Given** デプロイの途中に2件目の push が届く、**When** 受ける、**Then** 2件目は積まれ、1件目が終わってから処理される
6. **Given** Worker が別のジョブの実装工程を処理している、**When** push の知らせを受ける、**Then** デプロイは Worker を待たずに始まる
7. **Given** PR のマージの知らせより先に push の知らせが届いた（ジョブはまだ `ci_waiting`）、**When** デプロイを始める、**Then** PR がマージされたことを確かめて `ci_waiting` → `merged` に進めてから、`deploying` に移す
8. **Given** 受付が push の知らせを受けた、**When** 応答する、**Then** ビルドを待たずに短い時間で応答する

---

### User Story 2 - ヘルスチェックに失敗したら直前の版に戻し、revert PR を作る (Priority: P1)

ファクトリーは、新しいイメージに入れ替えたあとヘルスチェックが決まった時間内に通らなければ、直前に成功したデプロイのイメージに戻し、戻した版のヘルスチェックを確かめる。そのうえで、push の変更を打ち消す revert PR を作り、ジョブを `rolled_back` にして、Issue に1回報告する。

**Why this priority**: `04` 層9・原則 VI の MUST。自動マージした変更がステージングを壊したまま残らないようにする、レベルBの安全弁。

**Independent Test**: 偽の実行器でヘルスチェックを失敗させ、戻し先のイメージ・戻したあとの確認・revert PR の中身（ローカルの bare リポジトリへの push と偽の GitHub の PR）・記録・状態・報告を確かめる。本物の Docker を使う確認では、`/healthz` が 500 を返すイメージをデプロイして、直前のイメージに戻ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 直前に成功したデプロイがあり、新しいイメージのヘルスチェックが時間内に通らない、**When** デプロイする、**Then** 直前のイメージに戻し、戻したあとのヘルスチェックが通り、記録に「ロールバックした・戻し先のイメージ」が残る
2. **Given** ロールバックした、**When** 続ける、**Then** push の変更を打ち消す commit を新しいブランチに積んで push し、revert PR を作る。revert PR は auto-merge を有効にしない通常の PR で、本文に元の PR・失敗したヘルスチェックの結果・戻し先を書く
3. **Given** ロールバックしたデプロイがジョブに結び付いている、**When** 終わる、**Then** ジョブが `deploying` → `rolled_back` に移り、PR の本文のデプロイの欄にロールバックと revert PR へのリンクが書き足され、Issue に1回報告される
4. **Given** 直前に成功したデプロイがない（最初のデプロイ）、**When** ヘルスチェックに失敗する、**Then** ステージングを止め、記録に「戻し先なし」を残し、revert PR を作ってジョブを `rolled_back` にする
5. **Given** 戻した版のヘルスチェックも通らない、**When** 確かめる、**Then** 記録とレポートに「戻した版も不健康」と残し、運用者が気づけるようにエラーのログを出す（ジョブは `rolled_back`）
6. **Given** revert の commit を作れない（打ち消しが衝突する・push の範囲が分からない）、**When** revert PR を作ろうとする、**Then** revert PR を作らずに、作れなかった理由を記録とレポートに残す（ロールバックはそのまま）
7. **Given** revert PR を人間がマージした、**When** その push の知らせを受ける、**Then** 通常のデプロイとして処理する（ジョブなし）

### User Story 3 - ビルドの失敗・中断・取りこぼしでも状態を残さない (Priority: P1)

ファクトリーは、イメージのビルドに失敗したら、ステージングを入れ替えずに、デプロイを失敗として記録し、ジョブを `failed` にして Issue に報告する。デプロイの途中で止まったら、起動時に途中のデプロイを失敗（中断）として片付ける。停止中に届かなかった push は、起動時に main の先頭を取り直して拾う。

**Why this priority**: 原則 II（すべての工程に上限・失敗時も報告）。デプロイの記録とジョブが「途中」のまま永久に残らないようにする。

**Independent Test**: 偽の実行器でビルドを失敗・時間切れにする。途中のデプロイの記録を作ってから起動し、掃除と報告を確かめる。偽の GitHub の main の先頭を最後のデプロイと違う commit にして起動し、デプロイが積まれることを確かめる。

**Acceptance Scenarios**:

1. **Given** イメージのビルドが失敗する（Dockerfile の誤り・時間切れ）、**When** デプロイする、**Then** ステージングは入れ替えず、デプロイは失敗（ビルド）として記録され、ジョブが `failed`（理由: デプロイの失敗）になり、Issue に1回報告される。revert PR は作らない
2. **Given** 対象の commit を取得できない（ブランチが消えた・GitHub に届かない）、**When** デプロイする、**Then** デプロイは失敗として記録され、ジョブは `failed` になる
3. **Given** デプロイの途中でファクトリーが止まった、**When** 起動する、**Then** 途中のデプロイは失敗（中断）として記録され、ジョブは `failed` になって Issue に報告される。積まれていたまだ始めていないデプロイは、順に処理される
4. **Given** 停止中に main に push があった（知らせを受けていない）、**When** 起動する、**Then** main の先頭の commit が最後に記録したデプロイの commit と違えば、デプロイを積む
5. **Given** ステージングの設定がない、**When** 起動する・push を受ける、**Then** デプロイの機能は動かず、push は無視される（起動時の取り直しもしない）

### User Story 4 - ステージングの動かし方を設定で変える (Priority: P2)

運用者は、ステージング対象のリポジトリ、ヘルスチェック（URL・時間の上限・続けて通る回数）、ビルドの時間の上限、残しておくイメージの数、レポートに書くステージングの URL を、設定ファイルで変えられる。不正な値ではファクトリーは起動しない。

**Why this priority**: VPS（公開ドメイン）とローカルの予行演習で、同じコードを設定だけで切り替える。既定の値で P1 は動くので P2。

**Independent Test**: 設定の値を変えて、ヘルスチェックの扱い（待つ時間・回数）が変わることを確かめる。不正な値で起動しないことを確かめる。

**Acceptance Scenarios**:

1. **Given** ヘルスチェックの時間の上限を短くした設定、**When** 起動の遅いイメージをデプロイする、**Then** 上限で打ち切ってロールバックする
2. **Given** 残しておくイメージの数を 3 にした設定、**When** デプロイが成功する、**Then** 直近 3 個より古いステージングのイメージが消える（動いているイメージと戻し先は消さない）
3. **Given** 不正な設定（ヘルスチェックのパスが `/` で始まらない・時間の上限が 0・リポジトリの名前の形が違う）、**When** 起動する、**Then** 項目の名前を含むエラーで起動しない

### User Story 5 - デモ用の対象リポジトリを用意する (Priority: P2)

運用者は、デモ用の対象リポジトリ（`Coxless/factory-sandbox`）を、ファクトリーが依頼を受けてステージングまで出せる形に整える。`/healthz` を返す小さな HTTP サーバー、ステージング用の Dockerfile、`pnpm run check` を回す CI、main のブランチ保護（CI を必須チェック・auto-merge を有効）、AGENTS.md を持つ。

**Why this priority**: 24時間稼働のデモ（M4）と記事の実測の土台。ファクトリーのコードの確認は偽物と Workshop の Docker でできるので P2。

**Independent Test**: デモ用のリポジトリを clone して、作業場のイメージで `pnpm run check` が通ること、Dockerfile からイメージを作ってコンテナの `/healthz` が `200` を返すことを確かめる。GitHub で main のブランチ保護と auto-merge の設定を確かめる。

**Acceptance Scenarios**:

1. **Given** デモ用のリポジトリ、**When** 作業場のイメージで `pnpm install --frozen-lockfile && pnpm run check` を回す、**Then** ネットワークなしでもテストが通る
2. **Given** Dockerfile からビルドしたイメージ、**When** ステージングの compose で起動する、**Then** `/healthz` が `200` を返す
3. **Given** main に直接 push しようとする PR 以外の変更、**When** ブランチ保護を確かめる、**Then** CI が必須チェックで、auto-merge が使える

### Edge Cases

- push の知らせの commit が、すでに成功・失敗で記録したデプロイの commit と同じ → 積まない（同じ commit を2回デプロイしない）
- ステージングの今の版と同じ commit が強制の push で戻ってきた（人間の操作） → 記録にない新しい知らせなら1件のデプロイとして扱う。ただし同じ commit のデプロイの記録があれば積まない
- 強制の push・ブランチの作り直しで、push の前の commit が push の後の commit の祖先でない → デプロイはする。ヘルスチェックに失敗したら、revert PR は作らず、理由（範囲が分からない）を記録とレポートに残す
- push に複数の commit が含まれる（人間がまとめて push した） → 先頭の commit をデプロイする。revert PR は push の範囲全体を1つの commit で打ち消す
- デプロイを待っている間に、同じジョブの PR がまだ `ci_waiting` のまま（マージの知らせを取りこぼした） → デプロイの工程で PR の状態を取り直し、マージ済みなら `merged` に進めてから始める
- push の先頭の commit が、ファクトリーの PR のマージだが、ジョブがすでに終わりの状態（`failed` など） → ジョブの状態は変えず、デプロイはジョブなしと同じ扱いで記録だけ結び付ける
- 直前に成功したデプロイのイメージが手元から消えていた → 戻し先なしと同じ扱い（ステージングを止める）
- ヘルスチェックの URL が一度だけ `200` を返し、すぐに落ちる → 決まった回数続けて通らなければ失敗として扱う
- デモアプリが factory のネットワーク・ポートに触れようとする → 別のネットワーク・リソースの制限・ループバックへの公開で隔離する（`04` 層9）
- ビルドにデモアプリのコードが使われる → ビルドにファクトリーの秘密情報（GitHub のトークン・API キー）を渡さない。clone はホストで行い、トークンを含まないディレクトリだけをビルドに渡す
- イメージが増え続ける → 成功したデプロイのあとに、残しておく数より古いステージングのイメージを消す。動いているイメージと戻し先は消さない
- PR の本文の書き足し・Issue の報告・revert PR の作成で GitHub に届かない → デプロイの結果とロールバックはそのまま記録に残し、書き足せなかったことを記録に残す（デプロイをやり直さない）
- 起動時の取り直しで GitHub に届かない → 起動は止めず、ログに残す
- デプロイ中に停止の合図を受けた → 実行中の外部コマンド（ビルド・入れ替え）を打ち切り、デプロイを失敗（中断）にして止まる。ステージングはそのとき動いていた版のまま残る

## Requirements *(mandatory)*

### Functional Requirements

**push の受信**

- **FR-001**: ファクトリーは、push の知らせを 007〜009 と同じ受付（署名の検証のあと）で受け、短い時間で応答しなければならない。ビルドなど重い処理は応答のあとに回す
- **FR-002**: デプロイするのは、設定で指定したステージング対象のリポジトリの既定のブランチへの push だけとし、それ以外（ほかのリポジトリ・ブランチ・タグ・ブランチの削除・ステージングの設定がない）は状態を変えずに無視しなければならない
- **FR-003**: 受け付けた push は、デプロイの記録として「待ち」で積まなければならない。同じリポジトリの同じ commit の記録がすでにあれば積まない

**デプロイの実行**

- **FR-004**: デプロイは、LLM を使う工程（Worker）・CI 待ちの見回りとは別に、1件ずつ、積んだ順に行わなければならない。LLM は使わない
- **FR-005**: デプロイを始めるときに、push の先頭の commit を、ファクトリーのジョブの PR をマージした commit かどうかで、ジョブに結び付けなければならない。ジョブが `ci_waiting` なら、PR がマージ済みであることを確かめて `merged` に進めてから（009 と同じ記録・PR の本文の書き足しを行う）、`merged` → `deploying` に移す
- **FR-006**: 対象の commit をホストで取得し（トークンはホストの git にだけ渡す）、そのディレクトリから、対象のリポジトリの Dockerfile でイメージを作らなければならない。イメージの名前には commit を含める。ビルドには秘密情報を渡さず、時間の上限を設ける
- **FR-007**: ビルドに成功したら、ステージングの compose を新しいイメージで入れ替え、ヘルスチェックを行わなければならない。ヘルスチェックは、ループバックに公開したステージングの決まったパスに、時間の上限内で、決まった回数続けて正常（`200`）が返ることで通過とする
- **FR-008**: ヘルスチェックが通ったら、デプロイを成功として記録し、ジョブを `deploying` → `deployed` に移し、PR の本文のデプロイの欄に、結果・commit・イメージ・ステージングの URL（設定があれば）を書き足さなければならない
- **FR-009**: 成功したデプロイのあと、残しておく数より古いステージングのイメージを消さなければならない。動いているイメージと、直前に成功したデプロイのイメージは消さない

**ロールバックと revert PR**

- **FR-010**: ヘルスチェックが通らなければ、直前に成功したデプロイのイメージに入れ替え、戻した版のヘルスチェックを行わなければならない。直前に成功したデプロイがない・そのイメージがなければ、ステージングを止める
- **FR-011**: ロールバックしたら、push の範囲（push の前の commit から先頭の commit まで）の変更を打ち消す1つの commit を、既定のブランチから作った新しいブランチに積んで push し（強制しない）、revert PR を作らなければならない。revert PR は auto-merge を有効にせず、Draft でもない通常の PR とし、本文に元の commit・元の PR（あれば）・ヘルスチェックの結果・戻し先を書く
- **FR-012**: 打ち消しが衝突する・push の範囲が分からない（前の commit が祖先でない・ブランチの作成）ときは、revert PR を作らずに理由を記録とレポートに残さなければならない。ロールバックは取り消さない
- **FR-013**: ロールバックしたデプロイを失敗（ヘルスチェック）として記録し、ロールバックしたこと・戻し先・戻した版のヘルスチェックの結果・revert PR の番号を残さなければならない。ジョブがあれば `deploying` → `rolled_back` に移し、PR の本文のデプロイの欄に書き足し、Issue に1回報告する

**失敗・中断・取りこぼし**

- **FR-014**: 取得・ビルドに失敗したら、ステージングを入れ替えずに、デプロイを失敗として記録しなければならない。ジョブがあれば `failed`（理由: デプロイの失敗）にし、Issue に1回報告する。revert PR は作らない
- **FR-015**: 起動時に、途中のデプロイを失敗（中断）として記録し、結び付いた `deploying` のジョブを `failed`（理由: 再起動・停止で中断）にして報告しなければならない。待ちのデプロイは残して順に処理する
- **FR-016**: 起動時に、ステージング対象のリポジトリの既定のブランチの先頭を取り直し、デプロイの記録にない commit なら、デプロイを積まなければならない。GitHub に届かなくても起動は止めない
- **FR-017**: 停止の合図を受けたら、実行中のビルド・入れ替えを打ち切り、デプロイを失敗（中断）として記録してから止まらなければならない
- **FR-018**: PR の本文の書き足し・Issue の報告・revert PR の作成に失敗しても、デプロイの結果とロールバックの記録は残し、失敗したことを記録しなければならない

**ステージングの隔離**

- **FR-019**: ステージングのデモアプリは、ファクトリーとは別の Docker ネットワークで、メモリ・CPU・プロセス数の制限をかけて動かし、ポートはループバックにだけ公開しなければならない（`04` 層9）
- **FR-020**: ステージングの compose の定義は、ファクトリーのリポジトリに置き（対象のリポジトリのファイルから読まない）、イメージの名前だけを差し替えて入れ替えなければならない

**記録とレポート**

- **FR-021**: デプロイ1件ごとに、リポジトリ・commit・push の前の commit・イメージ・結び付いたジョブ・状態（待ち・実行中・成功・失敗）・失敗の段階（取得・ビルド・ヘルスチェック・中断）・ロールバックの有無と戻し先・revert PR の番号・開始と終了の時刻を記録しなければならない（デプロイの成功率・ロールバックの回数を SQL で集計できること）
- **FR-022**: ジョブに結び付いたデプロイの開始・結果・ロールバック・revert PR は、ジョブの記録にも残さなければならない
- **FR-023**: PR の本文のデプロイの欄は、008・009 のまとめレポートのほかの部分（CI の欄を含む）を消さずに書き足さなければならない

**GitHub 層と設定**

- **FR-024**: push の知らせの読み取り、マージした commit から PR の特定、既定のブランチの先頭の取得、revert PR の作成は、GitHub 層にまとめなければならない（原則 VII）
- **FR-025**: ステージング対象のリポジトリ・ヘルスチェックの URL と時間の上限と続けて通る回数と間隔・ビルドの時間の上限・残しておくイメージの数・ステージングの URL・イメージの名前・待ち受けのポートは、設定で変えられなければならない（compose の定義はファクトリーのリポジトリに固定する）。不正な値ではファクトリーは起動しない

**デモ用の対象リポジトリ**

- **FR-026**: デモ用の対象リポジトリに、`/healthz` を返す HTTP サーバー、ステージング用の Dockerfile、`pnpm run check` を回す CI、main のブランチ保護（CI を必須チェック）と auto-merge の許可、AGENTS.md を用意しなければならない

**テスト**

- **FR-027**: 受付・積み方・結び付け・成功・ロールバック・revert PR（ローカルの bare リポジトリへの push）・ビルドの失敗・起動時の掃除と取り直しは、GitHub と Docker を使わない自動テストで確かめられなければならない。ビルド・入れ替え・ヘルスチェック・ロールバックは、Docker のある環境で、本物の Docker を使う自動テストでも確かめる

### Key Entities *(include if feature involves data)*

- **デプロイ（Deployment）**: 001 の `deployments`。リポジトリ・commit・push の前の commit・イメージ・結び付いたジョブ・状態（待ち・実行中・成功・失敗）・失敗の段階・ロールバックの有無と戻し先・revert PR の番号・開始と終了の時刻
- **ジョブ（Job）**: 007 の `jobs`。`merged` → `deploying` → `deployed` / `rolled_back`、またはデプロイの失敗で `failed`
- **push の知らせ（Push event）**: リポジトリ・ブランチ（ref）・push の前と後の commit・削除かどうか
- **ジョブの記録（Job event）**: デプロイの開始・結果・ロールバック・revert PR・書き足しの失敗
- **設定**: ステージング対象のリポジトリ、ヘルスチェック、ビルドの時間の上限、残しておくイメージの数、ステージングの URL、イメージの名前、待ち受けのポート

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: マージされたファクトリーの PR の確認セットで、ヘルスチェックが通る変更の 100% が `deployed` になり、PR の本文にステージングの URL が書かれる
- **SC-002**: ヘルスチェックが通らない変更の確認セットで、100% が直前の版に戻り、戻したあとのヘルスチェックが通り、revert PR が1件だけ作られる
- **SC-003**: push の知らせを受けてからデプロイの開始（記録が「実行中」になる）まで、Worker が別のジョブを処理していても 1 分以内
- **SC-004**: 同じ push の知らせを2回送った確認セットで、デプロイが重複する件数が 0
- **SC-005**: デプロイの記録・ジョブが、ビルドの時間の上限 ＋ ヘルスチェックの時間の上限 ＋ 余裕を過ぎても「実行中」・`deploying` のまま残る件数が 0（再起動を挟んでも）
- **SC-006**: 記録から、デプロイの成功率・ロールバックの回数・ジョブごとのデプロイの結果を SQL だけで集計できる
- **SC-007**: ビルドとステージングのコンテナに、ファクトリーの秘密情報（GitHub のトークン・API キー）が渡る経路が 0
- **SC-008**: Workshop の Docker での確認で、デモアプリの正常な版がデプロイされ、`/healthz` が 500 を返す版で直前の版に戻る

## Assumptions

- 009 までで、PR がマージされたジョブは `merged` に進む。010 は `merged` → `deploying` → `deployed` / `rolled_back` を作る。遷移は 007 の状態の表に既にある
- ステージング対象のリポジトリは1つ（デモ用の `Coxless/factory-sandbox`）。複数のリポジトリのステージングは扱わない
- ステージングのデモアプリは、対象のリポジトリの直下の Dockerfile でビルドでき、コンテナの中で決まったポートで待ち受け、`/healthz` で `200` を返す。この約束はデモ用のリポジトリの AGENTS.md に書く
- イメージのビルドはホストの Docker で行い、依存の取得のためにネットワークを使う。ビルドの対象はブランチ保護の必須チェック（CI）を通ってマージされたコードで、ビルドにはファクトリーの秘密情報を渡さない
- GitHub App は `03` 5章のとおり `push` の知らせを購読し、Contents の書き込み（revert のブランチの push）と Pull requests の書き込み（revert PR）を持つ。テスト用のリポジトリの App の設定は、本物での確認の前に運用者が足す
- VPS解禁（12-03）までは、ステージングは Workshop の中の Docker で compose を動かして確かめる。Caddy からの公開（`STAGING_DOMAIN`）は 006 で用意済み
- `/status` でのデプロイ成功率の表示は 011 で作る
- テストでは GitHub の API を呼ばない。本物の GitHub での確認（デモ用のリポジトリへの push → デプロイ）は、Workshop で App の Webhook を転送して行う
