## Clarifications

### Session 2026-11-11

ユーザーの指示（人間の確認が要るものは、いったん推奨する内容で進める）により、以下は推奨の回答で決めた。

- Q: ファクトリーのユーザーは、作業場（003）のコンテナを操作するために Docker へどう接続するか？ → A: 専用ユーザーを `docker` グループに入れる（推奨）。rootless Docker は作業場の隔離設定（`--read-only`・`--pids-limit` など）とステージングの compose の動作確認をやり直すことになり、締切に対して重い。`docker` グループは実質的に管理者権限に近いので、計画の Complexity Tracking に理由を書き、systemd の保護設定と SSH の締め付けで外側を固める
- Q: VPS へファクトリーのコードをどう届けるか？ → A: VPS 上で GitHub から `git clone` し、更新はコミットかタグを指定してチェックアウトする（推奨）。開発機から rsync すると、VPS 上の版がリポジトリのどの版か追えなくなる。イメージにして配る方式は、作業場の Docker を操作する都合でコンテナの中から Docker を使うことになり複雑になる
- Q: 生存確認の URL は Caddy を通して外に公開するか？ → A: 公開する（推奨）。返すのは状態だけで内部の情報を含めないので害がなく、外部の監視や記事の読者が稼働を確かめられる。ファクトリーのドメインで公開するのは `/healthz` と後続の `/webhook`・`/status` だけとし、ほかのパスは Caddy で「見つからない」を返す
- Q: CI の秘密情報スキャンは、作業ツリーだけか、git の履歴全体か？ → A: 履歴全体をスキャンする（推奨）。リポジトリは小さく数秒で終わり、一度コミットして消した秘密情報も見つけられる。ローカルの同じコマンドも履歴全体を対象にする
- Q: 予行演習の Ubuntu 環境で、作業場のイメージのビルドなど Docker を要する手順をどう流すか？ → A: 予行演習のコンテナを特権付きで動かし、その中に配備スクリプトで Docker を入れて使う（推奨）。ホストの Docker のソケットを渡すと、配備スクリプトの「Docker を入れる」手順を確かめられない。特権付きは開発機のローカルでだけ使い、CI では予行演習を動かさない

## User Scenarios & Testing *(mandatory)*

この機能の利用者は2種類いる。

- **運用者（開発者本人）**: VPS解禁の日（2026-12-03）に、手順書を上から流してファクトリーを VPS に配備する。以後、更新とログの確認を行う
- **外部の監視・Caddy・後続の機能**: ファクトリーが生きているかを決まった URL で確かめる。008 の出荷前チェックは秘密情報スキャンのツールが VPS にある前提で作る

### User Story 1 - 生存確認の URL を持つ常駐プロセスとして起動する (Priority: P1)

ファクトリーは、起動するとローカルのポートで HTTP を待ち受け、生存確認の URL に応答し続ける常駐プロセスになる。生存確認は、データベースを読めるかまで確かめ、読めなければ「不健康」を返す。停止の合図を受けたら、待ち受けを閉じ、データベースを閉じてから終わる。

**Why this priority**: 今の起動処理はマイグレーションのあと終了してしまい、常駐できない。Caddy・systemd・ステージングのヘルスチェック（010）・`/webhook`（007）・`/status`（011）はすべて、この HTTP の土台の上に乗る。

**Independent Test**: 開発機で起動し、生存確認の URL が正常を返すこと、データベースを読めなくすると不健康を返すこと、停止の合図で数秒以内に終わることを確かめる。LLM は使わない。

**Acceptance Scenarios**:

1. **Given** 正しい設定とデータベース、**When** ファクトリーを起動する、**Then** マイグレーションのあと設定のポートで待ち受け、生存確認の URL が「正常」を返す
2. **Given** 起動中のファクトリー、**When** データベースを読めなくなる、**Then** 生存確認の URL が「不健康」を返す（例外でプロセスは落ちない）
3. **Given** 起動中のファクトリー、**When** 停止の合図を受ける、**Then** 新しい接続を受け付けなくなり、データベースを閉じて正常に終わる
4. **Given** 設定のポートが使用中、**When** 起動する、**Then** 原因を示して異常終了する
5. **Given** 起動中のファクトリー、**When** 存在しないパスにアクセスする、**Then** 「見つからない」を返し、内部の情報を漏らさない
6. **Given** 開発用の LLM 提供元の設定、**When** 常駐プロセスとして起動しようとする、**Then** これまでどおり起動を拒否する（原則 I）

### User Story 2 - 手順書を上から流して VPS に配備する (Priority: P1)

運用者は、新しい VPS（Ubuntu）に対して、手順書の手順を上から順に実行するだけで、ファクトリーを systemd で常駐させ、Caddy で HTTPS 公開するところまで到達する。秘密情報は手順書にもリポジトリにも書かず、VPS 上の権限を絞ったファイルに置く。手順は何度流しても同じ結果になる。

**Why this priority**: VPS の無料期間は2週間しかない（12-03〜12-16）。解禁の日に調べものや手直しをすると、24時間稼働の実績づくりの時間が減る。

**Independent Test**: 本物の VPS の代わりに、systemd が動くローカルの Ubuntu 環境（コンテナ）で配備の手順を流し、サービスが起動して、Caddy 経由で生存確認の URL に届くことを確かめる。2回目を流しても壊れないことも確かめる。

**Acceptance Scenarios**:

1. **Given** 初期状態の Ubuntu 環境、**When** 手順書の配備手順を上から流す、**Then** ファクトリーが専用ユーザーで常駐し、再起動しても自動で起動する
2. **Given** 配備済みの環境、**When** 配備手順をもう一度流す、**Then** エラーにならず、状態も変わらない（データベースは消えない）
3. **Given** 配備済みの環境、**When** ファクトリーのプロセスが異常終了する、**Then** 自動で再起動する
4. **Given** 配備済みの環境、**When** 運用者がログを見る、**Then** システムのログ（journald）から JSON の構造化ログを読める
5. **Given** 配備済みの環境、**When** 秘密情報のファイルの権限を調べる、**Then** ファクトリーのユーザーと管理者以外は読めない
6. **Given** 配備済みの環境、**When** 新しい版に更新する手順を流す、**Then** 依存の再インストール・マイグレーション・作業場のイメージの再ビルド・再起動が行われ、生存確認が正常に戻る
7. **Given** 配備済みの環境、**When** 外から開いているポートを調べる、**Then** SSH と HTTP・HTTPS だけが開いていて、ファクトリーのポートは外から直接届かない
8. **Given** 配備済みの環境、**When** 運用者が動いている版を調べる、**Then** チェックアウトしたコミットがわかる

### User Story 3 - Caddy で factory とステージングを公開する (Priority: P1)

Caddy は、ファクトリー用のドメインへのアクセスをファクトリーへ、ステージング用のドメインへのアクセスをステージングのデモアプリへ転送し、HTTPS の証明書を自動で取得・更新する。ドメイン名はリポジトリに書かず、VPS 上の設定で与える。

**Why this priority**: `03` 2章・5章。GitHub の Webhook（007）とステージングの公開（010）の入口になる。海外のトンネルサービスを使わない。

**Independent Test**: ローカルでは、証明書を内部の認証局で発行する設定にして Caddy を起動し、ファクトリー用の名前で生存確認の URL に届くこと、ステージング用の名前でステージング側（仮のアプリ）に届くことを確かめる。設定の文法は自動で検査する。

**Acceptance Scenarios**:

1. **Given** 起動中のファクトリーと Caddy、**When** ファクトリー用のドメインで生存確認の URL にアクセスする、**Then** ファクトリーの応答が返る
2. **Given** 起動中のステージングのアプリと Caddy、**When** ステージング用のドメインにアクセスする、**Then** ステージングのアプリの応答が返る
3. **Given** ステージングのアプリが止まっている、**When** ステージング用のドメインにアクセスする、**Then** 転送先がないことを示すエラーが返り、ファクトリー側には影響しない
4. **Given** HTTP でのアクセス、**When** どちらかのドメインにアクセスする、**Then** HTTPS に転送される
5. **Given** 起動中のファクトリーと Caddy、**When** ファクトリー用のドメインで公開していないパスにアクセスする、**Then** Caddy が「見つからない」を返し、ファクトリーに転送されない
6. **Given** Caddy の設定ファイル、**When** 自動の検査を走らせる、**Then** 文法の誤りがあれば失敗する

### User Story 4 - 秘密情報スキャンをローカル・CI・VPS で同じように使う (Priority: P2)

開発者は、ローカル（Workshop）と CI で同じコマンドで秘密情報スキャン（gitleaks）を走らせ、リポジトリに秘密情報が入っていないことを確かめる。VPS にも同じ版のスキャナーが入り、008 の出荷前チェックがそれを使える。テスト用の偽の秘密情報は、理由付きの許可リストで明示的に除外する。

**Why this priority**: 008 の出荷前チェック（原則 VI の自動マージ条件）の前提。ファクトリー自体のリポジトリに秘密情報が入るのも防ぐ。ただし配備そのもの（P1）には要らないので P2 とする。

**Independent Test**: 今のリポジトリでスキャンが通ること、偽のトークンを含むファイルを足すとスキャンが失敗することを、ローカルと CI の両方で確かめる。

**Acceptance Scenarios**:

1. **Given** 今のリポジトリ（テスト用の偽の秘密情報を含む）、**When** スキャンを走らせる、**Then** 許可リストの対象だけが除外され、成功する
2. **Given** 秘密情報らしい文字列を含む変更、**When** CI が走る、**Then** スキャンが失敗し、CI が赤になる
3. **Given** Workshop の開発環境を作り直した、**When** スキャナーのバージョンを調べる、**Then** 固定したバージョンが入っている
4. **Given** 配備済みの VPS、**When** スキャナーのバージョンを調べる、**Then** ローカル・CI と同じバージョンが入っている
5. **Given** スキャナーのダウンロード物、**When** 入れるとき、**Then** 固定したチェックサムと一致しなければ入れずに失敗する

---

### User Story 5 - 配備の手順をローカルで予行演習する (Priority: P2)

運用者は、VPS解禁の前に、ローカルの Docker で Ubuntu の環境を作って配備の手順書を通しで流し、生存確認までの到達を確かめる。予行演習は1つのコマンドで始まり、終わったら片付く。

**Why this priority**: 解禁の日に「手順書を上から流すだけ」にするための保証。P1 の配備物ができていれば手でも確かめられるので P2 とする。

**Independent Test**: 予行演習のコマンドを実行し、最後に生存確認が正常であることと、後片付けで何も残らないことを確かめる。

**Acceptance Scenarios**:

1. **Given** Docker が動く開発機、**When** 予行演習のコマンドを実行する、**Then** Ubuntu の環境で配備手順が通り、Caddy 経由の生存確認が正常を返す
2. **Given** 予行演習が終わった、**When** 片付けを実行する（または自動で片付く）、**Then** 予行演習のコンテナ・ネットワーク・ボリュームが残らない
3. **Given** 配備手順のどこかが失敗する、**When** 予行演習を実行する、**Then** どの手順で失敗したかがわかる形で止まる

### Edge Cases

- 生存確認の最中にデータベースがロックされている → 短い待ち時間で諦めて「不健康」を返し、待ち受けを止めない
- 停止の合図を受けたが処理中の要求がある → 一定時間待って終わる。時間を超えたら打ち切って終わる
- 停止の合図が2回来る → 2回目で即座に終わる
- 設定に HTTP の項目がない → 既定値（ループバックのアドレスと決まったポート）で起動する
- 待ち受けのアドレスに外向きのアドレスが設定された → 起動はするが、警告を出す（Caddy を通さない公開は想定外）
- 秘密情報のファイルがない・権限が広すぎる → 配備手順がその旨を示して止まる
- ドメインの DNS がまだ VPS を向いていない → Caddy の証明書の取得が失敗する。手順書に DNS の確認を先に置き、確かめ方を書く
- VPS の再起動でファクトリーが Docker より先に起動する → Docker の起動を待ってから起動する
- データベースの置き場所が書き込めない → 起動時にわかる形で異常終了し、systemd の再起動の繰り返しには上限がある
- スキャナーの公式の配布元に届かない → インストールが失敗し、理由を示して止まる（古い版や別の配布元に黙って切り替えない）
- スキャンで誤検知が出た → 許可リストに理由を書いて除外する。許可リストは対象を最小限に絞る

## Requirements *(mandatory)*

### Functional Requirements

**常駐プロセスと生存確認**

- **FR-001**: ファクトリーの起動処理は、設定の読み込み・ログ・マイグレーションのあと HTTP の待ち受けを始め、停止の合図を受けるまで終わってはならない
- **FR-002**: 待ち受けのアドレスとポートは設定で変えられなければならない。既定はループバックのアドレス（外から直接届かない）とする
- **FR-003**: 生存確認の URL（`/healthz`）は、データベースを読めれば「正常」、読めなければ「不健康」を、機械で判定できる状態コードと短い本文で返さなければならない。本文に内部の情報（パス、エラー文、設定値）を含めてはならない
- **FR-004**: 生存確認は認証なしで呼べ、LLM を呼ばず、予算を消費してはならない
- **FR-005**: 停止の合図（SIGTERM・SIGINT）を受けたら、新しい接続の受け付けをやめ、処理中の要求を上限時間まで待ち、データベースを閉じて終わらなければならない
- **FR-006**: 定義していないパスへの要求には「見つからない」を返し、内部の情報を漏らしてはならない
- **FR-007**: 開発用の LLM 提供元の設定では、これまでどおり常駐プロセスを起動してはならない（原則 I）

**systemd**

- **FR-008**: ファクトリーは systemd のサービスとして、専用の管理者でないユーザーで動かなければならない。異常終了したら自動で再起動し、短時間の再起動の繰り返しには上限を設ける
- **FR-009**: サービスは Docker とネットワークが使えるようになってから起動しなければならない
- **FR-010**: 秘密情報（APIキー、後続の機能で使う GitHub App の鍵など）は、VPS 上の権限を絞った環境変数ファイルからサービスに渡し、リポジトリ・手順書・ユニットファイルに値を書いてはならない
- **FR-011**: サービスは、書き込める場所をデータの置き場所と作業ディレクトリの置き場所に限るなど、systemd の保護設定で権限を絞らなければならない。作業場（003）の操作に要る Docker への接続は、専用ユーザーを `docker` グループに入れて許す
- **FR-012**: サービスのログは標準出力から journald に出し、運用者が JSON の構造化ログとして読めなければならない

**Caddy**

- **FR-013**: Caddy は、ファクトリー用のドメインをファクトリーの待ち受けに、ステージング用のドメインをステージングのデモアプリの待ち受けに転送しなければならない
- **FR-014**: ドメイン名と証明書の連絡先は、リポジトリに書かず、VPS 上の設定（環境変数）で与えなければならない
- **FR-015**: Caddy は HTTPS の証明書を自動で取得・更新し、HTTP でのアクセスを HTTPS に転送しなければならない
- **FR-016**: ファクトリー用のドメインで転送するのは、ファクトリーが公開するパス（本機能では `/healthz`、後続で `/webhook`・`/status`）だけとし、ほかのパスには Caddy が「見つからない」を返さなければならない
- **FR-017**: ローカルの確認用に、証明書を内部の認証局で発行する切り替えを持たなければならない（本物の認証局に要求しない）
- **FR-018**: Caddy の設定の文法は、自動の検査（CI を含む）で確かめられなければならない
- **FR-019**: ステージングのアプリが止まっていても、ファクトリー側の転送には影響してはならない

**配備手順と予行演習**

- **FR-020**: 配備手順は、初期状態の Ubuntu から、上から順に実行するだけで常駐と公開まで到達する手順書と、それが呼ぶスクリプトで構成しなければならない。手順書には各手順の確かめ方（期待する出力）を書く
- **FR-021**: ファクトリーのコードは、VPS 上で GitHub から取得し、コミットかタグを指定してチェックアウトしなければならない。VPS で動いている版（コミット）を運用者が確かめられなければならない
- **FR-022**: 配備のスクリプトは何度流しても同じ結果にならなければならず（冪等）、既存のデータベースとデータを消してはならない
- **FR-023**: 配備のスクリプトは、途中で失敗したらその手順を示して止まらなければならない
- **FR-024**: 配備手順は、ランタイム・パッケージマネージャー・Caddy・スキャナーのバージョンを固定して入れなければならない。Docker は Ubuntu LTS の配布物に従う（Workshop の開発環境と同じ入れ方にし、セキュリティ更新を受ける）
- **FR-025**: 配備手順は、外から届くポートを SSH・HTTP・HTTPS に限り、SSH のパスワードでのログインを無効にしなければならない
- **FR-026**: 更新の手順（新しい版の取得、依存の再インストール、マイグレーション、作業場のイメージの再ビルド、再起動、生存確認）を、1つのスクリプトで実行できなければならない
- **FR-027**: 予行演習は、ローカルの Docker 上の systemd が動く Ubuntu の環境（特権付きのコンテナ。中に配備スクリプトで Docker を入れる）で、配備のスクリプトを本番と同じものを使って流し、Caddy 経由の生存確認までを確かめなければならない。予行演習で本物の認証局・本物の LLM は使わない。コードは GitHub から取らず、開発機のリポジトリの HEAD のコミットを渡してよい
- **FR-028**: 予行演習は終わったら（成功・失敗とも）作ったコンテナ・ネットワーク・ボリュームを片付けなければならない

**秘密情報スキャン**

- **FR-029**: 秘密情報スキャナーは、ローカル（Workshop）・CI・VPS で同じバージョンを使わなければならない。入れるときはダウンロード物のチェックサムを確かめ、一致しなければ入れない
- **FR-030**: リポジトリのスキャンは、ローカルと CI で同じコマンドで実行し、作業ツリーだけでなく git の履歴全体を対象にしなければならない
- **FR-031**: CI は、スキャンで秘密情報が見つかったら失敗しなければならない
- **FR-032**: テスト用の偽の秘密情報は、対象と理由を書いた許可リストで明示的に除外しなければならない。許可リストで規則全体や広いディレクトリを除外してはならない

**テスト**

- **FR-033**: 生存確認・停止処理・待ち受けの設定は、自動テストで確かめられなければならない
- **FR-034**: systemd のユニットの文法、Caddy の設定の文法、配備スクリプトのシェルの文法は、自動の検査で確かめられなければならない

### Key Entities *(include if feature involves data)*

- **HTTP の設定**: 待ち受けのアドレス、ポート、停止時に処理中の要求を待つ上限時間
- **生存確認の結果**: 正常か不健康か。外に見せるのは状態だけ
- **配備物**: systemd のユニット、Caddy の設定、配備・更新のスクリプト、秘密情報のファイルのひな形（値は空）、手順書
- **VPS 上の設定**: ドメイン名（ファクトリー用・ステージング用）、証明書の連絡先、秘密情報の環境変数ファイル
- **スキャナーの固定情報**: バージョン、ダウンロード物のチェックサム、許可リスト

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 予行演習のコマンド1つで、初期状態の Ubuntu 環境から Caddy 経由の生存確認が正常を返すまでが、手作業なしで 15 分以内に終わる
- **SC-002**: 配備のスクリプトを2回続けて流しても、2回目がエラーにならず、データベースの中身が変わらない
- **SC-003**: ファクトリーのプロセスを強制終了してから 30 秒以内に、自動で再起動して生存確認が正常に戻る
- **SC-004**: 停止の合図から 10 秒以内にプロセスが終わる
- **SC-005**: 生存確認が、正常時に 100 ミリ秒以内に応答する
- **SC-006**: リポジトリ・手順書・配備物に、秘密情報の値とドメイン名の実値が 1 件も含まれない（スキャンと目視で確認）
- **SC-007**: 偽のトークンを含む変更を加えると、ローカルのスキャンと CI のスキャンの両方が 100% 失敗する
- **SC-008**: ローカル・CI・VPS のスキャナーのバージョンが一致する

## Assumptions

- VPS は さくらのVPS の Ubuntu 24.04 LTS とし、1台にファクトリー・作業場・ステージングを載せる（`03` 2章）
- ステージングのデモアプリそのもの（compose、ビルド、入れ替え、ロールバック）は 010 で作る。本機能は Caddy の転送先（ローカルのポート）を決め、予行演習では仮のアプリで確かめるだけにする
- `/webhook`（007）と `/status`（011）は本機能では作らない。HTTP の土台に後から足せる形にするだけにする
- Worker（ジョブの処理）は 007 で足す。本機能の常駐プロセスは HTTP の待ち受けだけを行う
- VPS の契約・DNS の登録・GitHub App の作成は運用者が手で行い、手順書にその確認だけを書く
- データベースのバックアップ・監視の通知は扱わない（必要なら後で足す）
- 作業場（003）を動かすため、ファクトリーのユーザーは `docker` グループに入る（Docker を操作できることは実質的に管理者権限に近い。このリスクは計画の Complexity Tracking で扱う）
- 予行演習は開発機の Docker（または Workshop の中の Docker）で、特権付きのコンテナを使って行う。CI では文法の検査だけを行う（CI で systemd の環境を立ち上げる予行演習は重いので必須にしない）
- ファクトリーのリポジトリは GitHub から HTTPS で取得できる前提とする。非公開にする場合は読み取り専用のデプロイキーを使う手順を手順書に書く
- 秘密情報スキャナーは gitleaks とする（原則 VI、`04` 2章 層6）。008 での対象リポジトリの diff のスキャンの使い方は 008 で決める
