## Clarifications

### Session 2026-11-12

ユーザーの指示（人間の確認が要るものは、いったん推奨する内容で進める）により、以下は推奨の回答で決めた。

- Q: どんなコメントを `@agent` の依頼とみなすか？ → A: 最初の空でない行が `@agent`（単語として）で始まるコメントだけ（推奨）。文中の言及・引用・コードの中は依頼にしない。誤って動くと月の予算を消費するので、意図がはっきりした形に絞る
- Q: 権限のない人の `@agent` に、Issue で返事をするか？ → A: 返事をしない。ログにだけ残す（推奨）。返事をすると、誰でもファクトリーにコメントを書かせられ、スパムの踏み台になる
- Q: 権限の確認や記録に失敗したとき、GitHub に再送してもらえるか？ → A: GitHub は失敗した Webhook を自動では再送しない（手動の再送だけ）。失敗したら積まずに `500` を返し、配送の ID とともにログに残す。運用者は App の設定画面の「Recent Deliveries」から再送できる（推奨）。自前の再試行の仕組み（受信箱のテーブル）は、同時実行1件・1台の構成には過剰なので持たない
- Q: 008（出荷）ができるまで、判定に合格したジョブをどう終えるか？ → A: 判定の結果を Issue に報告し、`failed`（理由: 出荷の工程が未実装）で終える（推奨）。状態は `03` 3章の決め打ちのものだけを使い、出荷していないのに成功の状態にしない。008 で `pr_opened` へ進めるように差し替える
- Q: 予算が残っていないときの知らせは、どの単位で1回か？ → A: 断った依頼1件ごとに1回（推奨）。依頼できるのは権限のある人だけなので数は少なく、依頼した人が自分の依頼の結果を知れることを優先する

## User Scenarios & Testing *(mandatory)*

この機能の利用者は3種類いる。

- **依頼者**（対象リポジトリに書き込み権限のある開発者）: Issue に `@agent` とコメントして作業を頼み、受け付けられたか・失敗したかを Issue で知る
- **権限のない人・外部の第三者**: Issue にコメントできるが、ファクトリーを動かせてはならない。Webhook の URL に偽の要求を送ってくることもある
- **運用者**: ジョブの状態と失敗の理由を、データベースとログで追う

### User Story 1 - 正しい Webhook だけを受け取る (Priority: P1)

ファクトリーは、GitHub から届く Webhook の署名を確かめ、正しいものだけを処理する。署名がない・合わない要求は、中身を読まずに拒否する。同じ配送が2回届いても、ジョブは1つしかできない。

**Why this priority**: 原則 IV（Webhook は署名を定数時間比較で検証してから処理する）。Webhook の URL は公開されるので、これがないと誰でもジョブを作れる。

**Independent Test**: 正しい秘密で署名した要求・署名のない要求・別の秘密で署名した要求・本文を書き換えた要求を送り、正しいものだけが処理されることを確かめる。GitHub は使わない（記録したペイロードを使う）。

**Acceptance Scenarios**:

1. **Given** 正しい秘密で署名した `issue_comment` の要求、**When** `/webhook` に届く、**Then** 受け付けて `202` を返す
2. **Given** 署名のない要求、または別の秘密で署名した要求、**When** 届く、**Then** `401` を返し、本文を解釈せず、ジョブを作らない
3. **Given** 署名のあとで本文を1バイト書き換えた要求、**When** 届く、**Then** `401` を返す
4. **Given** 処理の対象でないイベント（`ping`、ほかのイベント）、**When** 届く、**Then** `202`（`ping` は `200`）を返し、ジョブを作らない
5. **Given** 同じコメントの配送が2回届く、**When** 処理する、**Then** ジョブは1つだけで、2回目もエラーにならない
6. **Given** 上限を超える大きさの本文、**When** 届く、**Then** 読み切る前に `413` を返す

---

### User Story 2 - `@agent` の依頼を確かめてキューに積む (Priority: P1)

ファクトリーは、Issue に付いた新しいコメントが `@agent` の依頼かを判定し、依頼者が対象リポジトリに書き込み権限を持ち、設定の許可ユーザーに含まれるときだけジョブを積む。積んだら Issue のコメントにリアクションを付けて、受け付けたことを知らせる。月の予算の残りが1ジョブの上限を下回っていれば積まず、その旨を Issue に1回だけ知らせる。

**Why this priority**: `04` 2章 層1（実行できるのは書き込み権限のあるユーザーだけ）と原則 V（月の残りが1ジョブの上限を下回ったら新しいジョブを受け付けない）。依頼の入口そのもの。

**Independent Test**: 依頼者の権限・許可ユーザー・コメントの形・予算の残りを変えたペイロードを流し、ジョブが積まれるか・リアクションと知らせが出るかを確かめる。GitHub の API は偽物に差し替える。

**Acceptance Scenarios**:

1. **Given** 書き込み権限があり許可ユーザーに含まれる人の、`@agent` で始まる新しいコメント、**When** 受け付ける、**Then** ジョブが `queued` で1つでき、コメントに「受け付けた」リアクションが付く
2. **Given** 書き込み権限のない人（または許可ユーザーに含まれない人）の `@agent` コメント、**When** 受け付ける、**Then** ジョブを作らず、Issue に何も書かない（ログにだけ残す）
3. **Given** 文中で `@agent` に触れているだけのコメント（引用やコードの中、行の途中）、**When** 受け付ける、**Then** 依頼とみなさない
4. **Given** ボット（ファクトリー自身を含む）のコメント、**When** 受け付ける、**Then** 依頼とみなさない
5. **Given** コメントの編集・削除、または Pull Request に付いたコメント、**When** 受け付ける、**Then** 依頼とみなさない
6. **Given** 月の予算の残りが1ジョブの上限を下回っている、**When** 正しい依頼が来る、**Then** ジョブを作らず、受付を止めた時刻を記録し、その依頼に対して Issue に「今月の予算が残っていない」旨を1回だけ書く
7. **Given** 依頼の本文（`@agent` のあとの文）、**When** ジョブを積む、**Then** 本文は依頼の指示としてそのまま保存され、上限を超える部分は切り詰められる

### User Story 3 - Worker がジョブを1件ずつ処理する (Priority: P1)

ファクトリーは、積まれたジョブを古い順に1件ずつ取り出し、対象リポジトリを作業ディレクトリに取得して作業ブランチを作り、依存をインストールしたうえで、計画から判定までの工程（005）を実行する。工程の遷移は決め打ちの状態機械で行い、遷移のたびに記録を残す。ジョブ全体の時間に上限を設ける。

**Why this priority**: ファクトリーの5条件の「イベント駆動・非同期」。005 の工程を、Issue から来たジョブで回せるようにする。

**Independent Test**: 偽の LLM・偽の GitHub・ローカルの git リポジトリを使い、積んだジョブが取り出され、作業ブランチが作られ、005 の工程が呼ばれ、状態が順に移って記録されることを確かめる。

**Acceptance Scenarios**:

1. **Given** `queued` のジョブが2つある、**When** Worker が動く、**Then** 古いほうから1つずつ処理し、同時に2つは処理しない
2. **Given** 取り出したジョブ、**When** 準備する、**Then** 対象リポジトリの既定のブランチを作業ディレクトリに取得し、ジョブごとの作業ブランチを作る
3. **Given** 取得した作業ディレクトリ、**When** 中の git の設定を調べる、**Then** GitHub のトークンはどこにも書かれていない
4. **Given** 準備が終わったジョブ、**When** 工程を進める、**Then** 005 の計画から判定までを呼び、状態は `planning` → `implementing` → `testing` → `judging` の順に移り、移るたびに記録が1件残る
5. **Given** 決め打ちの遷移にない移り方（例: `queued` から `judging`）、**When** 状態を変えようとする、**Then** 拒否され、状態は変わらない
6. **Given** ジョブ全体の時間の上限を超えた、**When** 工程の途中、**Then** 工程を打ち切り、`failed`（理由: 時間切れ）にする
7. **Given** 判定に合格したジョブ（出荷の工程 008 がまだない）、**When** 工程が終わる、**Then** 判定の結果を Issue に報告し、`failed`（理由: 出荷の工程が未実装）で終える
8. **Given** ジョブが終わった（成功・失敗・例外のどれでも）、**When** 片付ける、**Then** そのジョブの作業場（コンテナ）と作業ディレクトリが残らない

### User Story 4 - 失敗したら Issue に1回だけ報告する (Priority: P1)

ファクトリーは、ジョブがどこで失敗しても、失敗の理由・どの工程で止まったか・消費したリクエスト数を、Issue に1回だけコメントしてから止める。報告には秘密情報を含めない。報告の投稿そのものが失敗しても、ジョブは `failed` になり、記録が残る。

**Why this priority**: 原則 II（失敗時も Issue にまとめレポートを1回投稿してから停止する）。007 は最小版で、008 で完成させる。

**Independent Test**: 工程の各所（取得・インストール・005 の工程・時間切れ・予算切れ）で失敗させ、Issue へのコメントがちょうど1回で、必要な項目を含み、秘密情報を含まないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 工程の途中で失敗したジョブ、**When** 失敗の処理をする、**Then** `failed` になり、Issue に、失敗した工程・理由・消費したリクエスト数・ジョブの番号を含むコメントが1回だけ付く
2. **Given** 失敗の理由にトークンや秘密鍵らしい文字列が含まれる、**When** 報告する、**Then** その値は伏せ字になっている
3. **Given** 報告の投稿が GitHub の障害で失敗する、**When** 失敗の処理をする、**Then** ジョブは `failed` のままで、投稿の失敗が記録に残る（ジョブの処理は止まらない）
4. **Given** 同じジョブの失敗の処理が2回呼ばれる、**When** 処理する、**Then** 報告は1回だけ

---

### User Story 5 - 再起動しても途中のジョブを宙に浮かせない (Priority: P2)

ファクトリーが途中で止まって再起動したとき、処理中だったジョブを `failed`（理由: 再起動で中断）にして報告し、前回の作業場と作業ディレクトリを片付けてから、次のジョブの処理を始める。

**Why this priority**: 24時間稼働（systemd の自動再起動）の前提。処理中のまま残ったジョブがあると、同時実行1件の制約で後ろのジョブが止まる。ただし通常の流れ（P1）が先なので P2 とする。

**Independent Test**: `implementing` のまま残ったジョブと、残った作業場・作業ディレクトリがある状態で起動し、ジョブが `failed` になって報告され、残骸が消えることを確かめる。

**Acceptance Scenarios**:

1. **Given** LLM を使う工程の状態（`planning`〜`judging`）のまま残ったジョブ、**When** 起動する、**Then** そのジョブを `failed`（理由: 再起動で中断）にし、Issue に1回だけ報告する
2. **Given** 前回の作業場と作業ディレクトリが残っている、**When** 起動する、**Then** 片付けてから次のジョブを処理する
3. **Given** `queued` のジョブ、**When** 起動する、**Then** そのまま残り、順に処理される
4. **Given** 停止の合図、**When** ジョブの処理中に受ける、**Then** 新しいジョブを取り出さず、処理中のジョブを中断して `failed`（理由: 停止で中断）にしてから終わる

---

### Edge Cases

- 1つのコメントに `@agent` の行が複数ある → 最初の行からあとを依頼の本文とし、ジョブは1つ
- `@agent` だけで本文が空 → 依頼とみなすが、指示がないので積まずに Issue に使い方を1回だけ書く
- `@agentx` や `@agent-bot` など、別の名前 → 依頼とみなさない
- Issue が閉じられている → 依頼とみなさない
- 権限の確認の API が失敗・時間切れ → 安全側に倒して積まない。`500` を返し、配送の ID をログに残す（GitHub は自動では再送しないので、運用者が App の設定画面から再送する）
- リアクションの付与が失敗する → ジョブは積んだまま進める（ログに残す）
- 同じ Issue に、前の依頼が終わる前に新しい依頼が来る → 別のジョブとして順番に積む（同じ Issue のジョブの重複は止めない）
- 対象リポジトリにファクトリーの GitHub App が入っていない → 権限の確認ができないので積まない
- 取得（clone）が失敗する（リポジトリが大きすぎる、ネットワーク） → `failed`（理由: 取得の失敗）にして報告
- 作業ブランチの名前がすでにリモートにある → ジョブの番号を含む名前なので重ならない。007 は push しないので、リモートとの重なりは push する 008 で扱う
- Webhook の本文が JSON として不正 → 署名が正しくても `400` を返し、ジョブを作らない
- データベースに書けない → `500` を返し、配送の ID をログに残す（同上）
- 005 の工程が例外を投げる → `failed`（理由: 内部エラー）にして報告する

## Requirements *(mandatory)*

### Functional Requirements

**Webhook の受け取り（層1）**

- **FR-001**: ファクトリーは `POST /webhook` で GitHub の Webhook を受け取らなければならない
- **FR-002**: 処理の前に、本文の HMAC-SHA256 署名を、設定した秘密で計算した値と定数時間で比較しなければならない。署名がない・合わないときは `401` を返し、本文を解釈してはならない
- **FR-003**: 本文の大きさに上限を設け、超えたら読み切る前に `413` を返さなければならない
- **FR-004**: 同じコメントからのジョブは1つだけにしなければならない（配送の重複・再送に対して冪等）
- **FR-005**: 処理の対象は、Issue（Pull Request ではない）に新しく付いたコメントだけとし、それ以外のイベント・操作はジョブを作らずに受け取りだけ返さなければならない。`ping` には `200` を返す
- **FR-006**: Webhook への応答は、ジョブを積むか積まないかを決めたらすぐに返し、ジョブの処理を待ってはならない

**依頼の判定と受付**

- **FR-007**: コメントの最初の空でない行が `@agent`（単語として。直後が空白か行末）で始まるときだけ、依頼とみなさなければならない。引用（`>`）やコードの中の `@agent` は依頼とみなさない
- **FR-008**: ボットのコメント（ファクトリー自身を含む）、閉じた Issue へのコメントは依頼とみなしてはならない
- **FR-009**: 依頼者が対象リポジトリに書き込み以上の権限を持ち、かつ設定の許可ユーザーに含まれるときだけ、ジョブを積まなければならない。権限は GitHub の API で毎回確かめる
- **FR-010**: 権限のない依頼は、ジョブを作らず、Issue に何も書かず、ログにだけ残さなければならない
- **FR-011**: 権限の確認ができない（API の失敗・時間切れ・App が入っていない）ときは、積まずに安全側に倒し、`500` を返して配送の ID をログに残さなければならない（GitHub は自動では再送しないので、運用者が手で再送できるようにする）
- **FR-012**: ジョブを積んだら、依頼のコメントに「受け付けた」リアクションを付けなければならない。リアクションの失敗でジョブを取り消してはならない
- **FR-013**: 月の予算の残りが1ジョブの上限を下回っているときは、ジョブを積まず、その月の受付を止めた時刻を記録し（最初の1回だけ）、断った依頼1件ごとに Issue に予算が残っていない旨を1回書かなければならない
- **FR-014**: 依頼の本文（`@agent` のあとの文）を、Issue の番号・依頼者・コメントの ID と一緒にジョブとして保存しなければならない。本文は上限で切り詰める。本文は「データ」として扱い、受付の判断に使わない
- **FR-015**: 依頼の本文が空なら、積まずに Issue に使い方を1回だけ書かなければならない

**Worker と状態機械**

- **FR-016**: Worker は `queued` のジョブを古い順に1件ずつ取り出し、LLM を使う工程を同時に1件だけ処理しなければならない
- **FR-017**: ジョブの状態の遷移は、決め打ちの遷移の表に従わなければならない。表にない遷移は拒否する。遷移のたびに、前後の状態と時刻を記録に残す
- **FR-018**: 準備の工程では、GitHub App の短命のトークンで対象リポジトリの既定のブランチを作業ディレクトリに取得し、ジョブごとの作業ブランチ（ジョブの番号を含む名前）を作らなければならない
- **FR-019**: トークンを作業ディレクトリ（git の設定・リモートの URL を含む）に書き残してはならない。作業場（コンテナ）にトークンを渡してはならない
- **FR-020**: 作業ディレクトリは、ファクトリーのデータの置き場所の下にジョブごとに作らなければならない（006 の配備で作業場から bind mount できる場所）
- **FR-021**: 準備のあと、依存のインストール（003）を行い、計画から判定までの工程（005）を呼ばなければならない
- **FR-022**: ジョブ全体の時間に上限（設定）を設け、超えたら工程を打ち切って `failed` にしなければならない
- **FR-023**: 判定に合格したジョブは、出荷の工程（008）ができるまで、判定の結果を Issue に報告し、`failed`（理由: 出荷の工程が未実装）で終えなければならない
- **FR-024**: ジョブが終わったら（成功・失敗・例外のどれでも）、作業場と作業ディレクトリを片付けなければならない

**失敗時の報告**

- **FR-025**: ジョブが `failed` になるときは、Issue に、失敗した工程・理由・消費したリクエスト数・ジョブの番号を含むコメントを1回だけ投稿しなければならない
- **FR-026**: 報告は、秘密情報を伏せてから投稿しなければならない（001 のマスクと同じ判定）
- **FR-027**: 報告の投稿が失敗しても、ジョブは `failed` のままにし、投稿の失敗を記録に残さなければならない

**起動と停止**

- **FR-028**: 起動時に、LLM を使う工程の状態のまま残ったジョブを `failed`（理由: 再起動で中断）にして報告し、残った作業場と作業ディレクトリを片付けなければならない
- **FR-029**: 停止の合図を受けたら、新しいジョブを取り出さず、処理中のジョブを中断して `failed`（理由: 停止で中断）にし、006 の停止の上限時間の中で終わらなければならない

**GitHub 層と設定**

- **FR-030**: GitHub 固有の処理（App の認証、署名の検証、権限の確認、リアクション、コメント、トークンの発行）は1つの層にまとめ、ほかの層から GitHub の型や SDK を直接使ってはならない（原則 VII）
- **FR-031**: GitHub App の ID・秘密鍵・Webhook の秘密は、環境変数（秘密鍵はファイルの場所）で与え、設定ファイルとリポジトリに書いてはならない
- **FR-032**: 本文の上限、Worker がキューを見る間隔は設定で変えられなければならない

**テスト**

- **FR-033**: 署名の検証・依頼の判定・状態の遷移・受付・Worker・報告は、GitHub と本物の LLM を使わない自動テストで確かめられなければならない（記録したペイロード、偽の GitHub、偽の LLM、ローカルの git リポジトリ）

### Key Entities *(include if feature involves data)*

- **ジョブ（Job）**: 001 の `jobs` テーブル。対象リポジトリ、Issue の番号、依頼のコメントの ID（リポジトリと組で一意）、依頼者、依頼の本文、状態、作業ブランチ、失敗の理由、時刻
- **ジョブの記録（Job event）**: 001 の `job_events`。状態の遷移（前後の状態）、メモ、エラー（報告の投稿の失敗など）
- **依頼（Request）**: Webhook から取り出した、リポジトリ・Issue・コメント・依頼者・本文の組。受付の判定の入力
- **遷移の表（Transition table）**: 状態ごとに移ってよい先の一覧。`03` 3章の状態機械
- **月の予算（Budget）**: 001 の `budget`。受付を止めた時刻を持つ
- **GitHub の設定**: App の ID、秘密鍵のファイルの場所、Webhook の秘密、許可ユーザー

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 署名のない・合わない・書き換えた要求の確認セットで、ジョブが作られる件数が 0
- **SC-002**: 権限のない人・許可ユーザーでない人・ボット・文中の言及の確認セットで、ジョブが作られる件数が 0。正しい依頼の確認セットでは取りこぼしが 0
- **SC-003**: 同じ配送を何回送っても、ジョブは1つ
- **SC-004**: Webhook への応答が、正常時に 1 秒以内に返る（GitHub の待ち時間の上限 10 秒に余裕を持たせる）
- **SC-005**: 失敗したジョブの 100% で、Issue への報告がちょうど1回（投稿の失敗を除く）
- **SC-006**: 作業ディレクトリ・作業場・報告・ログのどこにも、GitHub のトークンと App の秘密鍵の値が現れない
- **SC-007**: LLM を使う工程が同時に2件以上動くことがない
- **SC-008**: ジョブの終了後（成功・失敗・例外）、そのジョブの作業場と作業ディレクトリが1つも残らない
- **SC-009**: 再起動のあと、処理中のまま残ったジョブが 0（すべて `failed` になり報告されている）

## Assumptions

- 計画から判定までの工程は 005（local-pipeline）が提供し、本機能は「作業ディレクトリ・Issue の本文・依頼の本文を渡し、判定の結果を受け取る」入口として呼ぶ。005 の入口の形が決まったら plan で合わせる
- PR の作成・自動マージ・まとめレポートの完成版は 008、CI 待ちは 009 で作る。本機能の状態機械は `03` 3章の全状態を表に持つが、実際に動かすのは `queued` から `judging` までと `failed`
- 常駐の HTTP（`/healthz`、待ち受け、停止処理）、systemd、Caddy は 006 のものを使う。`/webhook` は 006 の Caddyfile で既に転送されている
- 対象リポジトリは TypeScript で、依存のインストールのコマンドは pnpm（`pnpm install --frozen-lockfile`）とする（003 の作業場のイメージに合わせる）
- GitHub App は運用者が手で作り、対象リポジトリに入れる。App の権限とイベントは `03` 5章のとおり（Workflows の書き込みなし）。手順は 006 の手順書に足す
- 受付の応答の中で、権限の確認の API を1回呼ぶ（数百ミリ秒）。GitHub の Webhook の待ち時間の上限（10 秒）に収まる
- テストでは GitHub の API を呼ばない。本物の GitHub での確認は、テスト用のリポジトリで手で行う（`docs/実装計画.md` の M2）
