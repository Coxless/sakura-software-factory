# Feature Specification: 計測と状況ページ（status-dashboard）

**Feature Branch**: `011-status-dashboard`

**Created**: 2026-11-14

**Status**: Draft

**Input**: User description: "011 status-dashboard 計測と /status。範囲: 今月の消費、成功率、平均処理時間、CI初回通過率、デプロイ成功率を /status で表示する（Hono の簡易ダッシュボード、LLM は呼ばない）。依存: 001（データは 002〜010 で記録済み: llm_calls, jobs, job_events, deployments, budget, agent_runs）。関係する設計: docs/design/03 7章（計測）、2章・5章（公開するパス /status は Caddy で転送）、トレースの可視化（agent_runs の要約を /status で見られるようにする）。ブランチ名は 011-status-dashboard。"

## Clarifications

### Session 2026-11-14

- Q: 状況ページはインターネットからどう見えるか？ → A: 公開のドメインで配るが、認証付きにする（ユーザーの判断。「脆弱性になりそうなものは入れたくない」）。認証は前段の Web サーバーで行い、パスワードはハッシュだけを設定に置く。認証の設定がなければ状況ページは外に出さない（前段が 404 を返す）
- Q: 認証があるなら何まで出すか？ → A: 集計値、ジョブ・工程・デプロイの要約（番号・状態・時刻・件数・終わり方・失敗の理由のコード値）、リポジトリ名と Issue・PR の番号まで。依頼の本文・エラー文・軌跡の中身・軌跡のファイルの場所・秘密の設定値は、認証があっても出さない（認証が破られても、また画面の写しが記事に載っても困らない範囲に絞る）
- Q: 「成功」とは何か？ → A: ジョブがステージングまで反映された（`deployed`）こと。`rolled_back` と `failed` は不成功。Draft PR で人間に渡したジョブは、人間がマージするまで終わらない（CI 待ちのまま）ので、終わったジョブの率には入らない
- Q: 集計の期間は？ → A: 今月（予算と同じタイムゾーンの月の区切り）。月をまたいで比べるのは SQL か回帰評価で行う
- Q: ジョブに属さない LLM 呼び出し（回帰評価・スモークテスト）は消費に入れるか？ → A: 入れる。月の予算から実際に減るため。内訳でジョブの分とジョブ以外の分を分ける

## User Scenarios & Testing *(mandatory)*

この機能の利用者は2種類いる。

- **運用者**: ファクトリーが今どう動いているか（予算の残り・失敗の傾向・止まっているジョブ）を、VPS に入らずにブラウザで確かめたい
- **記事の筆者（運用者と同じ人）**: 徹底検証の数値（消費・成功率・処理時間・CI 初回通過率・デプロイ成功率）を、画面か機械で読める形で取り出したい

### User Story 1 - 今月の数値を1画面で見る (Priority: P1)

運用者は、ブラウザで状況ページを開き、認証を通ると、今月の LLM の消費と上限・残り、ジョブの成功率、平均処理時間、CI 初回通過率、デプロイ成功率を1画面で見られる。

**Why this priority**: `03` 7章の決定事項そのもの。24時間稼働中に予算と品質を見張る手段で、記事の数値の出どころになる。

**Independent Test**: 決まった中身のデータベース（今月と先月のジョブ・呼び出し・デプロイ・CI の記録）を用意してページを取得し、各数値が期待どおりであることを確かめる。

**Acceptance Scenarios**:

1. **Given** 今月の LLM 呼び出しが 412 件、月の上限が 3000、**When** ページを開く、**Then** 「412 / 3000」と残り 2588 が表示され、役割別・モデル別・ジョブ以外の件数、入出力トークンの合計、失敗の種類別の件数が出る
2. **Given** 今月終わったジョブが `deployed` 6件・`rolled_back` 1件・`failed` 3件、**When** ページを開く、**Then** 成功率 60%（6/10）と、失敗の理由ごとの件数が出る
3. **Given** 今月終わったジョブがある、**When** ページを開く、**Then** 開始から終わりまでの時間の平均と中央値が出る
4. **Given** CI の結果が出たジョブが 5 件あり、うち 4 件は1回目の CI で通った、**When** ページを開く、**Then** CI 初回通過率 80%（4/5）が出る
5. **Given** 今月終わったデプロイが成功 8件・失敗 2件（うち1件はロールバック）、**When** ページを開く、**Then** デプロイ成功率 80%（8/10）とロールバック 1件が出る
6. **Given** 先月の記録だけがある、**When** ページを開く、**Then** 今月の数値はどれも 0 件として出て、率は「データなし」と表示される（0 で割らない）
7. **Given** 月の受付を予算で止めている、**When** ページを開く、**Then** 受付停止中であることと止めた時刻が出る

---

### User Story 2 - 最近のジョブと工程の実行を見る (Priority: P2)

運用者は、同じページで最近のジョブと、ツールを使う工程・計画・判定の実行1回ごとの要約を新しい順に見られる。止まっている・やり直しを繰り返しているジョブに気づける。

**Why this priority**: `03` のトレースの可視化（実行ごとの要約を状況ページで見られるようにする）。数値だけでは「どのジョブが」が分からない。

**Independent Test**: ジョブと工程の実行を件数より多く用意し、新しい順に決まった件数だけ出ること、出してはいけない列が本文に含まれないことを確かめる。

**Acceptance Scenarios**:

1. **Given** ジョブが 30 件ある、**When** ページを開く、**Then** 新しい順に 20 件まで、番号・リポジトリ・Issue・PR の番号・状態・失敗の理由・作成時刻・所要時間・使ったリクエスト数が出る
2. **Given** 工程の実行の記録がある、**When** ページを開く、**Then** 新しい順に決まった件数まで、ジョブ番号・工程・何回目・モデル・終わり方・ターン数・リクエスト数・ツール呼び出し数・ブロックされた数・判定・所要時間が出る。終わっていない実行は「実行中」と出る
3. **Given** ジョブの依頼の本文・工程のエラー文・軌跡のファイルの場所が記録されている、**When** ページを取得する、**Then** それらの文字列は応答のどこにも含まれない
4. **Given** 最近のデプロイの記録がある、**When** ページを開く、**Then** 新しい順に決まった件数まで、番号・ジョブ番号・commit（短縮）・状態・失敗した段階・ロールバックの有無・revert PR の番号が出る

---

### User Story 3 - 同じ数値を機械で読める形で取り出す (Priority: P2)

記事の筆者は、同じ内容を JSON で取得し、記事の表やグラフの材料にする。

**Why this priority**: 画面の数値を手で写すと誤りが入る。SQL を書かずに同じ定義の数値を取れるようにする。

**Independent Test**: JSON の形式を指定して取得し、決まった形（スキーマ）に合うこと、HTML と同じ数値であることを確かめる。

**Acceptance Scenarios**:

1. **Given** 記録がある、**When** JSON の形式を指定して取得する、**Then** HTML と同じ集計値と一覧が、決まったスキーマの JSON で返る
2. **Given** 知らない形式を指定する、**When** 取得する、**Then** HTML が返る（エラーにしない）

---

### User Story 4 - 認証なしでは見られない (Priority: P1)

公開のドメインからは、正しい認証情報を持つ人だけが状況ページを見られる。認証の設定がない配備では、状況ページは外に出ない。

**Why this priority**: ユーザーの判断（脆弱性になりそうなものは入れない）。リポジトリ名・Issue 番号など、非公開のリポジトリの手がかりを含むため。

**Independent Test**: 前段の Web サーバーの設定を検査用の手順で確かめる（認証なしで 401、正しい認証で 200、認証の設定がない場合は 404）。ファクトリー本体の側は、ページの応答にキャッシュ禁止・埋め込み禁止などの安全のための見出しが付くことをテストで確かめる。

**Acceptance Scenarios**:

1. **Given** 認証の設定がある配備、**When** 認証なしで状況ページを開く、**Then** 401 が返り、中身は返らない
2. **Given** 認証の設定がある配備、**When** 正しい認証情報で開く、**Then** ページが返る
3. **Given** 認証の設定がない配備、**When** 外から状況ページを開く、**Then** 404 が返る（`/healthz`・`/webhook` はこれまでどおり）
4. **Given** ページの応答、**When** 受け取る、**Then** キャッシュ禁止・他のサイトへの埋め込み禁止・スクリプトを動かさない指定が付いている

### Edge Cases

- 記録が1件もない（起動直後）: すべて 0 件・「データなし」で出る。エラーにしない
- 月の境目: 月の区切りは予算と同じタイムゾーンで決め、月をまたいだジョブは終わった時刻の月に数える。LLM 呼び出しは呼び出しの開始時刻の月に数える（予算ゲートと同じ）
- 終わっていないジョブ（`queued`〜`deploying`）: 成功率・処理時間には入らず、一覧には今の状態で出る
- CI が1回も結論を出さずに終わったジョブ（CI 待ちの期限切れなど）: CI 初回通過率の分母に入らない
- 終わり時刻がないのに終わりの状態になっているジョブ（古い記録）: 処理時間の計算から外す
- データベースが読めない: 500 を返し、内部の情報（パス・エラー文）は本文に入れない。運用者向けのログには残す
- 記録が多い（数万件）: 集計は件数に比例して遅くならないよう、時刻の範囲で絞って数える。一覧は件数の上限で切る
- 記録の文字列に HTML の特殊文字が入っている（リポジトリ名・失敗の理由など）: 表示の前に必ずエスケープする
- `GET` 以外で開く: 受け付けない

## Requirements *(mandatory)*

### Functional Requirements

**表示と集計**

- **FR-001**: 状況ページは、今月の LLM 呼び出しの件数・月の上限・残り・受付停止の有無を表示しなければならない。月の上限と月の区切りは予算ゲートと同じ値を使う
- **FR-002**: 今月の LLM 呼び出しについて、役割別・モデル別・ジョブに属するもの／属さないものの件数、入力・出力トークンの合計、失敗の種類別の件数を表示しなければならない
- **FR-003**: 成功率を、今月終わったジョブ（`deployed`・`rolled_back`・`failed`）のうち `deployed` の割合として表示しなければならない。分子と分母の件数も出し、失敗の理由ごとの件数を出す
- **FR-004**: 平均処理時間を、今月終わったジョブの開始から終わりまでの時間の平均と中央値として表示しなければならない
- **FR-005**: CI 初回通過率を、今月 CI の最初の結論が記録されたジョブのうち、1回目の結論が成功だった割合として表示しなければならない
- **FR-006**: デプロイ成功率を、今月終わったデプロイのうち成功の割合として表示し、ロールバックした件数を出さなければならない。ジョブに結び付かないデプロイも含める
- **FR-007**: 分母が 0 の率は「データなし」とし、0 で割ってはならない
- **FR-008**: 最近のジョブ・工程の実行・デプロイを、新しい順に、種類ごとに決まった件数まで一覧で表示しなければならない
- **FR-009**: 終わっていない工程の実行は「実行中」として出さなければならない

**出してはいけないもの**

- **FR-010**: 依頼の本文、工程・デプロイ・LLM 呼び出しのエラー文、軌跡の中身と軌跡のファイルの場所、設定ファイルのパス・秘密の値を、応答に含めてはならない
- **FR-011**: 記録から取り出した文字列は、HTML に出す前にすべてエスケープしなければならない
- **FR-012**: 状況ページは LLM を呼んではならず、データベースへの書き込みもしてはならない（読むだけ）

**形式**

- **FR-013**: 既定は HTML の1ページとし、スクリプトなしで読めなければならない
- **FR-014**: 形式を指定すると、同じ内容を決まったスキーマの JSON で返さなければならない。知らない形式の指定は HTML として扱う
- **FR-015**: 応答には、キャッシュ禁止・他のサイトへの埋め込み禁止・スクリプトと外部の読み込みを許さない指定を付けなければならない

**公開と認証**

- **FR-016**: 公開のドメインでは、前段の Web サーバーが認証を通った要求だけを状況ページに転送しなければならない。パスワードは平文で置かず、ハッシュだけを配備の設定に置く
- **FR-017**: 認証の設定（利用者名とパスワードのハッシュ）がない配備では、前段の Web サーバーは状況ページに 404 を返さなければならない
- **FR-018**: 配備の手順書に、認証のハッシュの作り方と設定の置き場所、確かめ方（認証なしで 401、正しい認証で 200）を書かなければならない
- **FR-019**: データベースが読めないときは 500 を返し、本文に内部の情報を含めてはならない。原因はログに残す

### Key Entities

- **状況の要約**: ある時点で計算した、今月の集計値（消費・成功率・処理時間・CI 初回通過率・デプロイ成功率）と最近の一覧をまとめたもの。保存はせず、要求のたびに記録から計算する
- **率**: 分子・分母・割合（分母 0 なら割合なし）の組
- **一覧の行**: ジョブ・工程の実行・デプロイの要約の1行。表示してよい列だけを持つ

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 運用者は、ブラウザで1ページを開くだけで、`03` 7章の5つの数値をすべて確かめられる（VPS へのログインや SQL を書く必要がない）
- **SC-002**: 画面と JSON の数値は、同じ記録に対して手で SQL を書いて数えた値と一致する（テストで、用意した記録の全項目が一致する）
- **SC-003**: 記録が1か月分（ジョブ数百件・LLM 呼び出し 3,000 件程度）あっても、ページは1秒以内に返る
- **SC-004**: 依頼の本文・エラー文・軌跡の場所に入れた目印の文字列が、HTML と JSON のどちらの応答にも1件も現れない
- **SC-005**: 公開のドメインでは、認証なしの要求に中身が1件も返らない（予行演習の配備で確かめる）
- **SC-006**: ページを何回開いても、LLM の呼び出し件数と予算の消費は増えない

## Assumptions

- 表示に使う記録は 002〜010 ですでに残っている（呼び出し・ジョブ・ジョブのイベント・工程の実行・デプロイ・予算）。この機能で新しい記録は足さない
- 認証は前段の Web サーバー（006 の Caddy）の基本認証で行う。ファクトリー本体はループバックでだけ待ち受けているので、本体の側では認証しない
- 利用者は運用者1人。複数の利用者や権限の区別は扱わない
- 自動更新・グラフ・期間の切り替えは扱わない（必要になったら足す）。月をまたいだ比較は SQL か回帰評価で行う
- 「CI の最初の結論」は、009 がジョブのイベントに残している CI の結果の記録のうち、1回目のものを使う
- 処理時間は、ジョブの開始時刻（Worker が取り出した時刻）から終わりの時刻まで。人間が Draft PR をマージするまでの待ちも含まれる（画面に注記する）
