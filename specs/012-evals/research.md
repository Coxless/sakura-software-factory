# Research: 回帰評価（evals）

## R1. 成功の定義と隠しチェック

- **Decision**: ケースの成功 = 工程（005）が `passed` ＋ 合格条件のコマンドがすべて終了コード 0。合格条件は「隠しのファイル（`hidden/` の下を作業ディレクトリの同じ相対パスに置く）」と「作業場で順に実行するコマンド」の組。工程の終わり方によらず、作業場が使える限り隠しチェックは実行して記録する
- **Rationale**: 検査役の合格だけでは、検査役の甘さが成功率に混ざり、検査役の比較の正解に使えない。工程が不合格でも隠しチェックを回すと、「検査役が誤って不合格にした」件数が数えられる
- **Alternatives**: 検査役の合格だけ（上記の理由で不採用）。人が採点する（再現性がなく、記事の数値にならない）。LLM に採点させる（さらにリクエストを食い、検査役の比較の正解として循環する）

## R2. 対象のプロジェクトと初期状態

- **Decision**: 共有の小さなプロジェクト `evals/projects/inventory`（依存なし。テストは `node --test`、lint は自前の `scripts/lint.ts`）を1つ置き、ケースごとの初期状態は `setup/` の重ね合わせで作る。複製したら `git init` → 全ファイルを1コミット（作者は評価用の固定の名前）にして、005 の diff の基準にする
- **Rationale**: 作業場のイメージ（node:24-slim ＋ git・pnpm）だけで lint・テストが動き、依存のインストールが要らない（ネットワークなし・速い）。Node 24 は `.ts` を型除去で直接実行できる。ケースごとにプロジェクトを丸ごと持つより重複が少なく、lint 解消のケースのように「初期状態が他と違う」ものも `setup/` で表せる
- **Alternatives**: 外部の公開リポジトリを clone（ネットワーク依存・版の固定が要る）。ケースごとに別のプロジェクト（重複が多い）。pnpm で Biome・tsc を入れる（インストールに時間とネットワークが要る。ケースに `install` を書けば将来は可能にしておく）

## R3. 隠しのファイルを工程から隠す

- **Decision**: `hidden/` は工程が終わるまで作業ディレクトリに置かない（ホストの `evals/cases/<id>/hidden` にだけある）。対象のプロジェクトの複製には `evals/cases` を含めない。工程のあとに、同名のファイルを上書きして置く
- **Rationale**: 作業場は `--network none` で作業ディレクトリしか見えないので、置かなければ実装役は読めない。ファイル一覧（計画役）・diff（検査役）にも現れない。上書きで、実装役が同じ名前のファイルを作って合格条件を変える抜け道をふさぐ
- **Alternatives**: 作業ディレクトリに置いて書き込み禁止のガードで守る（読めてしまう。ガードはやわらかい層）

## R4. 工程内テストのコマンド

- **Decision**: ケースの `check_commands` で評価の実行の間だけ `[pipeline].check_commands` を差し替える（設定のコピーに上書き）。既定は `["node --test \"test/**/*.test.ts\"", "node scripts/lint.ts"]` を各ケースに書く
- **Rationale**: 005 の方針（コマンドは対象リポジトリのファイルから読まない）を保ったまま、評価の対象のプロジェクトに合うコマンドにできる。`pnpm run check` は対象のプロジェクトにない

## R5. 比較用の検査役の呼び方と記録

- **Decision**: 005 の `runPipeline` の結果に `lastJudge`（最後に検査役へ渡した diff とテスト結果の要約）を足す。評価の実行器は、工程のあとに `judge(..., { alt: true })` を同じ Issue・依頼の本文・計画の文章と `lastJudge` で1回呼ぶ。`runOneShot` に `modelRole`（既定は `role`）を足し、比較用は `modelRole: "verifier_alt"`・`role: "verifier"`・`phase: "judge_alt"` で呼ぶ
- **Rationale**: `llm_calls.role` は CHECK 制約で planner / implementer / verifier に限られるので、役割は `verifier` のまま、工程名 `judge_alt` で主の判定と区別する（`phase` は CHECK なし）。`agent_runs` の一意制約（job, phase, attempt）にもぶつからない。`completeOnce` は既に `verifier_alt` を `ModelRole` として受け付ける。実装を2回回さないので追加の消費は1〜2リクエスト（`03` 7章「同じジョブの判定工程だけを両方で実行」）
- **Alternatives**: 検査役のモデルを変えて評価全体を2回回す（実装役のばらつきが混ざり、消費が倍）。軌跡から入力を復元して後で比べる（復元の手間。実行器の中で呼べば十分）

## R6. 検査役の正解との突き合わせ

- **Decision**: 正解は隠しチェックの結果（通った → pass が正しい）。主の検査役は「最後の判定」の合否を使う。分母に入れるのは、(a) 判定まで進み、(b) 最後の回が判定された（`lastJudge.diff` が最後の diff と同じ）、(c) 隠しチェックを実行できた、ケースだけ。比較用は同じ集合で、判定できなかった（形が合わない・失敗）ものは「判定できない」として数え、一致率の分母には入れる
- **Rationale**: 最後の回がテスト失敗などで判定されなかった場合、検査役が見た diff と隠しチェックの対象がずれる。判定できないのは検査役の弱点として一致率に効かせる
- **Alternatives**: 判定できないを分母から外す（形の崩れやすいモデルが有利に見える）

## R7. 評価全体のリクエスト上限

- **Decision**: `--max-requests N`（既定は ケース数 × 回数 × `per_job_requests`）。各ケースを始める前に「使った量」を数え、残りが 0 ならそれ以降を `not_run`。ケースの設定のコピーで `[budget].per_job_requests` を `min(per_job_requests, 残り)` に下げる（比較用の判定も同じジョブなので含まれる）。ケースが `budget_exceeded` で終わったら、ジョブの消費が1ジョブの上限に達していればそのケースだけの予算切れ（残りの上限が尽きていれば止める）、達していなければ月の予算切れとみなして止める
- 各ケースの前に `canAcceptNewJob`（`src/llm/budget.ts`）を、下げた1ジョブの上限の設定で呼び、受け付けられなければ LLM を呼ばずに `stopped = "budget_exceeded"`・残りを `not_run`（原則 V の「月の残りが1ジョブの上限を下回ったら新しいジョブを受け付けない」。評価は受付〔007 の webhook〕を通らないため）
- **Rationale**: 既存の予算ゲートの仕組み（1ジョブの上限）だけで評価全体の上限が守れる。月の予算は 002 のゲートがそのまま効く。受付の確認は、そのケースで実際に使いうる量（下げた上限）で行えば、原則の意図（1ジョブを途中で予算切れにしない）を保てる
- **Alternatives**: 予算ゲートに評価用の上限を足す（002 の変更が要る）

## R8. 結果のファイルと直前の実行

- **Decision**: 1実行1ファイル `<eval_dir>/<YYYYMMDDTHHmmssZ>-<setName>.json`。`setName` は評価のセットのディレクトリ名（既定 `evals`）。比較の相手は、指定がなければ同じ `setName` で開始時刻が今回より前の最新のファイル（壊れたファイルは警告して飛ばす）。ケースごとに内容のハッシュ（`case.toml`・`issue.md`・`setup/`・`hidden/` とプロジェクト）を残し、比較でハッシュが違うケースを「ケースが変わった」と示す。ハーネスの版は `git rev-parse HEAD` と作業ツリーの変更の有無
- **Rationale**: ファイルなら記事の材料として選んで残せ、DB のスキーマ変更が要らない。ハッシュで「ケースを直したせいで変わった」と「ハーネスで変わった」を見分けられる
- **Alternatives**: SQLite に評価のテーブルを足す（マイグレーションが要る。集計はファイルで足りる）

## R9. 成功率と回数

- **Decision**: `--repeat N` で各ケースを N 回。結果は (ケース, 回) ごと。成功率 = 成功の件数 ÷ 実行した件数（未実行・実行できないを含めない。実行できないは別に数える）
- **Rationale**: 実行できない（作業場の異常）はハーネスの良し悪しではないので、成功率から外して別に示す

## R10. 終了コード

- **Decision**: `eval:dev`: 0 = 全件を実行した（成否は問わない）、2 = 実行前の誤り（引数・設定・セット・さくらの拒否）、3 = 途中で止まった（上限・予算・中断。未実行あり）。`--self-check`: 0 = すべてのケースで成り立つ、1 = 成り立たないケースあり、2 = 実行前の誤り。`eval:compare`: 0 = 比較を表示した、2 = 読めない
- **Rationale**: 成功率の上下は数値で見るもので、終了コードで失敗扱いにすると評価を回す運用が面倒になる。止まったかどうかは自動化で見分けたい

## R11. 自己確認（模範解答）

- **Decision**: `pnpm run eval:dev -- --self-check`。LLM・APIキー・DB を使わない。ケースごとに「(1) 準備した状態で工程内テストのコマンドを実行（記録だけ）、(2) 隠しチェックが落ちる、(3) `solution/` を重ねると工程内テストと隠しチェックが通る」を確かめる。同じ関数を `selfcheck.docker.test.ts` から呼ぶ
- **Rationale**: 合格条件が「Issue を解かないと通らない」ことを保証しないと、成功率が意味を持たない

## R12. 実装中に確かめる事実
