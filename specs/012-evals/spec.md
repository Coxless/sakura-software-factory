**Feature Branch**: `012-evals`

**Created**: 2026-11-14

**Status**: Draft

**Input**: User description: "012 evals 回帰評価。範囲: evals/ のサンプル Issue と合格条件、判定工程で止める実行器、前回との比較、検査役 Qwen3.6 と gemma-4 の比較。依存: 005（local-pipeline の CLI の上に乗る）。関係する設計: docs/design/04 4章、02 6章。AI解禁前なので偽の LLM で作り、実機の評価は12月の枠で行う。"

## Clarifications

### Session 2026-11-14

ユーザーの指示（人間の判断が要る項目は推奨の内容で進め、PR に書く）により、以下は推奨の回答で決めた。

- Q: 評価の「成功」を何で決めるか？ → A: 工程が「合格」で終わり、かつ、ケースごとの隠しチェック（評価用に用意したテストやコマンド。実装役・検査役には見せない）が通ったときだけ成功とする（推奨）。検査役の合格だけを成功にすると、検査役の甘さが成功率に混ざり、検査役の比較の正解にも使えないため
- Q: サンプル Issue の対象リポジトリはどこに置くか？ → A: 本リポジトリの `evals/` の中に、ケースごとの小さなプロジェクト（または共有の小さなプロジェクト）をファイルとして置き、実行のたびに一時ディレクトリへ複製して git の作業ツリーにする（推奨）。外部のリポジトリに依存せず、公開してよいデータだけになり、Google AI Studio に送ってよい（原則 I の例外の条件）
- Q: 評価のセットの大きさは？ → A: 作業の種類（test・bugfix・lint 解消・docs・refactor）ごとに1件、合計5件から始める（推奨）。1件あたり20〜50リクエストの見積もり（`02` 2章）で、全件1回が100〜250リクエスト。12月の枠 3,000 のうち評価に回せる量で数回実行できる大きさにする
- Q: 検査役の比較はどう行うか？ → A: 各ケースの最後の判定と同じ入力（Issue・計画・diff・テスト結果）を、比較用の検査役にも1回渡して判定させ、主の検査役の判定・隠しチェックの結果と並べて記録する（推奨）。`03` 7章「同じジョブの判定工程だけを両方で実行して記録する」に合わせる。実装を2回回さないので、比較の追加の消費は1ケースあたり1〜2リクエストで済む
- Q: 結果はどこに残し、何と比べるか？ → A: 実行ごとの結果を、機械が読める形のファイルとして評価の結果のディレクトリに1つずつ残し、指定がなければ同じ評価のセットの直前の実行と比べる（推奨）。比べる相手は指定もできる。結果のファイルには diff の本文を入れず（軌跡を参照する）、記事に使う集計値を入れる
- Q: 評価の実行で予算をどう守るか？ → A: 評価の実行全体のリクエスト上限を指定でき（既定は「ケース数 × 1ジョブの上限」を超えない値）、1ケースずつ予算ゲートを通し、上限か予算切れに当たったら残りのケースを「未実行」として止める（推奨）。月の予算ゲート（002）も通常どおり効く
- Q: 対象を指定した一部のケースだけを実行できるか？ → A: できる（ケース ID で絞る）（推奨）。ハーネスの一部を変えたときに、関係するケースだけを安く確かめるため。ただし前回との比較は、両方の実行に含まれるケースだけで行う

## User Scenarios & Testing *(mandatory)*

この機能の利用者は、ファクトリーの開発者（ハーネスを直す人・記事を書く人）である。ハーネス（プロンプト・ツール・ガード・コンテキスト管理）を変えたときに評価を回し、成功率・消費リクエスト数・処理時間が前回からどう変わったかを見る。12月の枠では、検査役のモデルの比較の結果を記事の徹底検証パートに使う。

### User Story 1 - サンプル Issue と合格条件を評価のセットとして持つ (Priority: P1)

開発者は、`evals/` に作業の種類ごとのサンプル Issue を置く。1件のケースは、対象のプロジェクト・Issue 文・作業の種類・合格条件（隠しチェック）からなり、決まった形で書かれている。評価を回す前に、セットの形が正しいかを検証できる。

**Why this priority**: 評価の入力そのもの。これがないと実行器も比較も作れない。

**Independent Test**: 正しい形のセット・項目が欠けたケース・存在しない対象を指すケース・ID が重複するケースを読み込ませ、正しいものは読めて、誤りはケースと理由つきで拒まれることを確かめる。

**Acceptance Scenarios**:

1. **Given** `evals/` に5件のケース（test・bugfix・lint・docs・refactor）、**When** セットを読み込む、**Then** 5件が ID・作業の種類・Issue 文・対象・合格条件つきで得られる
2. **Given** 合格条件（隠しチェック）のないケース、**When** セットを読み込む、**Then** そのケースの ID と「合格条件がない」理由を示して読み込みを拒む
3. **Given** ID が重複する2件、**When** セットを読み込む、**Then** 重複を示して拒む
4. **Given** 正しいセット、**When** 各ケースの対象のプロジェクトに手を加えずに隠しチェックだけを実行する、**Then** 隠しチェックが失敗する（Issue を解かなければ通らない合格条件であることを確かめられる）
5. **Given** 正しいセット、**When** 各ケースの対象のプロジェクトに用意済みの模範解答を当てて隠しチェックを実行する、**Then** 隠しチェックが通る

---

### User Story 2 - 判定工程で止める実行器で全件を回す (Priority: P1)

開発者がコマンドを1回実行すると、評価のセットの各ケースについて、対象のプロジェクトを一時ディレクトリに複製し、005 の工程（計画から判定まで）を1回通し、判定のあとに隠しチェックを実行して、ケースの成功・失敗を決める。commit・push・PR・CI・マージ・デプロイは行わない。全件が終わると、ケースごとの結果と全体の集計（成功率・消費リクエスト数・処理時間）が表示され、ファイルに残る。

**Why this priority**: 原則（開発ワークフロー）「ハーネスを変えたら回帰評価を実行し、判定工程までで止める」そのもの。

**Independent Test**: 偽の LLM と偽の作業場で、「工程が合格して隠しチェックも通る」「工程は合格したが隠しチェックが落ちる」「工程が不合格」「工程が失敗」の各ケースを含むセットを回し、ケースごとの結果・集計・出荷の工程が呼ばれないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 工程が合格し隠しチェックも通るケース、**When** 評価を回す、**Then** そのケースは「成功」になり、消費リクエスト数・処理時間・やり直し回数が記録される
2. **Given** 工程は合格したが隠しチェックが落ちるケース、**When** 評価を回す、**Then** そのケースは「失敗（隠しチェック）」になり、検査役が誤って合格させたことが分かる形で記録される
3. **Given** 工程が不合格・失敗・時間切れで終わるケース、**When** 評価を回す、**Then** そのケースは工程の終わり方つきで「失敗」になり、隠しチェックは実行するが成功にはしない（検査役の比較の正解に使うため結果は記録する）
4. **Given** 評価の実行、**When** 1ケースが終わる、**Then** そのケースの作業場は片付けられ、次のケースは新しい複製から始まる（前のケースの変更が持ち越されない）
5. **Given** 評価の実行、**When** どのケースでも、**Then** commit・push・PR の作成・GitHub の呼び出しは1回も起きない
6. **Given** 隠しチェックのファイル、**When** 工程（計画・実装・判定）が動いている間、**Then** 隠しチェックのファイルは作業ディレクトリに存在せず、計画役・実装役・検査役の入力に現れない
7. **Given** 1ケースで予期しない異常（作業場を作れない等）、**When** 評価を回す、**Then** そのケースを「失敗（実行できない）」にして、残りのケースを続ける
8. **Given** ケース ID を指定、**When** 評価を回す、**Then** 指定したケースだけを実行する
9. **Given** 提供元が さくらの設定、**When** 明示の指定なしに評価を回す、**Then** LLM を呼ばずに実行を拒む

### User Story 3 - 前回の評価と比べる (Priority: P1)

評価が終わると、開発者は、同じ評価のセットの直前の実行（または指定した実行）と比べて、成功率・消費リクエスト数・処理時間の増減と、成功から失敗に変わったケース・失敗から成功に変わったケースを見られる。比べた相手の実行がどのハーネス・モデルの設定だったかも分かる。

**Why this priority**: `04` 4章「ハーネスを変えるたびに全件を実行し、前回と比べる」。記事の「どのハーネス変更が、どれだけ効いたか」の材料。

**Independent Test**: 結果のファイルを2つ用意して比較を実行し、増減・変化したケース・共通でないケースの扱いを確かめる。

**Acceptance Scenarios**:

1. **Given** 前回の結果があり、今回の成功率が上がった、**When** 比較を表示する、**Then** 成功率・合計と平均のリクエスト数・平均処理時間の、前回の値・今回の値・差が表示される
2. **Given** 前回成功して今回失敗したケース、**When** 比較を表示する、**Then** そのケースが「後退」として ID と今回の失敗の理由つきで挙がる
3. **Given** 前回失敗して今回成功したケース、**When** 比較を表示する、**Then** そのケースが「改善」として挙がる
4. **Given** 前回と今回で実行したケースが一部違う、**When** 比較する、**Then** 両方に含まれるケースだけで集計を比べ、片方にしかないケースは別に示す
5. **Given** 前回の結果がない（初回）、**When** 評価を終える、**Then** 比較は表示せず、今回の結果を残す
6. **Given** 前回と今回でモデルの設定やハーネスの版（コミット）が違う、**When** 比較を表示する、**Then** 違う項目が並べて示される
7. **Given** 結果のファイルを2つ指定、**When** 比較のコマンドを実行する、**Then** LLM を呼ばずに比較だけを表示する

---

### User Story 4 - 検査役のモデルを比べる (Priority: P2)

開発者は、比較用の検査役のモデル（例: 主が Qwen3.6、比較用が gemma-4）を設定して評価を回す。各ケースで最後に主の検査役が判定した入力と同じものを、比較用の検査役にも判定させ、両者の合否・隠しチェックの結果・消費（リクエスト数・トークン数・応答時間）を並べて見られる。正解（隠しチェック）との一致率で、どちらの検査役がよく判定できたかが分かる。

**Why this priority**: `01` 5章「同じIssueで判定精度とトークン消費を比較して決める」、`02` 6章の検証の材料。ただし実装計画の「遅れたときに削る順番」で2番目なので P2。

**Independent Test**: 偽の LLM で、主と比較用の検査役に異なる判定を返させ、両方の判定・一致率・消費が記録されること、比較用の検査役の判定が工程の結果（ケースの成功・失敗）を変えないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 比較用の検査役のモデルが設定されている、**When** 評価を回す、**Then** 判定まで進んだ各ケースで、主の検査役の最後の判定と同じ入力が比較用の検査役に1回渡され、両方の合否が記録される
2. **Given** 主が合格、比較用が不合格、隠しチェックが通った、**When** 結果を見る、**Then** そのケースでは主が正解、比較用が不正解として数えられる
3. **Given** 全件の評価が終わる、**When** 集計を見る、**Then** 検査役ごとに、隠しチェックとの一致率・誤って合格させた件数・誤って不合格にした件数・1回の判定あたりの平均トークン数と応答時間が表示される
4. **Given** 比較用の検査役の判定、**When** ケースの成功・失敗を決める、**Then** 比較用の判定は使わない（工程の流れもケースの結果も変わらない）
5. **Given** 判定まで進まなかったケース（テスト失敗・変更なし等）、**When** 評価を回す、**Then** 比較用の検査役は呼ばず、「判定なし」として集計から外す
6. **Given** 比較用の検査役のモデルが実装役と同じ設定、**When** 評価を始める、**Then** LLM を呼ぶ前に拒む（原則 III）
7. **Given** 比較用の検査役の出力が2回とも形に合わない、**When** 評価を回す、**Then** そのケースの比較用の判定を「判定できない」として記録し、ケースの結果と残りのケースは続ける
8. **Given** 比較用の検査役のモデルが設定されていない、**When** 評価を回す、**Then** 比較を行わず、消費も増えない

---

### User Story 5 - 予算の中で評価を回す (Priority: P2)

開発者は、評価の実行全体で使ってよいリクエスト数の上限を指定して評価を回す。上限に当たる・月の予算が尽きる・中断する、のどれかで止まったら、そこまでの結果を残し、残りのケースを「未実行」として示す。実行前に、セットの件数と上限から見積もりを表示する。

**Why this priority**: `04` 4章「月3,000の枠を食うため、実行回数も予算に入れて計画する」。原則 V の予算ゲートは 002 で効いているので、評価の側では上限と途中停止の扱いだけを足す。

**Independent Test**: 偽の LLM で、実行の上限を小さくしたとき・予算ゲートが途中で止めたとき・中断したときに、止まる位置と残りのケースの扱い・結果のファイルを確かめる。

**Acceptance Scenarios**:

1. **Given** 実行の上限を指定、**When** 評価を始める、**Then** ケース数・上限・1ジョブの上限から見積もった最大の消費を表示してから始める
2. **Given** 実行の上限に途中で達する、**When** 評価を回す、**Then** 実行中のケースは上限で止まり（予算切れとして記録）、残りのケースは「未実行」になり、結果のファイルは残る
3. **Given** 月の予算ゲートが途中で止める、**When** 評価を回す、**Then** 同じく残りを「未実行」にして止まる
4. **Given** 評価の途中で中断（Ctrl-C）、**When** 評価が止まる、**Then** 実行中のケースの作業場を片付け、そこまでの結果を「中断」として残す
5. **Given** 未実行のケースを含む結果、**When** 次回と比べる、**Then** 未実行のケースは比較の集計から外す

---

### Edge Cases

- ケースの対象のプロジェクトが依存のインストールを必要とする → ケースにインストールのコマンドを書けるようにし、005 の CLI と同じくネットワークありの一時コンテナで1回だけ実行する。インストールに失敗したら「失敗（実行できない）」
- 隠しチェックが時間の上限を超える → 打ち切って隠しチェックの失敗として扱う
- 隠しチェックの実行が作業場の異常で起動できない → 「失敗（実行できない）」とし、検査役の比較の集計からも外す
- 実装役が隠しチェックと同じ名前のファイルを作っていた → 隠しチェックのファイルで上書きしてから実行する（実装役のファイルで合格条件を変えられないようにする）
- 隠しチェックの結果を見て、検査役が合格・不合格のどちらでもない（判定に至らなかった）→ 検査役の一致率の分母に入れない
- 結果のディレクトリに壊れた結果のファイルがある → 比較の相手を探すときは読み飛ばし、警告を出す
- 評価のセットが空、または指定したケース ID がどれも存在しない → LLM を呼ばずに拒む
- 同じケースを何度も回したい（ばらつきを見るため）→ 回数を指定できる。結果は回ごとに記録し、ケースの成功率は回数で割った値にする
- 秘密情報らしい文字列がログや出力に出る → 結果のファイルと表示に書く前に伏せる（005 と同じマスク）
- 開発用の設定（Google AI Studio）で評価を回す → 公開してよいデータだけであることを表示で知らせる。評価のケースは本リポジトリの公開データだけで作る
- 比較用の検査役で予算切れ → 比較用の判定を「予算切れ」として記録し、評価全体を止める（予算の扱いは主の工程と同じ）

## Requirements *(mandatory)*

### Functional Requirements

**評価のセット**

- **FR-001**: 評価のケースは `evals/` に置き、1件ごとに ID・作業の種類・Issue 文（タイトルと本文）・対象のプロジェクト・合格条件（隠しチェック）・任意の依頼の本文・任意のインストールのコマンドを決まった形で持たなければならない。形はスキーマで検証する
- **FR-002**: 作業の種類は 005 の計画の作業の種類の一覧（bugfix・test・docs・refactor・feature・chore）のどれかとし、lint 解消は refactor か chore として扱う。最初のセットは test・bugfix・lint 解消・docs・refactor をそれぞれ1件以上含めなければならない
- **FR-003**: 合格条件は、作業場の中で実行するコマンドと、実行の前に作業ディレクトリへ置く隠しのファイル（テストなど）の組とし、すべてのコマンドが終了コード 0 で終わったときに満たしたとする
- **FR-004**: 各ケースに模範解答（対象のプロジェクトへの変更）を置き、「何もしなければ隠しチェックが落ち、模範解答を当てれば通る」ことを、LLM を使わずに確かめられなければならない
- **FR-005**: セットの読み込みで、形の誤り・ID の重複・存在しない対象や隠しのファイルを、ケースの ID と理由つきで拒まなければならない
- **FR-006**: ケースは本リポジトリの公開データだけで作らなければならない（開発用の LLM に送ってよい条件。原則 I）

**実行器**

- **FR-007**: 開発者が、評価のセット（既定は `evals/`）・ケース ID の絞り込み（任意）・回数（任意。既定1）・実行のリクエスト上限（任意）・比較の相手（任意）を指定して、評価を1回のコマンドで実行できなければならない
- **FR-008**: 各ケースは、対象のプロジェクトを一時ディレクトリに複製して git の作業ツリーにし、作業場を用意して、005 の計画から判定までの入口を1回実行しなければならない。工程の上限（やり直し・ターン数・期限）は設定の値を使う
- **FR-009**: 評価は判定で止め、commit・push・PR の作成・CI・マージ・デプロイ・GitHub の呼び出しをしてはならない
- **FR-010**: 隠しのファイルは、工程が終わるまで作業ディレクトリに置かず、計画役・実装役・検査役のどの入力にも含めてはならない
- **FR-011**: 工程が終わったら（終わり方によらず、作業場が使える限り）、隠しのファイルを作業ディレクトリに置いて（同名のファイルは上書きして）、合格条件のコマンドを作業場の中で実行し、結果（コマンドごとの終了コード・時間・切り詰めたログ）を記録しなければならない。LLM は使わない
- **FR-012**: ケースは、工程が「合格」で終わり、かつ合格条件をすべて満たしたときだけ「成功」とし、それ以外は理由（工程の終わり方、または隠しチェックの失敗）つきで「失敗」としなければならない
- **FR-013**: 1ケースが終わるごとに作業場を片付け、次のケースは新しい複製から始めなければならない
- **FR-014**: 1ケースの予期しない異常は「失敗（実行できない）」として記録し、評価の実行を止めずに次のケースへ進まなければならない
- **FR-015**: ケースごとに、評価用のジョブを記録に作り、そのジョブの ID でリクエスト数を数え、軌跡を残さなければならない（005 と同じ予算ゲート・軌跡）
- **FR-016**: 提供元が さくらの設定では、明示の指定がない限り、LLM を呼ぶ前に評価を拒まなければならない（005 の CLI と同じ）。開発用の設定のときは、公開してよいデータだけを送ることを表示で知らせなければならない

**結果と比較**

- **FR-017**: 評価の実行ごとに、実行の識別子・開始と終了の時刻・評価のセットの識別・ハーネスの版（コミット）・モデルの設定（計画役・実装役・検査役・比較用の検査役）・提供元・各ケースの結果・全体の集計を、機械が読める形のファイルとして結果のディレクトリに1つ残さなければならない
- **FR-018**: ケースの結果は、ケース ID・作業の種類・回・成功か失敗か・失敗の理由・工程の終わり方・やり直しの回数・リクエスト数・処理時間・diff の要約（ファイル数・行数）・隠しチェックの結果・主の検査役の最後の判定・比較用の検査役の判定（あれば）・軌跡の場所を含まなければならない。diff の本文は含めない
- **FR-019**: 全体の集計は、成功率（成功の件数 ÷ 実行した件数）・作業の種類ごとの成功率・合計と1ケースあたり平均のリクエスト数・1ケースあたり平均の処理時間・未実行の件数を含まなければならない
- **FR-020**: 評価を終えたら、比較の相手（指定がなければ、結果のディレクトリにある同じ評価のセットの直前の実行）と比べて、集計の前回・今回・差と、後退したケース・改善したケースを表示しなければならない。相手がなければ比較を表示しない
- **FR-021**: 比較は、両方の実行で実行したケースだけで集計し、片方にしかない・未実行のケースは別に示さなければならない
- **FR-022**: 比較では、両方の実行のモデルの設定とハーネスの版が違えば、その違いを示さなければならない
- **FR-023**: 結果のファイルを2つ指定して、LLM を呼ばずに比較だけを表示するコマンドを提供しなければならない
- **FR-024**: 結果は人が読む表示と機械が読む形の両方で出せ、評価の成否（すべて実行できたか、止まったか）を終了コードで区別しなければならない

**検査役の比較**

- **FR-025**: 設定に比較用の検査役のモデルがあるときは、判定まで進んだ各ケースで、主の検査役の最後の判定に渡したものと同じ入力（Issue・依頼の本文・計画・diff・テスト結果）で、比較用の検査役を1回（形が合わなければ再要求1回まで）呼ばなければならない
- **FR-026**: 比較用の検査役の呼び出しは、予算ゲートを通し、主の判定と区別できる工程の名前で記録しなければならない。比較用の判定は、ケースの成功・失敗にも工程の流れにも使ってはならない
- **FR-027**: 比較用の検査役のモデル名が実装役と同じ設定では、LLM を呼ぶ前に評価を拒まなければならない
- **FR-028**: 検査役ごとに、隠しチェックの結果を正解とした一致率・誤って合格させた件数・誤って不合格にした件数・判定できなかった件数・1回の判定あたりの平均の入力と出力のトークン数・平均の応答時間を集計しなければならない。判定まで進まなかったケース・隠しチェックを実行できなかったケースは分母に入れない
- **FR-029**: 比較用の検査役のモデルが設定されていないときは、比較を行わず、比較用の呼び出しを1回もしてはならない

**予算と停止**

- **FR-030**: 評価の実行全体のリクエスト上限を指定でき、上限に当たったら実行中のケースを止め（予算切れとして記録）、残りのケースを「未実行」にして評価を終えなければならない
- **FR-031**: 評価を始める前に、実行するケース数・回数・実行の上限・1ジョブの上限から見積もった最大の消費を表示しなければならない
- **FR-032**: 月の予算ゲートが止めたとき・中断されたときも、実行中のケースの作業場を片付け、そこまでの結果を残して、残りを「未実行」にしなければならない

**テスト**

- **FR-033**: セットの読み込み・実行器・成功の判定・比較・検査役の比較・予算と停止は、偽の LLM と偽の作業場を使った自動テストで確かめられなければならない。自動テストで実際の LLM を呼んではならない
- **FR-034**: 「何もしなければ隠しチェックが落ち、模範解答を当てれば通る」ことの確認（FR-004）は、作業場（コンテナ）を使う確認として、手動または Docker のあるテストで実行できなければならない

### Key Entities *(include if feature involves data)*

- **評価のセット**: 評価のケースの集まり。識別（ディレクトリと内容から決まる）を持つ
- **評価のケース**: ID、作業の種類、Issue 文、依頼の本文（任意）、対象のプロジェクト、インストールのコマンド（任意）、合格条件（隠しのファイルとコマンド）、模範解答
- **評価の実行**: 識別子、時刻、セットの識別、ハーネスの版、モデルの設定、提供元、実行の上限、ケースの結果の列、集計、止まった理由（あれば）
- **ケースの結果**: ケース ID、回、成功・失敗・未実行、理由、工程の終わり方、やり直し、リクエスト数、処理時間、diff の要約、隠しチェックの結果、主と比較用の検査役の判定、軌跡の場所
- **比較**: 2つの実行の集計の差、後退・改善したケース、共通でないケース、設定の違い
- **検査役の比較の集計**: 検査役ごとの一致率、誤合格・誤不合格・判定できない件数、平均トークン数、平均応答時間

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 開発者がコマンド1回で、評価のセット全件（最初は5件）を回し、ケースごとの結果・全体の集計・前回との比較を見られる
- **SC-002**: 評価の実行で、commit・push・PR 作成・GitHub の呼び出しが 0 件
- **SC-003**: 工程（計画役・実装役・検査役）の入力に、隠しのファイルの内容が現れた回数が 0 件（軌跡で確かめる）
- **SC-004**: 最初のセットの全件で、「何もしなければ隠しチェックが落ち、模範解答を当てれば通る」が成り立つ（100%）
- **SC-005**: 偽の LLM の確認で、工程は合格したが隠しチェックが落ちるケースが「成功」に数えられた回数が 0 件
- **SC-006**: 比較用の検査役を設定しない実行で、比較用の呼び出しが 0 件。設定した実行で、比較用の呼び出しは判定まで進んだ1ケースあたり2回を超えない
- **SC-007**: 実行の上限を指定した確認で、評価全体の消費が上限を超えない（予算ゲートの記録で確かめる）
- **SC-008**: 結果のファイル2つから、LLM を呼ばずに比較を表示できる。後退・改善したケースの取りこぼしが 0 件
- **SC-009**: 秘密情報の形をした文字列をログに混ぜた確認で、結果のファイルと表示に平文が 1 件も現れない
- **SC-010**: 12月の枠で、全件1回の評価が 250 リクエスト以内に収まる見積もりを、実行前の表示で確かめられる（実機の確認は12月）

## Assumptions

- 計画から判定までの工程（005 の入口）・予算ゲート（002）・作業場（003）・軌跡（004）は完成済みのものを使う。比較用の検査役の判定のために、005 の判定の関数をモデル名と工程名を指定して呼べるようにする変更が要れば、本機能で足す
- 評価は開発機で手動で実行する。常駐するファクトリー（Worker）からは呼ばない。CI でも実行しない（LLM を呼ぶため）
- 最初の評価のセットの対象は、本リポジトリの `evals/` に置く小さな TypeScript のプロジェクトとし、作業場のイメージ（003）に入っているツールで lint・型チェック・テストを実行できるものにする。依存のインストールが要らない形を優先する（評価を速く、ネットワークに依存させないため）
- 工程内テストのコマンドは、評価の対象のプロジェクトに合わせて評価の側で決めた値を使う（設定の `[pipeline].check_commands` を評価の実行の間だけ差し替える）。対象のプロジェクトの中のファイルからは読まない（005 と同じ方針）
- 比較用の検査役のモデル名は `factory.toml` の `[models]` に任意の項目として置く（既にコメントで予約されている `verifier_alt`）
- 結果のディレクトリの既定は、設定のデータの置き場所（`[storage]`）の下とする。記事に使う結果は、開発者が必要なものを選んで残す
- AI解禁前は、偽の LLM の自動テストと、Google AI Studio の無償枠での手動の確認（公開データだけ）で作る。さくらでの評価と検査役の比較の実測は12月の枠（実装計画 3章）で行う
- 1ケースの処理時間は、工程の開始から隠しチェックの終了までの壁時計の時間とする（作業場の用意と片付けは含めない）
- ばらつきを見るための回数の指定はできるが、既定は1回とする（枠を食うため）
