## Clarifications

### Session 2026-11-08

- Q: 実装役のプレビューモデルが提供終了して「存在しないモデル」エラーが返ったとき、退避先モデルへ自動で切り替えるか？ → A: 自動で切り替えない。恒久的なエラーとして失敗させ、運用者が設定ファイルを直す
- Q: スモークテストで不合格が出たとき、Pi から TanStack AI へ切り替える判断基準は？ → A: 互換性の設定を変えて再確認し、それでも不合格なら同じ要求を Pi を通さない素の HTTP で送って比べる。素の HTTP では合格し Pi 経由では不合格のときだけ切り替える。両方不合格ならモデル側の問題として別のモデルを検討する
- Q: 月・ジョブの消費件数に、失敗したリクエストも数えるか？ → A: 成功・失敗・取り消しを問わず、LLM に送った全件を数える

## User Scenarios & Testing *(mandatory)*

この機能の利用者は3種類いる。

- **開発者**（本プロジェクトを作る人）: 後続の機能（004 実装役・005 計画役と検査役・012 回帰評価）から LLM を呼ぶ。自動テストでは本物の LLM を呼ばずに動作を確かめる
- **運用者**（VPS でファクトリーを動かす人）: 月の無償枠（3,000リクエスト）を使い切らないように、予算の上限で LLM 呼び出しが止まることを当てにする
- **意思決定者としての開発者**: さくらのAI Engine で実装役のツール呼び出しが安定するかを実機で確かめ、エージェント層を Pi のまま進めるか予備（TanStack AI）に切り替えるかを決める

### User Story 1 - さくらのAI Engine で実装役のツール呼び出しを実機で確かめる (Priority: P1)

開発者は1つのコマンドで、さくらのAI Engine の実装役モデル（Kimi-K2.7-Code）に対して、ツールなしの応答・ツール呼び出し・ツール結果を返したあとの続きの応答を実際に試す。結果は項目ごとの合否として表示され、ツール呼び出しが構造化された形で返るか（本文に XML などとして漏れていないか）が分かる。この結果で Pi を続けるか切り替えるかを判断する。

**Why this priority**: 実装計画の最大のリスク（`03` 6章）。結果次第でエージェント層の選定が変わり、004 以降の作り方がすべて変わるため、最初に確かめる。

**Independent Test**: APIキーを環境変数で渡してコマンドを実行し、各確認項目の合否と、使ったリクエスト数が表示されること、各呼び出しが LLM 呼び出しの記録（ジョブなし）に残ることを確かめる。

**Acceptance Scenarios**:

1. **Given** 有効なAPIキーと設定ファイル、**When** 開発者がスモークテストのコマンドを実行する、**Then** 次の項目それぞれの合否が表示される: (a) ツールなしでテキストの応答が返る、(b) ツールを渡すと、指定した名前と引数でツール呼び出しが構造化された形で返る、(c) ツールの引数がツールの引数の定義に合う、(d) ツールの結果を返すと、続きの応答が返る、(e) 応答の本文にツール呼び出しの記法（`<tool_call>` など）が漏れていない、(f) 入出力トークン数が取得できる
2. **Given** スモークテストの実行、**When** 終わる、**Then** 使ったリクエスト数の合計が表示され、各呼び出しが LLM 呼び出しの記録に残り、すべて予算ゲートを通っている
3. **Given** 確認項目のどれかが不合格、**When** スモークテストが終わる、**Then** 0 以外の終了コードで終わり、不合格の項目と、モデルが返した内容（秘密情報はマスク済み）が表示される
4. **Given** APIキーが環境変数にない、**When** スモークテストを実行する、**Then** LLM を呼ばずに、必要な環境変数の名前を示して失敗する
5. **Given** 設定で別のモデル名（例: 検査役のモデルや退避先）を指定する、**When** スモークテストを実行する、**Then** そのモデルに対して同じ確認ができる
6. **Given** 素の HTTP で送る指定、**When** スモークテストを実行する、**Then** Pi を通さずに同じ要求を送って同じ確認項目の合否が表示され、Pi 経由の結果と比べられる。この呼び出しも予算の確認と記録の対象になる

### User Story 2 - すべての LLM 呼び出しを予算の範囲に収める (Priority: P1)

後続の機能は、LLM を呼ぶたびに予算ゲートを通る。ゲートは呼ぶ前に、月の消費件数と、そのジョブの消費件数を設定の上限と比べ、残りがなければ LLM を呼ばずに「予算切れ」として止める。運用者は、上限を超えて無償枠を使い切ることがないと当てにできる。

**Why this priority**: 原則 V（すべての LLM 呼び出しは予算ゲートを通す）の中核。ゲートを通らない呼び出しを1つでも作ると、予算管理と計測（記事の徹底検証パート）が成り立たない。

**Independent Test**: 偽の LLM と使い捨てのデータベースで、月の上限・ジョブの上限のそれぞれちょうど手前まで記録を入れ、次の呼び出しが通ること、その次が LLM を呼ばずに止まることを確かめる。

**Acceptance Scenarios**:

1. **Given** 今月の消費が月の上限より少なく、ジョブの消費もジョブの上限より少ない、**When** LLM を呼ぶ、**Then** 呼び出しが行われ、1件記録される
2. **Given** 今月の消費が月の上限に達している、**When** LLM を呼ぶ、**Then** LLM には何も送られず、「月の予算切れ」と分かるエラーで止まる
3. **Given** あるジョブの消費がジョブの上限に達している、**When** そのジョブで LLM を呼ぶ、**Then** LLM には何も送られず、「ジョブの予算切れ」と分かるエラーで止まる。別のジョブは影響を受けない
4. **Given** ジョブに属さない呼び出し（スモークテスト・回帰評価）、**When** LLM を呼ぶ、**Then** 月の上限だけで判断する
5. **Given** 月の残りが1ジョブの上限を下回っている、**When** 新しいジョブを受け付けてよいか問い合わせる、**Then** 「受け付けない」と答える（受付そのものは 007 が行う）
6. **Given** 月が変わった（設定のタイムゾーンで月初を過ぎた）、**When** LLM を呼ぶ、**Then** 新しい月の件数で判断される

### User Story 3 - 一時的な失敗をリトライし、すべての試行を記録する (Priority: P1)

LLM 呼び出しが一時的な理由（混雑・レート制限・サーバー側の一時エラー・通信の切断）で失敗したら、予算ゲートの層で待ってから再試行する。再試行1回ごとに予算を確認し、1件として記録する。リトライが漏れなく数えられるので、運用者は記録の件数を実際に送ったリクエスト数として信頼できる。

**Why this priority**: さくらのAI Engine はプレビュー提供で一時的な失敗が想定される。リトライを各工程に散らすと数え漏れが出るため、ゲートと同じ層に置く必要がある（原則 V）。

**Independent Test**: 偽の LLM に「1回目は一時エラー、2回目は成功」「毎回一時エラー」「恒久的なエラー（認証失敗など）」を返させ、試行回数・記録の件数と内容・最終的な結果を確かめる。

**Acceptance Scenarios**:

1. **Given** 1回目が一時エラー、2回目が成功する LLM、**When** 呼ぶ、**Then** 呼び出し元には成功の応答が返り、記録は2件（試行回数 1 は失敗、試行回数 2 は成功）になる
2. **Given** 毎回一時エラーを返す LLM、**When** 呼ぶ、**Then** 設定の上限回数まで試行したあと、最後のエラーで失敗し、試行した回数と同じ件数が記録される
3. **Given** 恒久的なエラー（認証失敗・リクエスト不正など）を返す LLM、**When** 呼ぶ、**Then** 再試行せずに失敗し、1件記録される
4. **Given** リトライの途中で月またはジョブの予算が尽きた、**When** 次の再試行を行おうとする、**Then** LLM を呼ばずに予算切れで止まる
5. **Given** 応答の途中で通信が切れた（応答の一部を受け取ったあと）、**When** 失敗する、**Then** 途中までの応答は呼び出し元に渡さず、試行全体を再試行の対象にする
6. **Given** 呼び出し元が処理を取り消した（ジョブのタイムアウトなど）、**When** 呼び出し中である、**Then** 呼び出しを中止し、再試行せず、取り消しとして1件記録する
7. **Given** レート制限の応答に待ち時間の指示がある、**When** 再試行する、**Then** 指示された時間以上待つ（ただし上限を超える待ち時間なら再試行せずに失敗する）

### User Story 4 - LLM 呼び出しを1回ずつ計測する (Priority: P1)

すべての LLM 呼び出しについて、ジョブ・工程・役割・モデル・試行回数・入出力トークン数・所要時間・結果・エラーが記録される。運用者と開発者は、記録を集計して消費と成功率を把握し、記事の徹底検証パートの材料にする。

**Why this priority**: 原則 V の必須事項。002 から記録できていれば、011 の画面が遅れても記事は記録の集計で書ける（実装計画の「遅れたときに削る順番」の前提）。

**Independent Test**: 偽の LLM で成功・失敗・取り消しの呼び出しを行い、記録の各項目が期待どおりに入ること、エラーの文面に秘密情報が残らないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 成功する呼び出し、**When** 終わる、**Then** 結果が「成功」、入出力トークン数と所要時間が入った記録が1件できる
2. **Given** 失敗する呼び出し、**When** 終わる、**Then** 結果が「失敗」、エラーの内容（秘密情報はマスク済み）が入った記録が1件できる。トークン数が分からなければ空にする
3. **Given** APIキーを含むエラー文（例: 認証ヘッダーの値がエラーに含まれる）、**When** 記録する、**Then** APIキーは伏せ字に置き換わっている
4. **Given** 呼び出し元が工程と役割を指定する、**When** 呼ぶ、**Then** 記録にその工程・役割・使ったモデル名が入る

---

### User Story 5 - 偽の LLM で後続機能をテストする (Priority: P2)

開発者は、自動テストで本物の LLM の代わりに偽の LLM を使う。偽の LLM には「テキストを返す」「指定のツール呼び出しを返す」「指定のエラーを返す」といった応答を順番に仕込める。偽の LLM も予算ゲートの内側に差し込めるので、ゲート・リトライ・記録も含めてテストできる。

**Why this priority**: constitution の開発ワークフロー（自動テストで さくらのAI Engine を呼ばない）の前提。004・005・012 のテストが依存するが、002 自体の価値（US1〜4）はこれがなくても検証の一部はできるため P2 とする。

**Independent Test**: 偽の LLM に応答を3つ仕込み、3回呼んだときに順に返ること、仕込みが尽きたときに分かるエラーになること、受け取った入力（メッセージ・ツールの定義）をあとから確かめられることを確認する。

**Acceptance Scenarios**:

1. **Given** テキスト応答・ツール呼び出し・エラーを順に仕込んだ偽の LLM、**When** 3回呼ぶ、**Then** 仕込んだ順に返る
2. **Given** 仕込みが尽きた偽の LLM、**When** もう1回呼ぶ、**Then** テストの失敗と分かるエラーになる
3. **Given** 偽の LLM、**When** 呼ぶ、**Then** 渡したメッセージ・ツールの定義・モデル名をテストからあとで確かめられる
4. **Given** 偽の LLM に入出力トークン数を仕込む、**When** 予算ゲート越しに呼ぶ、**Then** その値が記録に入る

---

### Edge Cases

- 月の上限ちょうどに達したところで、ジョブの途中の工程が LLM を呼ぼうとする → 呼ばずに予算切れで止める（ジョブの失敗への遷移は呼び出し元〔007 の状態機械〕が行う）
- 呼び出し中に月が変わる → 記録の月は呼び出しの開始時刻で決める
- 応答は 200 だがツール呼び出しが本文に XML として漏れている → 予算ゲートは成功として記録する。漏れの検出はスモークテストの確認項目で行う（本番の扱いは 004 で決める）
- 応答は 200 だが本文もツール呼び出しも空 → 成功として記録する（中身の妥当性の判断は呼び出し元が行う）
- 存在しないモデル名を指定した（プレビューモデルの提供終了を含む） → 恒久的なエラーとして再試行せず、モデル名を含むエラーで失敗する。退避先のモデルへ自動では切り替えない（運用者が設定を直す。実装役と検査役が同じモデルになって原則 III を崩す事故を防ぐ）
- データベースへの記録に失敗した → LLM の応答があっても呼び出しを失敗として扱う（記録されない呼び出しを作らない）
- 計画役・検査役の呼び出しにツールの定義を渡そうとした → 本機能では制限しない（ツールを渡さないことは 005 の計画役・検査役の側で守る）
- 同時に2つの呼び出しが予算を確認する → LLM を使う工程は同時に1件（原則 VII）なので、確認と記録の間の競合は想定しない
- エンドポイントの URL やAPIキーが誤っている → スモークテストの最初の呼び出しで、恒久的なエラーとして分かる文面で失敗する

## Requirements *(mandatory)*

### Functional Requirements

**さくらのAI Engine への接続**

- **FR-001**: システムは さくらのAI Engine を OpenAI互換（Chat Completions）の LLM の提供元として登録し、エージェント層（Pi）から使えるようにしなければならない
- **FR-002**: 接続先の URL とモデル名は設定ファイルから読み、コードに書いてはならない。APIキーは環境変数から読まなければならない
- **FR-003**: OpenAI 本家との差（開発者ロールの扱い、ストリーミングでの使用量の返し方など）は、提供元の登録時の互換性の設定で吸収しなければならない。どの設定にしたかはスモークテストの結果で決める
- **FR-004**: 役割（計画・実装・検査）ごとに、設定のモデル名から呼び出し用のモデルを得られなければならない。退避先のモデル名への切り替えは設定の変更だけでできなければならない。実行中に自動で退避先へ切り替えてはならない

**予算ゲート**

- **FR-005**: すべての LLM 呼び出しは、1つの予算ゲートの関数を通らなければならない。エージェント層が LLM を呼ぶ関数をゲートで丸ごと差し替え、ゲートを経由しない呼び出し経路を作ってはならない
- **FR-006**: ゲートは呼び出しの前（再試行の前を含む）に、今月の消費件数が月の上限未満であること、ジョブに属する呼び出しならそのジョブの消費件数がジョブの上限未満であることを確かめ、満たさなければ LLM を呼ばずに予算切れのエラーで止めなければならない
- **FR-007**: 予算切れのエラーは、月とジョブのどちらの上限か、上限値と消費件数が呼び出し元で分かる形でなければならない
- **FR-008**: 消費件数は、成功・失敗・取り消しを問わず LLM に送った回数とし、記録された LLM 呼び出しの件数から数えなければならない（月の区切りは設定のタイムゾーン）
- **FR-009**: システムは「新しいジョブを受け付けてよいか」を判断する関数を提供しなければならない。月の残り（月の上限 − 今月の消費）が1ジョブの上限を下回ったら「受け付けない」と答える

**リトライ**

- **FR-010**: ゲートは一時的な失敗（レート制限、サーバー側の 5xx、タイムアウト、通信の切断）を、間隔を空けて再試行しなければならない。再試行の上限回数は設定で変えられる（既定: 最初の1回を含めて3回）
- **FR-011**: 恒久的な失敗（認証失敗、リクエストの不正、存在しないモデルなど）と、呼び出し元による取り消しは再試行してはならない
- **FR-012**: レート制限の応答に待ち時間の指示があれば、それ以上の時間を待ってから再試行しなければならない。待ち時間が上限（既定: 60秒）を超えるなら再試行せずに失敗とする
- **FR-013**: 再試行は応答が呼び出し元に渡り始める前に判断しなければならない。失敗した試行の途中までの応答を呼び出し元に渡してはならない
- **FR-014**: 1回の LLM 呼び出しには応答の時間の上限（既定: 5分）を設け、超えたら一時的な失敗として扱わなければならない

**記録**

- **FR-015**: ゲートは試行1回ごとに LLM 呼び出しの記録を1件書かなければならない: ジョブ（任意）、工程、役割、モデル、試行回数（1始まり）、入力トークン数、出力トークン数、所要時間、結果（成功・失敗）、エラー、開始時刻
- **FR-016**: 記録のエラーには、失敗の種類（予算切れは記録しない。一時的・恒久的・タイムアウト・取り消し）と、秘密情報をマスクした内容を入れなければならない
- **FR-017**: 記録に失敗したら、その呼び出しを失敗として呼び出し元に返さなければならない
- **FR-018**: 呼び出し元は、呼び出しごとにジョブ（任意）・工程・役割を指定できなければならない

**偽の LLM（テスト用）**

- **FR-019**: テスト用に、仕込んだ応答（テキスト、ツール呼び出し、エラー、トークン数）を順に返す偽の LLM を提供しなければならない。偽の LLM は予算ゲートの内側（本物の LLM の位置）に差し込める
- **FR-020**: 偽の LLM は、受け取った入力（メッセージ、ツールの定義、モデル名）をテストから確かめられるようにしなければならない。仕込みが尽きたらテストの失敗と分かるエラーにする

**スモークテスト（実機確認）**

- **FR-021**: 実機の さくらのAI Engine に対して、User Story 1 の確認項目 (a)〜(f) を実行するコマンドを提供しなければならない。対象のモデルは既定で実装役のモデルとし、引数で設定の別の役割のモデルを選べる
- **FR-022**: スモークテストの呼び出しもすべて予算ゲートを通し、ジョブに属さない呼び出しとして記録しなければならない。1回の実行（1つの方式・1つのモデル）で使うリクエストは 10 件以下とする
- **FR-023**: スモークテストは確認項目ごとの合否、使ったリクエスト数、不合格の項目についてはモデルが返した内容（秘密情報はマスク済み）を表示し、1つでも不合格なら 0 以外の終了コードで終わらなければならない
- **FR-024**: スモークテストは自動テスト（チェックコマンド）には含めてはならない。手動でだけ実行する
- **FR-025**: スモークテストは、Pi を通さずに同じ要求を素の HTTP（OpenAI互換 Chat Completions）で送る方式でも実行できなければならない。この方式の呼び出しも、予算ゲートと同じ予算の確認と記録を通す（ゲートを迂回する経路にしない）
- **FR-026**: スモークテストの結果（各項目の合否、互換性の設定、モデル名、気づいた挙動）は試行錯誤の記録（`docs/journal/`）に残し、Pi を続けるか切り替えるかの判断と理由を書かなければならない。判断の基準は次のとおり: 不合格なら互換性の設定を変えて再確認する → それでも不合格なら素の HTTP の結果と比べる → 素の HTTP で合格し Pi 経由で不合格のときだけ予備（TanStack AI）へ切り替える → 両方不合格ならモデル側の問題として別のモデルを検討する。判断が「切り替える」なら、先に設計ドキュメントを直してから後続の機能に進む

### Key Entities *(include if feature involves data)*

- **LLM 呼び出し（llm_calls）**: 001 で用意した記録先。本機能が唯一の書き手になる。試行1回が1件
- **予算（budget）**: 001 で用意した月ごとの記録。本機能では受付可否の判断に使う上限値の写しを、その月の最初の呼び出し時に用意する（受付を止めた時刻の書き込みは 007 が行う）
- **呼び出しの文脈**: 呼び出し元がゲートに渡す情報。ジョブ（任意）、工程、役割。記録と予算の判断に使う
- **予算切れ**: ゲートが返す失敗の種類。どの上限（月・ジョブ）か、上限値、消費件数を持つ
- **スモークテストの結果**: 確認項目ごとの合否、使ったリクエスト数、モデル名、不合格時のモデルの出力

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: スモークテストの1回の実行が 10 リクエスト以下で終わり、正常時（再試行もタイムアウトも起きないとき）は2分以内に終わる。6つの確認項目すべての合否が出る。この結果で Pi を続けるか切り替えるかを、AI解禁の日（実装計画 3章。005 が偽の LLM で通ったあと）に決められる
- **SC-002**: 自動テストで、月とジョブの上限ちょうどを境に、上限を超える呼び出しが LLM に1件も送られない（超過 0 件）
- **SC-003**: LLM に送ったリクエストの数と、記録された LLM 呼び出しの件数が一致する（リトライを含め、記録漏れ 0 件）
- **SC-004**: 一時的な失敗が1回だけ起きる状況で、呼び出し元から見た呼び出しの成功率が 100% になる
- **SC-005**: 記録されたエラーの内容に APIキーが平文で現れない
- **SC-006**: 予算ゲート・リトライ・記録の自動テストが、外部サービスに接続せずに10秒以内に終わる
- **SC-007**: 後続の機能が LLM を呼ぶ方法が予算ゲートを通る1通りしかない（コードの検索で、ゲートを経由しない呼び出し経路が見つからない）

## Assumptions

- 技術の選定は constitution と `03` 5章のとおり（Pi の `pi-ai` に独自の提供元を登録し、エージェント層が LLM を呼ぶ関数〔`streamFn`〕をゲートで差し替える）。本仕様では選定し直さない
- さくらのAI Engine が失敗したリクエストを無償枠に数えるかは分からないため、消費件数は送った全件で数える（多めに数える側に倒す）。予算切れで送らなかった呼び出しは記録しない
- リトライの上限回数・待ち時間の上限・応答の時間の上限は `factory.toml` の `[llm]` に省略可能な項目として足し、既定値（3回・60秒・5分）を持たせる
- APIキーの環境変数の名前は 001 の秘密情報の読み込み口に合わせる（計画で決める）
- 接続先 URL とモデル名は 001 で仮の値が入っている。スモークテストで正しい値を確かめ、`factory.toml` を直す
- 新しいジョブの受付可否は判断の関数だけを用意し、実際に受付を止める処理（と受付を止めた時刻の記録）は 007 で行う
- 予算切れ・上限超過によるジョブの `failed` への遷移とレポートは、007 の状態機械が行う。本機能はエラーを返すまで
- 1工程の反復回数（`shouldStopAfterTurn`）とジョブ全体の時間の上限は 004・007 で実装する。本機能は呼び出し回数の上限だけを扱う
- 検査役の JSON 出力の検証と再要求は 005 で行う。`response_format` は使わない
- LLM を使う工程の同時実行は1件（原則 VII）なので、予算の確認と記録の間で排他制御はしない
- 軌跡（プロンプト・ツール呼び出し・結果の全文）の保存は 004 で行う。本機能が記録するのは呼び出しのメタデータだけ
