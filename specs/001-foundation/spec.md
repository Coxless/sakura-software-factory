## Clarifications

### Session 2026-11-08

- Q: 月の予算を数えるとき、「月初」をどのタイムゾーンで区切るか？ → A: 日本時間（JST）の月初で区切る。タイムゾーンは設定で変更可能にする
- Q: `budget`（予算）テーブルに何を記録するか？ → A: 月ごとの記録だけを持つ（対象月、その月に適用した上限〔設定値の写し〕、新規受付を止めた時刻）。上限の正は設定ファイル、消費は `llm_calls` から数える
- Q: マイグレーションは起動時に自動適用するか、専用コマンドで適用するか？ → A: 起動時に未適用分を自動で適用する。同じ処理を専用コマンドでも実行できるようにする

## User Scenarios & Testing *(mandatory)*

この機能の利用者は2種類いる。

- **開発者**（本プロジェクトを作る人）: 後続の機能（002〜012）を同じ品質基準で積み上げる
- **運用者**（VPS でファクトリーを動かす人）: 設定ファイルを用意し、ファクトリーを起動して記録を確認する

### User Story 1 - 品質チェックを1コマンドで通す (Priority: P1)

開発者は、コードを変えたあと1つのコマンドで lint・フォーマット確認・型チェック・自動テストをまとめて実行し、合否を確かめる。同じコマンドを CI でも使う。

**Why this priority**: 以降のすべての機能はこのチェックを通ることを前提に作る。これがないと品質ゲート（原則 VI）の土台がなく、他のストーリーの検証もできない。

**Independent Test**: 空に近いソースツリーで、チェックコマンドを実行して成功すること、わざと型エラー・lint 違反・失敗するテストを入れるとそれぞれ失敗することを確かめる。

**Acceptance Scenarios**:

1. **Given** 依存を入れたばかりのリポジトリ、**When** 開発者がチェックコマンドを実行する、**Then** lint・フォーマット確認・型チェック・テストが順に実行され、すべて通れば終了コード 0 で終わる
2. **Given** 型エラーを含むソース、**When** チェックコマンドを実行する、**Then** 0 以外の終了コードで終わり、エラーの場所が出力に示される
3. **Given** 失敗するテスト、**When** チェックコマンドを実行する、**Then** 0 以外の終了コードで終わり、失敗したテスト名が出力に示される
4. **Given** 開発環境（Workshop `dev`）、**When** 決められたパッケージマネージャー以外（`npm install`）でインストールしようとする、**Then** 0 以外の終了コードで失敗し、使うべきパッケージマネージャーの名前が出力に示される

---

### User Story 2 - 設定ファイルを読み込み、誤りを起動時に知る (Priority: P1)

運用者は `factory.toml` にモデル名・予算・各種上限・自動マージ条件・許可ユーザーなどを書く。ファクトリーは起動時にこれを読み込んで検証し、誤りがあれば何がどこで間違っているかを示して起動を止める。

**Why this priority**: モデル名をコードに書かない（原則 I）、予算と上限を設定で持つ（原則 II・V）ことの前提。002 の予算ゲートがこの設定を使う。

**Independent Test**: 正しい設定ファイル・項目が欠けた設定ファイル・型が違う設定ファイルを用意し、読み込み関数の結果（成功時は型付きの設定、失敗時は項目名付きのエラー）を確かめる。

**Acceptance Scenarios**:

1. **Given** 必須項目がすべて正しい設定ファイル、**When** 読み込む、**Then** 型付きの設定値が返り、省略可能な項目には既定値が入る
2. **Given** 必須項目（例: 実装役のモデル名）が欠けた設定ファイル、**When** 読み込む、**Then** 欠けている項目のパスを含むエラーで失敗する
3. **Given** 数値であるべき項目に文字列が入った設定ファイル、**When** 読み込む、**Then** 該当項目のパスと期待する型を含むエラーで失敗する
4. **Given** 設定ファイルが存在しない、**When** 起動する、**Then** ファイルのパスを示すエラーで起動を止める
5. **Given** 未知の項目（綴り間違いなど）を含む設定ファイル、**When** 読み込む、**Then** 未知の項目名を示すエラーで失敗する

---

### User Story 3 - ジョブと LLM 呼び出しの記録先を用意する (Priority: P1)

運用者・開発者は、ジョブ・ジョブのイベント・LLM 呼び出し・デプロイ・予算の記録を1つのデータベースファイルに保存できる。スキーマの変更はマイグレーションとして管理し、起動時に未適用のマイグレーションが適用される。

**Why this priority**: 002（予算ゲートは `llm_calls` と `budget` を使う）、007（キューは `jobs` を使う）、010（`deployments`）、011（集計）がすべてこの記録先に依存する。計測（原則 V）は記事の徹底検証パートの材料になるため、最初の LLM 呼び出しから記録できる必要がある。

**Independent Test**: 空のデータベースファイルに対してマイグレーションを適用し、5つの記録先それぞれに1件ずつ書き込み・読み出しできること、2回目の適用で何も変わらないことを確かめる。

**Acceptance Scenarios**:

1. **Given** データベースファイルがない、**When** 起動（またはマイグレーション）を実行する、**Then** ファイルが作られ、5つの記録先がすべて用意される
2. **Given** マイグレーション適用済みのデータベース、**When** もう一度適用する、**Then** エラーにならず、既存の記録は変わらない
3. **Given** 用意された記録先、**When** LLM 呼び出し1回分（ジョブ、工程、役割、モデル、試行回数、入出力トークン数、所要時間、結果、エラー）を記録する、**Then** 同じ値で読み出せる
4. **Given** ジョブを1件記録した状態、**When** そのジョブのイベントを複数記録する、**Then** ジョブに紐づけて時系列順に読み出せる
5. **Given** 今月の LLM 呼び出しが複数記録されている、**When** 今月の件数を集計する、**Then** 月初以降の件数が正しく返る

---

### User Story 4 - 構造化ログを出す (Priority: P2)

運用者は、ファクトリーのログを1行1件の構造化形式で受け取り、ジョブ ID などで絞り込める。秘密情報はログに出ない。

**Why this priority**: 24時間稼働の監視とトラブル調査に要るが、P1 の3つがなくても単独で価値を持たないため P2 とする。

**Independent Test**: ロガーで情報・エラーを出し、出力が1行1件の構造化形式であること、ジョブ ID などの付加情報が含まれること、秘密情報の項目が伏せられることを確かめる。

**Acceptance Scenarios**:

1. **Given** ロガー、**When** ジョブ ID を付けて情報を出す、**Then** 1行の構造化レコードに時刻・レベル・メッセージ・ジョブ ID が含まれる
2. **Given** APIキーやトークンを含む値、**When** ログに出す、**Then** その値は伏せ字に置き換わる
3. **Given** 設定でログレベルを指定、**When** それより低いレベルのログを出す、**Then** 出力されない

---

### Edge Cases

- 設定ファイルの TOML 構文自体が壊れている → 行番号を含むエラーで起動を止める
- 予算などの数値が負や 0 → 検証エラーにする（月の上限は 1 以上）
- 1ジョブの上限が月の上限より大きい → 検証エラーにする
- データベースファイルの置き場所のディレクトリがない → 作成する（作成できなければ起動を止める）
- 同じデータベースに別プロセス（後続機能の HTTP と Worker など）から同時に読み書きする → 読み取りが書き込みに妨げられない動作モードにする
- 記録中にプロセスが落ちる → 1件の記録は全部書かれるか、まったく書かれないかのどちらか
- 月の境目をまたいで動いているジョブ → 月の集計は呼び出し時刻で区切り、基準のタイムゾーン（下の Assumptions を参照）を全体で揃える

## Requirements *(mandatory)*

### Functional Requirements

**開発ツールと品質チェック**

- **FR-001**: リポジトリは、lint・フォーマット確認・型チェック・自動テストをまとめて実行する単一のチェックコマンドを提供しなければならない。どれか1つでも失敗したら 0 以外の終了コードで終わる
- **FR-002**: チェックコマンドはローカル開発環境と CI で同じものを使えなければならない
- **FR-003**: パッケージマネージャーとそのバージョンはリポジトリで固定し、ほかのパッケージマネージャーでのインストールは失敗させなければならない
- **FR-004**: 自動テストは外部サービス（LLM・GitHub など）に接続せずに実行できなければならない
- **FR-005**: ソースのディレクトリ構成は設計（`03` 8章）に従い、後続機能の置き場所（設定・記録・ログ）を決めておかなければならない

**設定**

- **FR-006**: システムは起動時に設定ファイル（`factory.toml`）を1回読み込み、スキーマで検証しなければならない
- **FR-007**: 設定には少なくとも次を含めなければならない: 役割ごとのモデル名（計画・実装・検査、および退避先）、LLM エンドポイントの URL、月とジョブごとのリクエスト上限、月の区切りに使うタイムゾーン（既定は `Asia/Tokyo`）、反復の上限（判定不合格のやり直し・CI 失敗後のやり直し・1工程のターン数）、ジョブ全体のタイムアウト、CI 待ちのタイムアウト、自動マージ条件（diff の上限・禁止パス・許可する作業の種類）、`@agent` を許可するユーザー、データベースと軌跡の保存先、ログレベル
- **FR-008**: 検証に失敗したら、問題のある項目のパスと理由をすべて示して起動を止めなければならない
- **FR-009**: 省略可能な項目には文書化された既定値を入れなければならない
- **FR-010**: APIキー・トークンなどの秘密情報は設定ファイルに書かず、環境変数から読まなければならない。設定ファイルに秘密情報らしい項目があれば検証エラーにする
- **FR-011**: 検証後の設定は型付きで、実行中に書き換えられない値として後続機能に渡さなければならない
- **FR-012**: 設定項目を説明するサンプル設定ファイルをリポジトリに置き、それ自体が検証を通らなければならない

**記録（データベース）**

- **FR-013**: システムは次の5つの記録先を1つのデータベースファイルに持たなければならない: ジョブ（`jobs`）、ジョブのイベント（`job_events`）、LLM 呼び出し（`llm_calls`）、デプロイ（`deployments`）、予算（`budget`）
- **FR-014**: スキーマの変更はマイグレーションとして履歴管理し、起動時に未適用のものだけを自動で適用しなければならない。同じ適用処理を専用コマンドでも単独で実行できる。適用は何度実行しても同じ結果になり、適用に失敗したら変更を残さずエラーで起動を止める
- **FR-015**: ジョブの状態は設計の状態機械（`03` 3章）の状態に限らなければならない: `queued`, `planning`, `implementing`, `testing`, `judging`, `pr_opened`, `ci_waiting`, `merged`, `deploying`, `deployed`, `rolled_back`, `failed`
- **FR-016**: LLM 呼び出しの記録は `job_id, phase, role, model, attempt, input_tokens, output_tokens, latency_ms, status, error` を持ち、呼び出し時刻も記録しなければならない。ジョブに属さない呼び出し（スモークテスト・回帰評価など）も記録できる
- **FR-017**: 月初からの LLM 呼び出し件数と、ジョブごとの件数を取得できなければならない（002 の予算ゲートが使う）。月初は設定のタイムゾーンで決める（例: JST なら 2026-12-01 00:00 JST ＝ 2026-11-30 15:00 UTC 以降が12月分）
- **FR-018**: 同時実行のジョブを取り出す操作が、1件のジョブを二重に取り出さない形で行えなければならない（007 のキューが使う）
- **FR-019**: 読み取りが書き込みに妨げられない動作モードでデータベースを開かなければならない
- **FR-020**: 自動テストは、実ファイルを汚さない使い捨てのデータベースで実行できなければならない

**ログ**

- **FR-021**: システムは1行1件の構造化ログを標準出力に出さなければならない
- **FR-022**: ログには時刻・レベル・メッセージを含め、ジョブ ID などの文脈を付けた子ロガーを作れなければならない
- **FR-023**: 秘密情報（APIキー・トークン・認証ヘッダーなど）の項目はログで伏せ字にしなければならない
- **FR-024**: ログレベルは設定で変えられなければならない

### Key Entities *(include if feature involves data)*

- **ジョブ（jobs）**: `@agent` の依頼1件。対象リポジトリ、Issue 番号、依頼者、依頼文、現在の状態、反復回数、作業ブランチ、PR 番号、作成・更新・完了時刻、失敗理由を持つ
- **ジョブのイベント（job_events）**: ジョブの状態遷移や工程の出来事の時系列。ジョブ、種類、遷移前後の状態、詳細、時刻を持つ。監査証跡になる
- **LLM 呼び出し（llm_calls）**: LLM 呼び出し1回（リトライは1回ずつ別の記録）。ジョブ（任意）、工程、役割、モデル、試行回数、入出力トークン数、所要時間、結果、エラー、時刻を持つ。予算の残量はここから数える
- **デプロイ（deployments）**: ステージングへのデプロイ1回。コミット、イメージタグ、結果、ロールバックの有無、関係するジョブ、時刻を持つ。ロールバック先の特定に使う
- **予算（budget）**: 月ごとの記録（1か月1件）。対象月、その月に適用した月のリクエスト上限（設定値の写し）、新しいジョブの受付を止めた時刻（止めていなければ空）を持つ。上限の正は設定ファイルで、消費件数は持たず LLM 呼び出しの記録から数える

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 依存を入れたばかりの開発環境で、チェックコマンドが一度で成功し、2分以内に終わる
- **SC-002**: 型エラー・lint 違反・失敗するテストをそれぞれ1つ入れたとき、チェックコマンドが3つとも検出する（見逃し 0）
- **SC-003**: 誤った設定ファイル（必須項目の欠落・型違い・未知の項目・範囲外の値）で起動したとき、100% の場合に問題の項目名を示して起動が止まる
- **SC-004**: 空の状態から、マイグレーションの適用までが起動するだけ（または専用コマンド1つ）で終わり、2回目以降の適用で記録が1件も変わらない
- **SC-005**: LLM 呼び出しを1,000件記録した状態で、今月の件数とジョブごとの件数の集計が1秒以内に返る
- **SC-006**: ログに出した秘密情報の値が、出力のどこにも平文で現れない

## Assumptions

- 技術の選定は constitution と `03` 5章で決まっているものを使う（pnpm・Biome・Vitest・TypeBox・smol-toml・pino・better-sqlite3＋Drizzle）。本仕様では選定し直さない
- 月の区切りは日本時間（JST）の月初とする。さくらのAI Engine の無償枠のリセット基準が JST と違うと分かった場合は、設定のタイムゾーンを変えて合わせる
- APIキー（さくらのAI Engine）や GitHub App の秘密鍵は環境変数で渡す。001 では読み込み口だけを用意し、実際に使うのは 002・007 以降
- 起動処理は「設定の読み込み → ログの準備 → マイグレーションの適用」までとする。HTTP サーバーと Worker は 006・007 で足す
- 軌跡の JSONL の書き出しは 004 で作る。001 では保存先の設定項目だけを用意する
- 状態の遷移ルールそのもの（どの状態からどの状態へ移れるか）は 007 で実装する。001 では状態の値の範囲だけを決める
- 対象は1台の VPS・1プロセス（HTTP と Worker を同じプロセスで動かす）で、データベースの同時書き込みは多くない
