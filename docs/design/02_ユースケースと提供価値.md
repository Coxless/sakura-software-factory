# ユースケースと提供価値

## 1. 想定ユーザー（確定）

**メインの想定ユーザーは「企業の開発案件（受託・SIer・社内開発チーム）」とする。**

### 理由
- Zennの読者には、企業で働くエンジニアも多い。業務で使う場面を思い浮かべやすい
- 差別化の軸「推論を国産・ZDRで閉じる」が最も強く効くのは、コードを海外のAIサービスに送れない企業の現場
- 今回の実装は小規模だが、**本格的なソフトウェアファクトリーを企業内に作るときの参考実装（リファレンス）** として位置づけられる

### 記事での位置づけ
- 本編: 「コードを海外のAIに渡せない企業チームのための、国産推論で動くソフトウェアファクトリーの小さな参考実装」
- 発展: 「この構成をもとに、本格的なファクトリーへ拡張するには何が要るか」を展望として示す（スケール、検証の強化、自律レベルの引き上げ、Forgejo による完全国産化など）
- 個人開発者・OSSメンテナーにも使える、という点は補足として触れる程度にする

### 前提と注意
- 企業の実案件のデータは使えない。デモと検証は、企業案件を想定したサンプルリポジトリ（または自分のリポジトリ）で行い、その旨を記事で明記する
- 「なぜ `@claude` や `@copilot` ではないのか」には、推論の所在（国内・ZDR）、コストの予測しやすさ、工程・検査・予算を自社で設計できる点で答える
- リポジトリは GitHub のままなので、「国産インフラで完結」とは言わない（`01` 4章の注意を参照）

## 2. 処理能力の目安

- **LLMを1回呼ぶたびに1リクエストを消費する**。1回の呼び出しで複数のツールを呼んでも、消費は1リクエスト（Pi のエージェントループでは、1ターン＝LLM呼び出し1回）
- 1 Issue あたり20〜50リクエストかかると想定（計画1〜2、実装10〜30、検査とリトライで数回）→ **月60〜150件**
  - 以前は「ツールを1回呼ぶたびに1リクエスト」として見積もっていた。1ターンで複数のツールを呼ぶことがあるため、実際にはこれより少なく済む可能性がある（見積もりは楽観的な方向に変わる）
  - CI失敗後の修正ループもリクエストを消費する。一方、CI（Actions）の実行とステージングデプロイ自体はリクエストを消費しない
- 回帰評価（`04` 参照）の実行分も、月の枠から差し引いて計画する
- この見積もりは仮のもので、実測値（`03` 7章の計測）で更新する

## 3. 向いているユースケース

共通条件: **仕様がはっきりしていて、テストで合否を判定できる小さな作業**

| ユースケース | 向いている理由 |
|---|---|
| テストの追加 | 成果がテストの成否で判定でき、品質ゲートとの相性が最も良い |
| 再現手順のあるバグ修正 | 再現テストを書いてから修正すれば、検査役が判定しやすい |
| 依存ライブラリ更新の後始末 | Renovate や Dependabot の PR が CI で落ちたのをきっかけに起動でき、イベント駆動が活きる |
| lintエラー・非推奨APIの解消、型付けの追加 | 機械的で量が多く、人がやると退屈な作業 |
| ドキュメントの同期 | コードの変更に合わせて README や API ドキュメントを更新する |

**向いていない作業**（ファクトリーが受け付けない作業として明記する）: 要件があいまいな機能、UIや見た目の調整、設計判断が必要な大きなリファクタリング

## 4. 提供価値（企業視点）

1. **コードを海外のAI事業者に渡さずに済む**: 守秘義務契約などで海外のAIサービスを使えないチームでも、推論が国内・ZDRなら採用を検討できる。リポジトリは今の GitHub のままで導入できる（最も強い差別化ポイント）
2. **レビュアーの負担を減らす**: 別のモデルの検査とチームのCIを通った変更が、工程レポート付きでステージングに出ている。人間は「本番に出してよいか」の判断に集中できる
3. **コストが読める**: 月の上限が決まっていて、Issueごとの消費量も見える
4. **待ち時間がない**: 常時稼働なので、Issueを立てておけば後からステージングで動くものが見られる
5. **監査証跡になる**: どのモデルが書き、どのモデルが検査し、CIの結果がどうで、何回やり直し、いつデプロイされたかが残る。規制のある業界での説明材料になる

## 5. 仕様があいまいなケースへの考え方（一般論）

- 仕様があいまいだと合格基準を作れず、「テストは通るが求めていたものとは違う」成果物が量産される。コードを書くコストが下がるほど、ボトルネックは「何を作るか決めること」と「正しいか判定すること」に移る
- あいまいさは2種類ある
  - **どう作るか**（実装方法・細部の設計）: エージェントがかなり埋められる
  - **何を作るか**（誰のどんな問題を解くか、優先度、使い勝手）: 人間の判断が必要
- 一般的な対処パターン
  1. 作る前に質問させる（あいまいな点があれば止めて確認を返す）
  2. 仕様を作る工程を手前に置く（要求→仕様・受け入れ基準→人間が承認→生産ラインへ。仕様駆動開発）
  3. 試作品を複数作って人間に選んでもらう
  4. フィーチャーフラグなどで小さく出し、利用状況から仕様を固める
- まとめ: ファクトリーはあいまいさを消すのではなく、「安く速く回せる確認ループ」に変える。自律度の高い工場ほど、上流（仕様・シナリオの作り込み）に人間の手間をかけている
- 本格的なファクトリーへ拡張する際は、2の「仕様を作る工程」を加えることが主要な発展の方向になる（`01` の「2段階コマンド（plan → 承認 → build）」はその小さな版にあたる）
- レベルBではステージングに自動で出るため、パターン4（小さく出して確かめる）と相性が良い

## 6. 検証の材料（徹底検証パート向け）

- 作業の種類ごとの成功率と消費リクエスト数
- 検査役を Qwen3.6 にした場合と gemma-4 にした場合の比較
- ファクトリー内のテストは通ったが CI で落ちた割合（工程内検査の精度）
- ステージングでのヘルスチェック失敗・ロールバックの回数
- 月3,000リクエストで実際に何件さばけたか
- ハーネスの変更ごとの成功率・消費量の変化（回帰評価の結果）
