# アーキテクチャと技術スタック

前提: 言語は TypeScript、ランタイムは Node.js（24 LTS）、パッケージマネージャーは pnpm。方針は `01_ソフトウェアファクトリーの定義と方針.md` に従う。ガードレールとハーネスの設計は `04_ガードレールとハーネス設計.md` を参照。

## 0. 決定事項の要約

| 項目 | 決定 |
|---|---|
| 自律レベル | **B**（CI通過後に自動マージ → ステージングへ自動デプロイ。本番は人間） |
| エージェント／LLM層（主） | **Pi**（`@earendil-works/pi-agent-core` ＋ `@earendil-works/pi-ai`） |
| エージェント／LLM層（予備） | **TanStack AI**（コア 1.0 ＋ openaiCompatible アダプター）。Pi で詰まったときだけ切り替える |
| 採用しない | AI SDK 6、Flue、Mastra、LangGraph.js、OpenAI Agents SDK |
| スキーマ | **TypeBox** に統一（Pi のツール定義が TypeBox のため。Zod は使わない） |
| 工程制御 | 自前の状態機械（ライブラリに任せない） |
| 最終の品質ゲート | 対象リポジトリの **GitHub Actions**（ブランチ保護の必須チェック） |
| ステージングデプロイ | VPS 上のファクトリーが main への push を受けてデプロイ（案。Actions から SSH する方式は採らない） |

選定の経緯: AI SDK 6 → ガードレールを重視して TanStack AI → ハーネスエンジニアリングを重視して Pi、の順に見直した。

## 1. 設計の基本方針

1. **工程はコードで制御し、LLMには任せない**: 計画→実装→検査→PR→CI→マージ→デプロイの流れは、決め打ちの状態機械として書く。LLM に任せるのは各工程の中身だけにする。リクエスト消費が読めるようになり、予算管理（差別化 #3）が成り立つ
2. **LLM呼び出しはホスト側、コード実行はサンドボックス側**: Pi のエージェントループは VPS ホストで動かす。ツール（read / write / edit / bash）は自前で定義し、中身を Docker コンテナへの `docker exec` にする
   - APIキーや GitHub トークンがコンテナに入らない（Pi の CLI をコンテナ内で動かすのではなく、ライブラリとしてホストで使う）
   - 実装工程のコンテナを `--network none` にできる
3. **予算ゲートは `streamFn` の層に置く**: Pi の `streamFn`（LLMを呼ぶ関数）を丸ごと差し替え、1回ごとに記録・上限を確認する。リトライもこの層で実装し、漏れなく数える
4. **ハーネスは差し替え可能な部品として作る**: コンテキスト、ツール、制約、フィードバックを Pi のフックに分けて実装し、回帰評価で効果を測りながら改善する（`04` 参照）
5. **ミドルウェアを増やさない**: Redis などは使わず、キューも記録も SQLite 1つにまとめる。同時に処理するジョブは1件にする
6. **検査は二段構え**: ファクトリー内は速いチェック（工程内検査）、CI は全件（受入検査）。CI はチームの基準なので、ファクトリーは CI を置き換えず、その結果をフィードバックとゲートに使う
7. **Git ホスティングとのやり取りは1つの層にまとめる**: GitHub 固有の処理は `github/` に閉じ込め、将来 Forgejo に置き換えられるようにする（`01` 4章）

## 3. 状態機械

```
queued → planning → implementing → testing → judging
testing ──(工程内テストの失敗)──▶ implementing（同じ会話に差し込む。1回の実装工程で上限あり）
judging ──(不合格)──▶ implementing（新しい会話。上限あり）
judging(合格) → pr_opened（PR作成・auto-merge 予約）→ ci_waiting
   ──(CI失敗)──▶ implementing（CIログ付き、上限あり）
ci_waiting(全通過) → merged → deploying → deployed
   ──(ヘルスチェック失敗)──▶ rolled_back
どこからでも → failed（予算切れ・上限超過・タイムアウト）
```

- PR を作ったら、`judging` → `pr_opened` → `ci_waiting` を1つのトランザクションで進め、PR の番号を `jobs.pr_number` に書く。出荷前チェックで止めた（秘密情報・CI の定義の変更）・push や PR の作成に失敗したときは `failed`
- `ci_waiting` はワーカーを占有しない。Webhook を待つ間は次のジョブを処理し、`check_suite` を受けたら再開する（タイムアウト例: 30分）。起動時の掃除（処理中のジョブを `failed` にする）の対象は `planning`〜`judging` だけで、`ci_waiting` は残す
- 同時実行1件の制約は「LLM を使う工程」に対してかける

## 4. 1ジョブの流れ

| # | 工程 | 実行場所 | 内容 |
|---|---|---|---|
| 1 | 受付 | ホスト | 署名を検証し、依頼か（コメントの最初の空でない行が `@agent`）、書き込み権限があり許可ユーザーに含まれるかを確認して jobs に追加。依頼のコメントに `eyes` のリアクションを付ける。権限のない依頼には Issue で返事をしない（ログにだけ残す） |
| 2 | 準備 | ホスト | Issue の題と本文を取り（jobs には保存しない）、インストールトークンで既定のブランチを浅く `git clone`、作業ブランチを作成。依存のインストール（`[pipeline].install_command`、既定 `pnpm install --frozen-lockfile`。空なら飛ばす）だけ、ネットワークありの一時コンテナで行う |
| 3 | 計画 | ホスト（LLM） | Issue 本文・依頼の本文・リポジトリ構成（ファイル一覧）・AGENTS.md を渡し、JSON（概要・作業手順・受け入れ条件・作業の種類）を出させる。ツールは渡さない。TypeBox で検証し、合わなければ1回だけ再要求する（2回とも合わなければ失敗）。作業の種類は工程7の自動マージ条件に使う |
| 4 | 実装 | ホスト（LLM）＋コンテナ（ツール） | 実装役の Agent ループ。ツールは `read_file` / `write_file` / `edit_file` / `bash` の4つで、逐次実行。各フックでガードレールとコンテキスト管理を行う |
| 5 | テスト | コンテナ | 実装役が完了を告げた時点で、`factory.toml` の `[pipeline].check_commands`（既定は CI と同じ `pnpm run check`）を順に実行する（LLM は使わない。対象リポジトリのファイルからコマンドを読まない）。失敗は同じ会話に steering で差し込んで実装役に戻す（1回の実装工程で上限あり）。上限を超えても通らなければ、判定せずに不合格として4へ戻る。コマンドを起動できない（作業場の異常）ときは失敗 |
| 6 | 判定 | ホスト（LLM） | 検査役に Issue・計画（受け入れ条件）・diff・テスト結果を渡し、JSON で合否・理由・受け入れ条件ごとの結果・直すべき点を返させ、TypeBox で検証する（再要求は1回まで。2回とも合わなければ失敗）。diff が空なら検査役を呼ばずに不合格。不合格なら作業ディレクトリを戻さず、理由と今の diff を付けて新しい会話で4へ戻る（上限あり）。検査役と実装役が同じモデルの設定では工程を始めない |
| 7 | PR作成 | ホスト | 作業ディレクトリの変更（判定に渡した diff と同じ範囲）を App のボットの名前で1つの commit にし（作業ディレクトリのフックとホストの git の設定を使わない）、その commit を対象に出荷前チェック（`04` 層6）を行う。秘密情報が見つかった・確かめられない変更と、`.github/workflows` を変えた変更は push せずに失敗として報告する。それ以外は作業ブランチだけを push し（強制しない）、PR を作る。自動マージの条件を満たせば auto-merge（squash）を有効にし、満たさない・有効にできなければ Draft PR にして人間に渡す。PR では Issue を参照するだけで閉じない（ステージングで戻すことがあるため）。LLM は使わない |
| 8 | CI待ち | GitHub Actions | `check_suite` の Webhook で結果を受ける。失敗したら失敗したジョブのログを取得し、要約・切り詰めて4へ戻す（上限あり） |
| 9 | マージ | GitHub | 必須チェックが全部通ると auto-merge で main にマージされる |
| 10 | デプロイ | ホスト | main への `push` を受け、デモアプリのイメージをビルドして `docker compose up` でステージングを入れ替える。`/healthz` を確認し、失敗したら直前のイメージに戻して revert PR を作る（LLM は使わない） |
| 11 | レポート | ホスト | PR を作った時点で、PR の本文にまとめレポート（計画概要、テスト結果、判定、リトライ回数、消費リクエスト数、変更、自動マージの6条件それぞれの結果と、自動マージした・しなかった理由）を書き、Issue に PR へのリンクを1回コメントする。CI結果・デプロイ結果とステージングURLは後の工程で PR の本文に書き足す。失敗時は Issue に失敗の報告だけを投稿して終了 |
| — | 本番 | 人間 | 本番デプロイは人間が行う（例: タグを打つと本番用ワークフローが動く） |

## 5. 採用する技術・ライブラリ

### ランタイム・基盤
| 用途 | 採用 | 理由 |
|---|---|---|
| ランタイム | **Node.js 24 LTS** | Pi が前提とするランタイムで、動作の確実性が最も高い。TypeScript は Node の型除去（type stripping）でそのまま実行し、型チェックは `tsc --noEmit` で行う |
| パッケージマネージャー | **pnpm** | 依存のインストールが速く、ディスク効率が良い。`package.json` の `packageManager` でバージョンを固定する（corepack） |
| HTTPサーバー | **Hono**（`@hono/node-server`） | 軽く、署名検証をミドルウェアで書きやすい。`/status` の簡易ダッシュボードにも使う |
| リバースプロキシ | **Caddy** | HTTPS 証明書を自動で取得・更新。海外のトンネルサービスを使わず、VPS で直接受ける。ステージングの公開にも使う |
| 常駐化 | **systemd** | 自動起動・再起動・journald へのログ出力 |
| 生存確認 | `/healthz`（DB に `SELECT 1`。正常 `200`／不健康 `503`、本文は状態だけ） | Caddy・systemd の再起動・ステージングの確認と同じ形で見られる。LLM は呼ばない |
| 待ち受け | `127.0.0.1:8787`（`factory.toml` の `[http]`） | ファクトリーのポートは外から直接届かないようにし、Caddy だけが転送する |
| 公開するパス | ファクトリーのドメインでは `/healthz`・`/webhook`・`/status` だけを転送し、ほかは Caddy が `404` | 外に見せる面を最小にする |
| ドメイン・TLS | Caddyfile は環境変数（`FACTORY_DOMAIN`・`STAGING_DOMAIN`・`CADDY_TLS`）で受け、値は VPS の `/etc/caddy/caddy.env` に置く | 公開リポジトリにドメインを書かない。`CADDY_TLS=internal` で予行演習と切り替えられる |
| VPS の配置 | コード `/opt/sakura-factory/app`（root の所有、git の checkout）、設定 `/etc/sakura-factory/factory.toml`、秘密情報 `/etc/sakura-factory/factory.env`（`root:factory`、`0640`）、データ `/var/lib/sakura-factory`（systemd の `StateDirectory`） | 更新（コミットかタグの checkout）で設定とデータが消えない。ファクトリーは自分のコードを書き換えられない |
| 実行ユーザー | 専用の `factory`（非 root）を `docker` グループに入れる。systemd の保護設定（`ProtectSystem=strict` など）で書き込みをデータの置き場所に限る | 作業場とステージングのコンテナを操作するため。`docker` グループは root に近いので、外から届くのは 22・80・443 だけ・SSH は鍵だけにして外側を固める |
| 版の固定 | Node.js（公式の tarball とチェックサム）、Caddy（公式の apt リポジトリ、`apt-mark hold`）、gitleaks（チェックサムを `scripts/install-gitleaks.sh` に持つ）。Docker は Ubuntu の配布物 | 予行演習と本番で同じものが入る |
| 配備 | `deploy/scripts/setup.sh`（冪等）・`update.sh` と手順書 `deploy/README.md`。ローカルの Docker で systemd 付きの Ubuntu に同じスクリプトを流す予行演習（`pnpm run deploy:rehearsal`） | VPS の無料期間（2週間）を調べものに使わない |

### GitHub 連携
| 用途 | 採用 | 理由 |
|---|---|---|
| 認証方式 | **GitHub App**（PAT は使わない） | 権限を最小限にでき、短命のトークンを使う。bot として表示される |
| SDK | **octokit**（`App` クラス）＋ **@octokit/webhooks** | App 認証、インストールトークン、Webhook 署名の検証（定数時間比較）、イベントの型付け |
| git 操作 | **git CLI**（execa） | clone / commit / push はホストでだけ行う |
| 自動マージ | **GitHub の auto-merge**（GraphQL `enablePullRequestAutoMerge`） | マージ判断を GitHub のブランチ保護に任せられる。ファクトリーが独自にマージ判定をしない |
| CI結果の取得 | `check_suite` Webhook ＋ Checks / Actions API | 失敗したジョブのログを取得して実装役へ渡す |

**GitHub App の権限**: Issues・Pull requests・Contents の読み書き、Checks・Actions の読み取り、Metadata の読み取り。イベント: `issue_comment` / `check_suite` / `pull_request` / `push`。Workflows の書き込み権限は与えない。

**App の秘密情報**: App の ID・秘密鍵・Webhook のシークレットは環境変数で渡す（`GITHUB_APP_ID`・`GITHUB_APP_PRIVATE_KEY_PATH`・`GITHUB_WEBHOOK_SECRET`）。秘密鍵は複数行なので、値ではなくファイルの場所を渡す。インストールトークンは git に環境変数（`GIT_CONFIG_COUNT`・`GIT_CONFIG_KEY_0`・`GIT_CONFIG_VALUE_0` の `http.extraHeader`）で渡し、`.git/config`・リモートの URL・コマンドラインの引数には書かない（作業場から `.git` は読めるため）。

**対象リポジトリの設定**: main のブランチ保護で CI を必須チェックにする。auto-merge を有効にする。レベルBでは必須レビューは課さない（その代わり `04` 層6の条件を満たさない PR は Draft にする）。

### エージェント・LLM（主: Pi）
| 用途 | 採用 | 使い方 |
|---|---|---|
| LLM API | **@earendil-works/pi-ai** | さくらを `openai-completions` の独自プロバイダーとして登録。互換フラグ（`supportsDeveloperRole` など）で差を吸収する。計画役・検査役はツールなしの1回呼び出し |
| エージェント実行 | **@earendil-works/pi-agent-core** | 実装役の Agent。`transformContext` / `beforeToolCall` / `afterToolCall` / `finishTurn`（停止条件。1.5.0 で `shouldStopAfterTurn` から置き換わった） / steering キューをハーネスの部品として使う |
| スキーマ | **TypeBox 1.x**（パッケージ名 `typebox`。旧名 `@sinclair/typebox` の 0.x は使わない） | Pi（`pi-schema`）が TypeBox 1.x の型の形を前提にしているため。ツール定義、検査役の JSON 出力の検証（`Value.Check`）、`factory.toml` の検証、Webhook ペイロードの絞り込み |

**Pi を選んだ理由**
- コーディングエージェントのハーネスの核として作られていて、ループ本体に手を入れずに、コンテキスト・ツール・停止条件をフックで変えられる
- ツールを自前で定義できるので、実行先をサンドボックスにできる
- `streamFn` を差し替えて、全リクエストに予算ゲートをかけられる
- OpenAI 互換の独自プロバイダーを追加でき、互換フラグで細かい差を吸収できる
**Pi で自作になるもの**（できなくなる機能はない）
| 項目 | 対応 |
|---|---|
| ガードレールの積み重ね | フックは関数1つなので、複数のチェックを順に実行し、1つでも拒否したら止める合成関数を書く |
| 承認の中断・再開 | 不要。承認は工程の境目（plan → build）で行い、ループの途中では人に聞かない |
| トレースの可視化 | イベントを購読して JSONL に保存し、実行ごとの要約を SQLite（agent_runs）に記録して `/status` で見られるようにする |
| テスト用の偽モデル | 予算ゲートの内側（ネットワークの手前）に偽の `fetch` を差し込む。本物のアダプターを通したまま、HTTP の状態コード・ヘッダー・接続の切断を再現でき、ゲートの再試行と記録もテストできる |
| リトライ | `streamFn` ラッパーに実装する（予算の計測と同じ層） |

**設計上の注意**
- ツールはデフォルトで並列実行されるため、実装役は逐次実行に設定する（同じ作業ディレクトリへの編集の衝突を防ぐ）
- 1回のLLM呼び出しで複数のツールを呼んでも、消費は1リクエスト
- 1.x（`pi-ai`・`pi-agent-core`・`pi-schema` を同じバージョンで出す）でもリリースが頻繁 → 3つを同じバージョンにそろえて完全に固定する
- パッケージ名は `@mariozechner/*` から `@earendil-works/*` に移った。古い情報が混ざりやすいので注意する

### エージェント・LLM（予備: TanStack AI）
- コア（`@tanstack/ai`）は 2026-10 に 1.0 で安定版。openaiCompatible アダプターでさくらに接続できる
- ミドルウェア（`onConfig` / `onBeforeToolCall` / `onAfterToolCall` / `onUsage`）でガードレールを積める
- harness / sandbox の機能は実験的なので使わない
- **切り替える条件**: さくらでツール呼び出しが安定しない、API変更で追従が困難、のいずれか
- 工程制御・サンドボックス・予算ゲートは自前なので、切り替えで書き直すのはLLMを呼ぶ層とフックの部分だけ

### 採用しなかったもの
| 候補 | 理由 |
|---|---|
| AI SDK 6 | 汎用性と成熟度は最も高いが、ハーネス用の仕組み（コンテキスト加工、ツールの検査、軌道修正）を自分で組むことになる |

## 6. さくらのAI Engine 固有の注意点（設計に反映）

外部記事（Zenn: RubyLLM × さくらのAI Engine）で報告されている挙動。使うモデルで必ず実機確認する。

- **`response_format`（JSON Schema）は無視される**: エラーにならずに 200 が返る → 検査役にはプロンプトで JSON を出させ、TypeBox で検証し、失敗したら1回だけ再要求する
- **`tool_choice` の扱いがモデルごとに違う**: `none` が無視されるモデル、ツール呼び出しが `<tool_call>` の XML として本文に漏れるモデルがある → ツールを使わない工程（計画・判定）では `tools` 自体を渡さない。実装役のツール呼び出しが正しく返るかを検証の最初の項目にする
- **Anthropic 互換 API は使わない**（`01` のとおり）

## 7. 計測（徹底検証パート向け）

`llm_calls` テーブルに、LLM呼び出し1回ごとに記録する（`streamFn` ラッパーで記録）:
`job_id, phase, role, model, attempt, input_tokens, output_tokens, latency_ms, status, error_kind, error`

- `error_kind` は失敗の種類（`transient` / `permanent` / `timeout` / `aborted`、成功なら NULL）。種類ごとの件数を SQL でそのまま集計するために、エラー文とは別の列に持つ

- 予算ゲートは、月初からの件数とジョブごとの件数を見て判断する（例: 月の残りが1ジョブの上限を下回ったら新しいジョブを受け付けない）
- `/status` で、今月の消費・成功率・平均処理時間・CI初回通過率・デプロイ成功率を表示する
- 検査役（Qwen3.6 と gemma-4）の比較は、同じジョブの判定工程だけを両方で実行して記録する。回帰評価（`pnpm run eval:dev`）の中で、主の検査役の最後の判定と同じ入力を比較用の検査役（`[models].verifier_alt`）に渡し、`llm_calls.phase = 'judge_alt'`（役割は `verifier`）で区別する
- ハーネスを変えるたびに回帰評価を回し、成功率と消費量を比べる（`04` 参照）
