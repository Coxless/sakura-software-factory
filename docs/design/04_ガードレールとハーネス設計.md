# ガードレールとハーネス設計

前提: エージェント層は Pi（`pi-agent-core` / `pi-ai`）。構成は `03_アーキテクチャと技術スタック.md` を参照。

## 1. 考え方

- **Agent = Model + Harness**。ハーネスとは、モデルの周りにあるもの全部（コンテキスト・ツール・制約・フィードバックループ・計測）を指す。モデルを変えなくても、ハーネスの改善で成功率は大きく変わる
- **SDKのガードレールは「やわらかい層」**。すり抜けられる前提で、本当の防御はOS（サンドボックス）と GitHub の権限で行う。SDKの層はその手前に重ねる
- **ハーネスは変えるたびに測る**。軌跡をすべて残し、決まったサンプルIssueのセットで回帰評価して、成功率と消費量で良し悪しを判断する
- **レベルBでは人間のレビューの代わりに、機械の条件で自動マージを絞る**。条件を満たさない PR は Draft にして人間に渡す。本番には人間しか出せない

## 2. ガードレールの層構造

| 層 | 場所 | 内容 |
|---|---|---|
| 1. 受付 | Webhook ハンドラー | 実行できるのは書き込み権限のあるユーザーだけ。Issue 本文やリポジトリ内のファイルは「データ」として渡し、指示として扱わない（プロンプトインジェクション対策）。CIログも同様にデータとして扱う |
| 2. 予算 | `streamFn` ラッパー | LLMを呼ぶ前に、月とジョブごとの残量を確認し、足りなければ止める。1工程の反復回数（`shouldStopAfterTurn`）、CI失敗後のやり直し回数、ジョブ全体の時間にも上限を設ける |
| 3. ツールの検査 | `beforeToolCall` | 読み書きは作業ディレクトリの中だけ。`.github/workflows`・`.env`・ロックファイル・デプロイ設定の直接編集を拒否。危険なコマンドのパターンを拒否。bashにタイムアウト |
| 4. ツールの結果 | `afterToolCall` | 長いログを切り詰める。秘密情報らしい文字列をマスクする |
| 5. サンドボックス（本当の防御） | Docker | ネットワークなし、読み取り専用のルートファイルシステム、cap-drop、非rootユーザー、CPU・メモリ・プロセス数の制限 |
| 6. 出荷前チェック・自動マージ条件 | 工程7の手前 | diffの大きさの上限、禁止パスが変更されていないかの確認、gitleaks による秘密情報のスキャン、検査役による判定。**すべて満たし、かつ `no-auto-merge` ラベルがなく、作業の種類が許可リスト内なら auto-merge を有効にする**。1つでも満たさなければ Draft PR にして人間に渡す |
| 7. CI（受入検査） | GitHub Actions ＋ ブランチ保護 | 必須チェックが全部通らないとマージされない。CI の定義（`.github/workflows`）はファクトリーが変更できない（層3と App 権限の両方で防ぐ） |
| 8. GitHub の権限 | GitHub App とリポジトリ設定 | App の権限は最小限（Workflows の書き込みなし）。ブランチ保護は必須。自動マージの対象は main（ステージング）だけ |
| 9. ステージング | VPS の deploy 層 | デモアプリは factory と別のネットワーク・リソース制限で動かす。ヘルスチェックに失敗したら直前のイメージに戻し、revert PR を作る |
| 10. 本番 | 人間 | 本番デプロイの権限はファクトリーに持たせない |

### 実装メモ
- Pi のフックは関数1つなので、`harness/compose.ts` で複数のガードを順に実行し、1つでも拒否したら止める合成関数を作る。拒否の理由はツールの結果としてモデルに返し、軌跡にも残す
- 拒否が続いて先に進めない場合は `terminate: true` で次のLLM呼び出しを省き、ジョブを失敗として終わらせる
- 自動マージの条件は `factory.toml` に置き、レポートに「どの条件で自動マージした／しなかったか」を書く

## 3. ハーネスの部品

| 部品 | Pi のフック・機能 | 内容 |
|---|---|---|
| コンテキスト | `transformContext` | AGENTS.md と計画を注入する。古いツール結果や長いテストログを圧縮・削除する |
| ツール | 自前の `AgentTool` ×4 | read / write / edit / bash。中身は `docker exec`。逐次実行 |
| 制約 | `beforeToolCall` / `afterToolCall` | 2章の層3・層4 |
| フィードバック（工程内） | steering キュー | lint / test の失敗を、ループを止めずに実装役へ戻す |
| フィードバック（CI） | 実装工程の再開 | CI で失敗したジョブ名とログ（失敗箇所の前後だけに切り詰め）を、前回の diff と一緒に渡して再開する。工程内テストで再現できない失敗は、その旨をモデルに伝える |
| 停止条件 | `shouldStopAfterTurn` | 反復回数・時間・予算の上限 |
| 計測 | イベント購読 ＋ `streamFn` | 軌跡を SQLite と JSONL に保存 |

### 対象リポジトリ側に置くもの
- **AGENTS.md**: コーディング規約、テストの実行方法、触ってはいけない場所
- **修正方法まで書いたエラーメッセージを返す lint**: エージェントへのフィードバックの質を上げる
- **CI とファクトリー内テストのコマンドをそろえる**: 工程内で通ったのに CI で落ちる差を小さくする（同じ `pnpm run check` などを呼ぶ）

## 4. 回帰評価（evals）

- `evals/` に、作業の種類ごとのサンプルIssue（テスト追加、バグ修正、lint解消など）と合格条件を置く
- ハーネス（プロンプト、ツール、ガード、コンテキスト管理）を変えるたびに全件を実行し、成功率・消費リクエスト数・処理時間を前回と比べる
- 評価は PR 作成の手前（判定工程）までで止め、CI・マージ・デプロイは回さない（評価用ブランチを main に入れないため）
- 結果は徹底検証パートの柱にする（「どのハーネス変更が、どれだけ効いたか」）
- 月3,000リクエストの枠を食うため、評価のセットは小さく保ち、実行回数も予算に入れて計画する
