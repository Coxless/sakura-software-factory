# ソフトウェアファクトリーの定義と方針

## 1. 定義

**ソフトウェアファクトリーとは、要求（Issue）を入力として、エージェントが標準化された工程（計画→実装→検証）を自動で回し、品質ゲートを通過した成果物を継続的に出力する、常時稼働の生産システムである。人間の関与度（自律レベル）は、検証の信頼性に応じて設計する変数とする。**

- 「出荷」が何を指すか（PRまでか、デプロイまでか）は定義に含めず、自律レベルで決める（3章）

### ファクトリーと呼ぶための5条件
1. **イベント駆動・非同期**: 人の指示待ちではなく、トリガー（Webhook）で稼働する
2. **工程の分業**: 計画・実装・検査を別の役割（別モデル）が担う
3. **隔離された作業場**: サンドボックス内で実行し、権限は最小限、リソースは制限する
4. **品質ゲート**: テストに通らないものは出荷しない
5. **計測可能**: リクエスト数・成功率・処理時間を記録する

### 用語の補足
- 「ソフトウェアファクトリー」という言葉自体は古い（1968年 Bemer、Microsoft 2004年など）。2026年の用法は、それをエージェント前提で解釈し直したもの
- 米国防総省（Kessel Run など）の「Software Factory」は、人間が開発するDevSecOps基盤を指す。本プロジェクトとは別の意味
- 人間レビューを一切しない「Dark Factory」（Dan Shapiro の Level 5、StrongDM）もある。人間の関与は定義の要件ではなく、自律レベルの違いとして扱う

## 2. 既存ツールとの位置づけ

- `@claude`（Claude Code GitHub Actions）、`@copilot`、`@codex` などは、すでに「Issue→PR」を実現している
- これらは単体のコーディングエージェント、つまり「工場の中の作業機械」にあたる。工程の分業・必須の品質ゲート・計測・生産管理まで含めて、初めてファクトリーと呼べる
- **打ち出し方**: 「@claude のクローン」ではなく、「単体エージェントを、国産の推論基盤の上で工程・検査・予算管理つきの工場に組み上げたもの」とする

## 3. 本プロジェクトの自律レベル（確定: レベルB）

| レベル | 出荷の範囲 | 本プロジェクト |
|---|---|---|
| A | PR作成まで。マージ・デプロイは人間 | — |
| **B** | **CI通過後に自動マージし、ステージングへ自動デプロイ。本番デプロイは人間** | **採用** |
| C | 本番まで自動（Dark Factory 寄り） | 採用しない |

- **レベルBを選ぶ理由**: 24時間稼働で「Issueを立てたら、動くものがステージングに出ている」までを見せられる。一方、本番まで自動にするだけの検証（シナリオテスト、デジタルツインなど）は月3,000リクエストでは組めないので、本番は人間が出す
- **自動マージの安全弁**: 自動マージするのはステージング向けの main だけ。条件（検査役の合格、CIの必須チェック全通過、diffの大きさ、禁止パス、秘密情報スキャン、`no-auto-merge` ラベルなし）をすべて満たしたときだけ。ステージングでヘルスチェックに失敗したら、直前の版に戻す（詳細は `03` `04`）

### CI（GitHub Actions）との役割分担
| | ファクトリー内のテスト | GitHub Actions |
|---|---|---|
| 位置づけ | 工程内検査（実装役へのフィードバック） | 受入検査（最終の品質ゲート） |
| 回数・範囲 | 1ジョブで何度も回す。lint・型チェック・関係するテストだけ | PRごと。全件 |
| 基準 | ファクトリーの基準 | チームの基準（ブランチ保護の必須チェック） |

- CIの結果は Webhook で受け、落ちたらログを実装役に戻して修正させる（リトライ上限あり）
- Actions は AI Engine のリクエストを消費しないので、重い検査は CI に任せる

## 4. 差別化の方針（確定）

| # | 項目 | 優先度 | 内容 |
|---|---|---|---|
| 1 | 推論（LLM）を国産・ZDRで閉じる | 必須 | LLMの推論は さくらのAI Engine（Zero Data Retention）だけで行い、コードが海外のモデル事業者に渡らない。ファクトリー本体・サンドボックス・ステージングは さくらのVPS で動かす。**リポジトリはチームが今使っている GitHub のまま**とする |
| 2 | 実装と検査を別モデルにする | 必須 | 実装は Kimi 系、検査・判定は別系統（Qwen / Gemma）のモデルにする。同じAIが書いて同じAIが判定する循環を避ける |
| 3 | 予算を意識した工場 | 必須 | 月3,000リクエストを生産能力として扱う。Issueごとに消費を記録・見積もり、上限を超えそうなら停止する。記事の「徹底検証」パートの材料にする |
| 4 | 工程レポート | 採用（簡易） | 逐次更新はしない。完了時（または失敗時）に、Issue / PR にまとめレポートを1回投稿する（計画概要、テスト結果、CI結果、リトライ回数、消費リクエスト数、デプロイ結果） |
| 5 | 2段階コマンド（`@agent plan` → 承認 → `@agent build`） | できれば | 余裕があれば実装する。基本は `@agent` 1回でステージングまで進める |

### #1 の表現についての注意
- 記事では「国産インフラで完結」とは書かない（GitHub は米国のサービスのため）。「推論を国産・ZDRで閉じる」と書く
- 理由づけ: 企業チームの多くはリポジトリを GitHub に置くことをすでに受け入れている。新たに問題になるのは「コードをLLM事業者に送ること」で、そこを国産・ZDRにする
- 完全に国産で閉じたい場合の発展案として、VPS 上の Forgejo（Gitea 系）に置き換える構成を展望で触れる。そのために Git ホスティングとのやり取りは1つの層にまとめておく

## 5. モデル構成

### 役割分担
| 役割 | モデル | 理由 |
|---|---|---|
| 実装 | Kimi-K2.7-Code（プレビュー、2026/7〜） | 唯一のコード特化モデルで、一番新しい |
| 計画 | Kimi-K2.7-Code、または Qwen3.6-35B-A3B | 計画は判定に使わないので、実装と同じモデルでも可。消費量を見て決める |
| 検査・判定 | Qwen3.6-35B-A3B（2026/6〜）か gemma-4-31B-it（2026/6〜） | 実装役（Kimi）とは別系統にする。同じIssueで判定精度とトークン消費を比較して決める（比較結果は記事の検証パートに使う） |
| 予備 | gpt-oss-120b（通常モデル） | 古いが、唯一の安定版（通常モデル）。プレビューモデルが停止したときの退避先 |

### 採用しないモデル
- **Kimi-K2.6**: 2026-11-09 に提供終了予定との報道がある
- **gpt-oss-120b（主力としては不採用）**: 世代が古いため、予備扱いにとどめる

### 設計上の制約
- **開発中だけ Google AI Studio（Gemini API）の無償枠を使う**: さくらの月3,000リクエストを本番の運用と検証に残すため。送るのは公開してよいデータだけ（無償枠の入出力は Google の学習と人のレビューに使われる）。常駐するファクトリーは さくら以外では起動しない。対外的には「本番の推論は さくらで閉じる。開発中は公開データだけを Gemini で試した」と書く
- **OpenAI互換の Chat Completions API で実装する**: さくらのAI Engine の無償枠で使えるのは Chat Completions だけ。Google AI Studio も OpenAI 互換の Chat Completions を持つので、提供元の設定だけで切り替えられる。Anthropic互換の Messages API で使えるのは Kimi-K2.6 のみで、K2.6 が終了すると使えなくなる見込み
- **モデル名は設定ファイルで差し替え可能にする**: プレビューモデルは予告なく終了することがある（実例: Qwen3-Coder 2モデルは 2026-07-21 に終了）。フォールバック先は gpt-oss-120b
- **無償枠（月3,000リクエスト）はチャットモデル全体の合計**: 役割ごとの消費を分けて計測する
- **今後の候補**: DeepSeek-V4.1-Flash、GLM-5.3-Flash（追加予告あり、時期は未定）

## 6. 基本フロー

1. Issue のコメントで `@agent` を呼び出す
2. GitHub Webhook → VPS の Listener → キューに投入
3. 計画: 計画役モデルがタスクを分解する
4. 実装: Kimi-K2.7-Code が Docker サンドボックス内でコードを変更する
5. 検査: lint / 型チェック / 関係するテストを実行し、検査役モデル（Qwen3.6 / Gemma 4）が判定する。不合格ならリトライ（上限あり）
6. PR作成: push して PR を作り、自動マージを予約する
7. CI: GitHub Actions の結果を Webhook で受ける。落ちたらログを実装役に戻して4へ（上限あり）
8. マージ: 必須チェックがすべて通ったら main に自動マージされる
9. ステージングデプロイ: VPS 上のステージング環境にデプロイし、ヘルスチェックする。失敗したら直前の版に戻す
10. まとめレポートを PR と Issue に投稿する。どこかで失敗した場合も、レポートを Issue に投稿して停止する
11. 本番デプロイは人間が行う
