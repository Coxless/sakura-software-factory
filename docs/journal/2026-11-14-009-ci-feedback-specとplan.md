# 009 ci-feedback の spec と plan

PR を作って `ci_waiting` で止まったジョブを、CI の結果で先へ進める工程（CI の結論の判断、マージ、CI 失敗後のやり直し、時間切れ）の spec と plan を書いた。ユーザーの指示で、判断が要るところはいったん推奨の回答で決め、PR に書いて見直してもらうことにした。

## 推奨の回答で決めたこと

| 問い | 決めたこと | 理由 |
|---|---|---|
| CI の「通過」「失敗」を何で決めるか | push した commit のチェックをすべて取り直して決める。全部終わってから判断し、成功・中立・スキップ以外が1つでもあれば失敗 | GitHub Actions はワークフローの実行ごとにチェックスイートを作るので、`check_suite` の completed はワークフローの数だけ届く。1件の知らせの `conclusion` では全体を決められない |
| CI が通ったあと、ジョブをどこまで進めるか | `ci_waiting` のまま、PR がマージされた知らせ（`pull_request` の closed）で `merged`。閉じられたら `failed` | Draft PR は人間の確認を待つので、通過のあとに時間切れを当てると失敗にしてしまう |
| 時間切れ・やり直しの上限で諦めたとき PR をどうするか | 閉じずに Draft に変えて人間に渡す | CI が後から通ったときに、ファクトリーが諦めたものが auto-merge でマージされないようにする |
| やり直しの作業ディレクトリ | 作業ブランチを取り直し、HEAD は前回の push のまま、diff の基準だけを最初の基準の commit にする | 008 の commit（HEAD からの変更）と push（強制しない）をそのまま使える。検査役には PR の変更全体を見せられる |
| やり直しのあとの振り分け | 出荷前チェックを PR の変更全体でやり直し、格下げだけ（auto-merge → Draft はあり、Draft → auto-merge はなし） | 一度人間に渡したものを機械が取り上げない |
| CI のやり直しと新しい依頼の順番 | やり直しを先にする。期限はやり直しごとに数え直す | 始めたものを先に終わらせる。最初の開始時刻で数えると、CI を待った時間で必ず期限切れになる |

## CI の判断を Worker と別のループにした

`03` 3章の「`ci_waiting` はワーカーを占有しない」を満たす方法を2つ比べた。

| 案 | 内容 | 採らなかった理由・採った理由 |
|---|---|---|
| 受付の応答のあとで判断する | Webhook を受けたら、応答のあとの処理（`defer`）でチェックを取り直す | 時間切れの見回りが別に要り、経路が2つになる |
| 見回りのループ（採用） | 受付は `jobs.ci_event_at` に印を付けて見回りを起こすだけ。見回りが印の付いたジョブと期限切れのジョブを評価する | 知らせの取りこぼし（GitHub は失敗した配送を自動では再送しない）の拾い直しも同じ経路になる |

同じ知らせが2回届いたり、評価中に次の知らせが届いたりしても重複しないように、`ci_status` の更新を「`ci_waiting` で `pending` で、評価した commit のとき」の条件付きの UPDATE にし、記録・PR の本文・報告はその更新が1行を変えたときだけ書く。印は評価の前に読んだ値と同じときだけ消す。このために `jobs` に列を5つ足した（`base_sha`・`head_sha`・`ci_status`・`ci_deadline`・`ci_event_at`）。

## やり直しのフィードバック

- ログは DB に保存せず、やり直しのときに Worker が取り直す（大きく、秘密情報を含みうる）
- Actions のチェックの ID はジョブの ID と同じなので、`/actions/jobs/{id}/logs` でジョブのログを取る。それ以外のチェックは `output` の文
- 切り詰めは `##[error]` の行の前 20 行・後 10 行。なければ `error`・`FAIL` などの行、それもなければ末尾 200 行。前を多めに残すのは、テストの失敗の詳細がエラーの行より前に出るため
- 実装の前に工程内テストを1回回し、通ったら「ファクトリー内では再現しない」と伝える（`04` 3章。LLM を使わずに判断できる）

## まだ分かっていないこと

- App が GitHub Actions のスイートの `check_suite.completed` を本当に受け取れるか（ドキュメントでは Checks の読み取り権限があれば受け取れる。`requested`・`rerequested` はスイートを作った App にだけ届く）
- Actions のジョブのログがインストールトークンで 302 のリダイレクトとして返り、octokit がプレーンテキストで受け取れるか
- `convertPullRequestToDraft` が有効な auto-merge を外すか

どれもやり直しで実装役（LLM）を使うので、AI解禁のあとにテスト用のリポジトリで確かめる。
