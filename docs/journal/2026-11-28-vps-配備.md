# 2026-11-28 VPS解禁: さくらのVPS への配備（006）

`deploy/README.md` を上から流した。11-27 の夜に始め、日付をまたいだ。

## VPS

- さくらのVPS 4G プラン（仮想4コア・メモリ 3.8GiB・SSD 197GB）、Ubuntu 24.04 LTS、クレジットカード払いで2週間の無料お試し（11-27〜12-10）
- 2G との比較: ジョブのコンテナの上限が `memory_mb = 2048` なので、2G でもスワップと `memory_mb = 1024` で動く見込みはあった。お試し期間は無料なので 4G にした。本契約に移すなら最低利用期間3か月で 2G 約5,500円・4G 約11,200円
- ドメインは買わず、[sslip.io](https://sslip.io/) を使った（`factory.<IP をハイフンでつないだもの>.sslip.io` と `staging.…`）。IP を名前に埋め込むだけで A レコードになり、Caddy が Let's Encrypt の証明書（発行元 `YE2`）をそのまま取れた

## つまずいたこと

### SSH の鍵: ssh-agent が拒否する

手元の `ssh-keygen` を Claude Code の `!` から実行すると、パスフレーズの入力に `ssh_askpass` が要り（`exec(/usr/bin/ssh-askpass): No such file or directory`）、空のパスフレーズで鍵ができた。その後 `ssh` は `sign_and_send_pubkey: signing failed for ED25519 ... from agent: agent refused operation` で失敗した。GNOME の鍵の管理（`SSH_AUTH_SOCK=/run/user/1000/gcr/ssh`）が鍵を扱えていなかった。運用者が別の端末でパスフレーズを付けて一度ログインしたあとは、agent 経由で入れるようになった。

### setup.sh: 鍵があるのに「authorized_keys に SSH の鍵がありません」

```
ERROR: ファイアウォールと SSH で失敗しました: authorized_keys に SSH の鍵がありません。鍵でログインできるようにしてから流し直してください
```

さくらの Ubuntu では鍵は `ubuntu` ユーザーにだけあり、`/root/.ssh/authorized_keys` はない。確認が `cat /root/.ssh/authorized_keys /home/*/.ssh/authorized_keys 2>/dev/null | grep -qE ...` で、`set -o pipefail` のもとでは `cat` の失敗（ファイルがない）がパイプ全体の失敗になり、`grep` が一致しても止まっていた。予行演習（Docker の Ubuntu）では root に鍵を置いていたので気づかなかった。`grep -qsE ... <ファイル>...` に直した（GNU grep は `-q` で一致があれば、読めないファイルがあっても 0 を返す）。

### setup.sh を直した版で流すときの落とし穴

- `setup.sh` の「コードの取得」は clone がなければ clone するだけで、チェックアウトは最後の `update.sh` で行う。直した版の `setup.sh` を使うには、先に `git checkout` してから流す必要がある
- `update.sh FETCH_HEAD` は、中の `git fetch --tags origin` が `FETCH_HEAD` を書き換えるので、意図しない古いコミット（`2f1d997`）をチェックアウトした。ブランチは `origin/<ブランチ名>` で渡す
- `/opt/sakura-factory/app` は root の持ち物なので、`ubuntu` から `git` を使うと `detected dubious ownership` になる。`sudo git` で扱う

### 作業場のイメージのビルドが1回失敗した

1回目の `update.sh` で `docker build --quiet -t factory-sandbox:latest sandbox` が終了コード 1 で失敗した。`--quiet` なので理由は出ていない。直後に `--quiet` なしで流すと成功し、以後は再現しなかった。初回の `node:24-slim` の取得か apt の一時的な失敗だったと見ている。VPS の Docker は buildx がなく、従来のビルダー（`DEPRECATED: The legacy builder is deprecated`）で動いている。

### ステージングのアプリが package.json を読めない（010）

配備の直後、ファクトリーは `factory-sandbox` の main の未デプロイの push を拾ってデプロイを始めた（`停止中の main への push をデプロイに積みました`）。コンテナは再起動を繰り返し、ヘルスチェックに落ちてデプロイ1は `failed` になった。

```
Error: Cannot read package config /app/package.json: permission denied.
```

ファクトリーは systemd の `UMask=0027` で動くので、取得したファイルが `0640` になる。Dockerfile の `COPY` は権限をそのまま写すので、非 root（`65534`）のアプリが読めない。予行演習と `staging.docker.test.ts` では umask が 0022 だったので起きなかった。ビルドの直前に、取得したディレクトリ（`.git` を除く）にほかのユーザーの読み取り（ディレクトリは実行も）を足す `makeReadableByOthers` を入れた。置き場所の StateDirectory は `0750` なので、ホストのほかのユーザーからは見えないまま。Dockerfile の `COPY --chmod` は BuildKit が要り、この VPS の従来のビルダーでは使えないので、ファクトリーの側で直した。

| 確認 | 結果 |
|---|---|

| `/healthz`（外から） | `{"status":"ok"}` |
