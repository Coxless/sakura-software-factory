# 009 ci-feedback の実装

## drizzle-kit が出したマイグレーションは、そのままでは既存の行を壊す

`jobs` に CI の列を5つ足して `pnpm exec drizzle-kit generate --name ci_feedback` を流したら、列の追加ではなくテーブルを作り直す SQL が出た（CHECK 制約 `jobs_ci_status_check` を足したため）。

```sql
CREATE TABLE `__new_jobs` ( ... `ci_status` text, ...
  CONSTRAINT "jobs_ci_status_check" CHECK("__new_jobs"."ci_status" IN ('pending', 'passed', 'failed')) );
INSERT INTO `__new_jobs`(..., "base_sha", "head_sha", "ci_status", "ci_deadline", "ci_event_at", ...)
  SELECT ..., "base_sha", "head_sha", "ci_status", "ci_deadline", "ci_event_at", ... FROM `jobs`;
DROP TABLE `jobs`;
```

元の `jobs` にない列を SELECT している。SQLite は解決できない二重引用符の識別子を文字列のリテラルとして扱うので、エラーにならずに `ci_status` に文字列 `'ci_status'` が入る。今回は CHECK に当たって失敗するが、CHECK のない列（`base_sha` など）には `'base_sha'` という文字列が黙って入る。さらに `job_events`・`llm_calls`・`agent_runs`・`deployments` が `jobs` を外部キーで参照しているところで `DROP TABLE jobs` をしている（`PRAGMA foreign_keys=OFF` はトランザクションの中では効かない）。

結論: `drizzle/0004_ci_feedback.sql` を `ALTER TABLE jobs ADD ...` の5文と索引に手で書き直した。CHECK は列の制約として `ADD` に付けられる（SQLite は `ALTER TABLE ADD COLUMN` で CHECK を許す）。スナップショット（`drizzle/meta/0004_snapshot.json`）は drizzle-kit が出したままにした（次の generate の差分の基準になる）。空のメモリ DB でマイグレーションを流すテストは通っていたので、既存の行がある DB での確認は手で行う必要がある。

まだ分かっていないこと: 0001（`llm_calls.error_kind`）も同じ形の SQL だった。0001 は `llm_calls` に行がない時点で流したので問題が出ていないが、同じ手順で列を足すときは毎回 SQL を読む。

## 引数の名前と、あとの `const { kind }` がぶつかった

Worker の `processJob` に `kind: "new" | "ci_retry"` の引数を足したら、同じ関数の後ろにある `const { kind, message, detail } = classifyOutcome(result);` と同じ名前になり、`tsc` が `TS2448: Block-scoped variable 'kind' used before its declaration` を出した。テストは 30 件中 30 件が 5 秒の待ちで落ちた（Worker の処理が `ReferenceError` で毎回止まる）。引数を `claimKind` に改名して直した。

## 実装役へのフィードバックの上限が2段になる

CI のログの上限（`[pipeline].max_ci_log_chars`、既定 12000）で切り詰めたあと、004 の `buildInitialContext` がフィードバック1件あたり `max_feedback_chars / 件数`（既定 30000 / 3 = 10000）でもう一度切り詰める。既定のままだと CI の失敗の欄は 10000 文字で中央が省かれる。どちらも上限以内には収まるので、そのままにした。012 の回帰評価で、CI のフィードバックの長さと直った割合を見て調整する。
