# 010 staging-deploy の spec と plan

009 まででジョブは `merged` で止まっていた。main への push を受けてステージングに出す部分を作る。人間の確認が要る決定は、007〜009 と同じく推奨で決め、PR で見直すことにした。

## 比べて決めたこと

### push をまとめるか、1件ずつ出すか

- まとめる（待っている push のうち最新だけを出す）: 速いが、飛ばした commit のジョブを `deployed` にするには「最新の commit にその変更が含まれるか」を git で確かめる必要があり、記録も「どの commit がいつ出たか」が欠ける
- 1件ずつ（届いた順）: 記録が1件ずつ残り、記事の実測（デプロイ成功率・ロールバック回数）にそのまま使える

デモの規模（push は1日に数件、ビルドは数十秒）では1件ずつで足りるので、1件ずつにした。

弱点: A がヘルスチェックに失敗して戻したあと、すでに積まれていた B（A を含む）も同じ理由で失敗し、B の revert PR も作られる。B 自体は無実でも打ち消す PR が出る。revert PR は自動でマージしないので、人間が見て閉じればよい、として受け入れた。

### push とジョブの結び付け

- 案1: 009 の見回りが `merged` にするときに、PR のマージ commit を `jobs` に書き、push の `after` と突き合わせる → マージの知らせ（`pull_request` closed）より push の知らせが先に届くと結び付かない
- 案2: デプロイの実行器が `GET /repos/{o}/{r}/commits/{sha}/pulls` でマージ commit から PR を引く → 届く順に依存しない

案2にした。ジョブがまだ `ci_waiting` なら、実行器が PR のマージを確かめて `merged` に進めてから `deploying` にする（009 の見回りの「マージ済み」の処理を `markMerged` として切り出して共有する）。

### revert PR を自動でマージするか

自動マージの6条件の1つは「検査役の合格」で、revert の commit は検査役を通っていない。条件を緩めるより、人間に渡す方が筋が通るので、auto-merge を有効にしない通常の PR（Draft でもない）にした。ステージングはすでに直前の版に戻っているので、急ぐ理由もない。

### ビルドの失敗で revert PR を作るか

設計（`04` 層9）は「ヘルスチェックに失敗したら」revert PR。ビルドの失敗はネットワーク（依存の取得）など作業場の外の原因もありうるし、ステージングは前の版のまま動いている。revert PR は作らず、ジョブを `failed`（`deploy_failed`）にして Issue に報告するだけにした。デモ用のリポジトリの CI で `docker build` も回すので、Dockerfile の誤りはマージの前に見つかる。

### compose の定義の置き場所

設定（`factory.toml`）で場所を変えられるようにすると、`/etc` の設定からファクトリーのコードの外のファイルを読ませることになる。`deploy/staging/compose.yaml` に固定し、渡すのはイメージの名前とポートだけにした。対象のリポジトリの compose は読まない（エージェントが書き換えられるファイルで、ステージングの隔離を緩められるため）。

### 起動時の途中のデプロイ

やり直す案も考えたが、再起動の原因がデプロイ自体だと繰り返す。007 の起動時の掃除と同じく「途中のものは失敗にして報告」にした。停止中に届かなかった push は、起動時に既定のブランチの先頭を取り直して拾う（GitHub は失敗した配送を自動では再送しない）。
