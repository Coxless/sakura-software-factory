### 計画役の JSON の再要求: 見当違いの指摘になっていた

計画役の1回目の出力は、Issue に書かれた `{"error": "text is required"}` を文字列の中にエスケープせずに写していた。

```
"... 存在しない場合は `400` と `{"error": "text is required"}` を ..."
```

全体は `JSON.parse` できない。取り出し処理（`extractJsonObject`）は、括弧を数えて最初に読めるオブジェクトを探すので、中の `{"error": "text is required"}` を拾った。それをスキーマで検証したため、再要求の文は次のようになった。

```
前回の出力は決められた形に合いませんでした。
- /summary: 必須の項目がありません
- /steps: 必須の項目がありません
- /acceptance_criteria: 必須の項目がありません
- /work_type: 必須の項目がありません
```

2回目は正しく返ったが、原因と違う指摘で、2回目も同じ誤りなら失敗になっていた。直したこと:

- 計画役・検査役のシステムプロンプトに「文字列の値の中の `"` は `\"` とエスケープする（Issue の JSON を写すときも同じ）」を足す（1回目で正しく出させ、リクエストを節約する）
- 最初の `{` から最後の `}` までが JSON として読めないときは、再要求で構文の誤り（`JSON.parse` の理由）とエスケープの指示を伝える

PR #18 でこれを VPS に入れたあと、Issue の本文に JSON を3つ書いた #18（下）では、計画役は再要求なしの1回で通った。

## Issue #42「countWords のテストに絵文字と数字を足す」（test → job 29）: 条件付きの依頼は合格できない

元の本文（あとで書き直した）:

```
`src/text.test.js` の `countWords` に、次のテストを足してください。

- 絵文字だけの語（`"🍣 🍺"` → `2`）
- 数字（`"2026 年 11 月"` → `4`）
- 英字と日本語の混在（`"Node.js と pnpm"` → `3`）

今の実装で通らないものがあれば、Issue にそう書いて止めてください（コードは変えない）
```

結果は `judging` で止まった（`judge_rejected`、やり直し 2 回、リクエスト 26 件、2 ファイル +17 −3、push なし）。検査役の理由:

```
Issueの指示「今の実装で通らないものがあれば...コードは変えない」およびPlanの受け入れ条件「通らない場合は Issue に失敗ケースを報告しコードを変更していない」に反し、diff で src/text.js が変更されている。
```

### 何が起きたか

1. 今の `countWords` は、`/[\p{L}\p{N}]/u` に一致する文字を含む語だけを数える（既存テスト「記号だけの語を数えない」）。絵文字は `\p{So}` なので `"🍣 🍺"` は 0 になり、絵文字のテストが落ちる
2. 実装中の steering がテストの失敗を返す。実装役のシステムプロンプトは「失敗していれば直してから作業を終えます」なので、実装役は `src/text.js` の正規表現と filter を変えた
3. 検査役は Issue の「コードは変えない」を正しく読んで不合格にした。やり直しでも同じ流れになり、上限で止まった

検査役は正しい。食い違いは、実装役に「Issue に書いて止める」終わり方がないこと。実装役は Issue にコメントできず、終わり方は「テストが通る diff を作る」か「失敗する」しかない。そのため「通らなければ報告して止めて」という条件付きの依頼は、どちらに転んでも合格できない。計画役もこの条件をそのまま受け入れ条件に写していた。

### 対応

- ファクトリーは変えず、Issue を「コードを変える作業」だけに書き直した。絵文字を語として数えるかは仕様の判断（今は記号扱い）なので外し、通るテスト2件（数字、英字と日本語の混在）だけを残した。本文に「実装（`src/text.js`）は変えません」と書いた
- 実装役に `report_and_stop(reason)` のような終わり方（ジョブを「人に返した」状態で終え、理由を Issue に投稿する）を足す案は、設計の変更と判定・報告の流れの見直しが要るので、今回は入れない

### まだ分かっていないこと

- 計画役が「Issue への報告」のようなファクトリーにできない受け入れ条件を書いたとき、計画の段階で弾くべきか

### job 36: 検査役の JSON が2回とも読めず、judging で止まる

Issue には次のように報告された。

```
判定できません（出力が2回とも決められた形に合いません）: 出力から JSON オブジェクトを見つけられませんでした
```

trace（`/var/lib/sakura-factory/traces/job-36.jsonl`）を見ると、2回の失敗は原因が別だった。

1. 1回目（25.1 秒、出力 3,706 トークン、`stopReason: stop`）: 判定そのものは `"verdict": "pass"` で、内容も正しかった。ただし `criteria[0].note` の中に、Issue の仕様をそのまま `{"error":"not found"}` と書いていた。値の中の `"` をエスケープしていないので、JSON として読めなかった

   ```
   "note": "…content-type: application/json; charset=utf-8と{"error":"not found"}を返す実装とした。…"
   ```

   検証のエラー: `/: JSON として読めません（Expected ',' or '}' after property value in JSON at position 396 (line 1 column 397)）。文字列の値の中の " は \" とエスケープしてください`

2. 2回目（再要求。55.4 秒、出力 8,192 トークン、`stopReason: length`）: 本文が空だった。8,192 は `src/llm/provider.ts` の `MAX_TOKENS` で、出力の上限までを本文の外（推論）で使い切ったと見ている。1回目も、本文は 1,000 字ほどなのに出力が 3,706 トークンあり、推論の分が含まれている

- 1回目の失敗は、JSON が値に入る Issue（応答の形を `{"error":…}` で書いたもの）なら、また起きうる。ほかの JSON 系の Issue（#45・#52）では起きていないので、毎回ではない
- 2回目の失敗は、エスケープを直させる再要求で推論が長引いた。再要求は1回目の出力全体を会話に入れて返すので、1回目より入力が増える（2,101 → 2,560 トークン）

### job 42（#44 CHANGELOG）: 浅いクローンで履歴が見えず、1件だけの CHANGELOG が合格する

できた `CHANGELOG.md` は次の 1 件だけだった。

```
# Changelog

## 2026-11-28

- README の「HTTP API」節の応答例を、実際のサーバー応答および `src/server.test.js` と一致するように修正
```

Issue では「利用者に見える変更（API の追加・挙動の変更）」を求めた。それなのに `/api/stats` の追加、413、404 の JSON 化、`lines` フィールドなどが抜けている。しかも載っている 1 件は docs の修正だった。

trace で実装役の動きを追った（19 ターン、21 リクエスト）。

1. 計画どおりに `git log --first-parent --merges main --oneline` を打つと、何も返らない
2. `git log --all --oneline -50` などを何度か試したあと、`git rev-parse --is-shallow-repository` で `true` を確かめた
3. `git fetch --unshallow origin main` を試したが、`error: cannot open '.git/FETCH_HEAD': Read-only file system` で失敗した。サンドボックスの `.git` は読み取り専用でマウントしている（`src/sandbox/options.ts`）。`git ls-remote` も `Could not resolve host: github.com` で失敗した（ネットワークなし）
4. 見える 1 コミット（`e4be6a7`、#83）だけで `CHANGELOG.md` を書いた。最後のメッセージで、そのことを自分から書いていた

   ```
   `git log` で確認できる main のコミットが 1 件（README の HTTP API 応答例修正）しかなく、マージコミットは確認できなかったため、利用者に見える README の修正内容を 2026-11-28 の日付見出しで 1 件記載
   ```

検査役は 5/5 で合格にした。受け入れ条件 2 には `READMEの応答例修正は利用者向けドキュメント整備として妥当と判断` と書いている。検査役に渡すのは `<issue>`・`<instruction>`・`<plan>`・`<commit>`・`<diff>`・`<checks>` だけで、実装役の最後のメッセージは渡さない。そのため「履歴が 1 件しか見えなかった」ことを検査役は知らず、diff だけ見れば条件に合っているように見えた。

原因は重なっている。

- クローンが `--depth 1`（`src/github/git.ts` の clone）。サンドボックスからは深くできない（`.git` は読み取り専用、ネットワークなし）。どちらも意図した制限
- そもそも依頼の前提が合っていなかった。factory-sandbox の main は PR をすべて squash でマージしているので、全履歴を取ってもマージ commit は 0 件だった（`git fetch --unshallow` したあとの `git log --merges --oneline | wc -l` が `0`、コミットは 39 件）。Issue の「マージ commit から拾う」は、この repo では成り立たない
- 実装役は「できなかった」と気づいたのに、job 29 と同じく、人に返して止める終わり方がない。そのため、できる範囲で diff を作って終えた
