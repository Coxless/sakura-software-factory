### 計画役の JSON の再要求: 見当違いの指摘になっていた

計画役の1回目の出力は、Issue に書かれた `{"error": "text is required"}` を文字列の中にエスケープせずに写していた。

```
"... 存在しない場合は `400` と `{"error": "text is required"}` を ..."
```

全体は `JSON.parse` できない。取り出し処理（`extractJsonObject`）は、括弧を数えて最初に読めるオブジェクトを探すので、中の `{"error": "text is required"}` を拾った。それをスキーマで検証したため、再要求の文は次のようになった。

```
前回の出力は決められた形に合いませんでした。
- /summary: 必須の項目がありません
- /steps: 必須の項目がありません
- /acceptance_criteria: 必須の項目がありません
- /work_type: 必須の項目がありません
```

2回目は正しく返ったが、原因と違う指摘で、2回目も同じ誤りなら失敗になっていた。直したこと:

- 計画役・検査役のシステムプロンプトに「文字列の値の中の `"` は `\"` とエスケープする（Issue の JSON を写すときも同じ）」を足す（1回目で正しく出させ、リクエストを節約する）
- 最初の `{` から最後の `}` までが JSON として読めないときは、再要求で構文の誤り（`JSON.parse` の理由）とエスケープの指示を伝える

PR #18 でこれを VPS に入れたあと、Issue の本文に JSON を3つ書いた #18（下）では、計画役は再要求なしの1回で通った。

## Issue #20「トップページに README を表示する」（feature → job 8）: ロールバックと revert PR

ステージングの安全網を本番で確かめるため、手元では動くがイメージでは動かない変更になる依頼をわざと出した。factory-sandbox の `.dockerignore` は `*.md` を除き、Dockerfile は `src` だけをコピーする。そこに「README を起動時に一度だけ読む」と頼んだ。

- 実装役は `server.js` の先頭で `const readmeBody = await readFile("README.md", "utf-8");` とした。工程内テスト・検査役・CI（`pnpm run check` と `docker build`）はすべて通過した。検査役には Dockerfile・`.dockerignore` が渡らないので、見つけられないのは仕様どおり
- 実装役のリクエストは 10 件（ほかのジョブは 4〜5 件）。受付から Draft PR（#21、`unmet: ["work_type"]`）まで 110 秒
- 運用者がマージ → デプロイ 11 は `ヘルスチェックが通りませんでした（30 回、最後: ECONNREFUSED）` で `failed`（`failed_stage = health`）。所要時間 85 秒
- 直前のイメージ `sakura-staging-app:fd8aa8a25550`（#19 の版）に戻し、戻した版のヘルスチェックは通過した
- revert PR #22「Revert be1b10a（ステージングのヘルスチェックの失敗）」が作られた。auto-merge は有効にしていない。打ち消す範囲は `fd8aa8a..be1b10a`（4ファイル）
- Issue #20 にロールバックの報告が1回出て、job 8 は `rolled_back` になった

レベルB（ステージングまで自動、本番は人間）の安全網が、人間のレビューをすり抜けた変更をステージングで止める流れが、本番で一通り動いた。

### 気づいたこと

- 報告のヘルスチェックの理由は `ECONNREFUSED` だけで、コンテナが落ちた本当の理由（`ENOENT: ... 'README.md'` のはず）は出ていない。直すには、失敗したコンテナのログの末尾を報告に足す必要がある
