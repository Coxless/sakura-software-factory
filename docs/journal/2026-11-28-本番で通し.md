## 見つけたバグ: デプロイがジョブに結び付かず、job 2 が `merged` のまま残る

デプロイ 4 は `succeeded` だったが、`deployments.job_id` が NULL で、job 2 は `merged` から進まなかった。`/status` では job 2 が進行中に数えられ、成功率が `0/1`（`in_progress: 1`）と出た。PR の本文のデプロイの欄も書かれない。

- 実行器は push の commit から `GET /repos/{o}/{r}/commits/{sha}/pulls` で PR を引いてジョブを探す（010 research R3）
- push の受付はマージの約 0.5 秒後（`ci_event merged` が 1795792435801、push の `deploy_queued` が 1795792435817、実行器の開始が 1795792436303）
- あとで同じ API を叩くと PR #11 が返り、`merge_commit_sha` も push の commit（`6c6f6e5`）と一致した。マージの直後は索引がまだ更新されておらず、空が返ったと見ている（空が返った瞬間そのものは記録していない）
- テスト（偽の GitHub）では索引の遅れがないので気づかなかった

直し方: 索引で見つからなければ、同じリポジトリで `ci_waiting`・`merged` のジョブの PR を `GET /pulls/{n}` で直接引き、マージ済みで `merge_commit_sha` が push の commit と一致するものに結び付ける。PR を直接引く API には索引の遅れがない。待ち時間を入れて索引を引き直す案は、どれだけ待てばよいかが決まらないので採らなかった。未マージの PR の `merge_commit_sha` は試しのマージ commit なので、マージ済みのときだけ使う。
