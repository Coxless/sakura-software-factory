# 2026-11-28 012 の回帰評価と検査役の比較を さくらで回す

`evals/` の5ケースを さくらのAI Engine で1回ずつ回し、検査役の Qwen3.6 と gemma-4 を同じ入力で比べた。

## どこで流したか: VPS で、本番とは別の DB に

予算ゲートに数えさせるため、スモークテストと同じく VPS で流した。ただし本番の DB（`/var/lib/sakura-factory/factory.db`）は使わなかった。

- 評価の実行器は、ケースごとに `jobs` に `repo = "eval:<セット>/<ケース>"` の行を `planning` で作り、終わっても終わりの状態（`deployed`・`rolled_back`・`failed`）にしない。本番の DB に入れると、`/status` の「進行中」に残り続ける
- ファクトリーの起動時の掃除（`recoverOnStartup`）は、`planning`〜`judging` のジョブを `failed`（`restarted`）にして報告しようとする。次の `update.sh` で評価の行がすべて失敗に数えられ、成功率が崩れる。作業場（`work_dir`）の残骸もまとめて消すので、評価中に再起動すると評価の作業場も消える

そこで `/etc/sakura-factory/factory.toml` を写した `/etc/sakura-factory/eval.toml` を作り、次だけを変えた。

```toml
verifier_alt = "preview/gemma-4-31B-it"
monthly_requests = 2945   # 3000 − その時点の本番の消費 55
database_path = "/var/lib/sakura-factory/eval.db"
trace_dir = "/var/lib/sakura-factory/eval-traces"
work_dir = "/var/lib/sakura-factory/eval-work"
eval_dir = "/var/lib/sakura-factory/evals"
```

実行は `factory` ユーザーで、`factory.env` を読んで `node src/eval-dev.ts --allow-sakura` を動かす。`eval-dev.ts` は `git status` でハーネスの版を記録するが、`/opt/sakura-factory/app` は root の持ち物なので、`factory` から `git` を使うと `detected dubious ownership` になる。`GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=safe.directory GIT_CONFIG_VALUE_0=/opt/sakura-factory/app` を渡して避けた。

```bash
sudo runuser -u factory -- /var/lib/sakura-factory/run-eval.sh --self-check        # 5/5 ok
sudo runuser -u factory -- /var/lib/sakura-factory/run-eval.sh --max-requests 300
```

評価で使った分（48）は、本番の `monthly_requests` から引いて 2952 にした（次の再起動で効く）。

### 検査役の比較

どちらも 5/5 で、精度の差は出なかった。全ケースで実装が合格だったので、誤合格（壊れた実装を通す）を試す場面がなかった。精度を比べるには、実装役が誤りやすいケースか、わざと壊した diff を判定させるケースが要る。

差が出たのはコストで、gemma-4 は出力が Qwen3.6 の約 1/6（1 回あたり 348 と 2,084 トークン）、応答時間が半分（5 秒と 10 秒）。Qwen3.6 はスモークテストのときから、短い問いでも出力が多い（思考の分が出力に数えられている可能性）。

## さくらのレート制限: 1分に約10回

5ケースの全部で、実装工程の途中に `429` が1回ずつ出た。

```
{"level":40,...,"model":"preview/Kimi-K2.7-Code","attempt":1,"kind":"transient","httpStatus":429,"delayMs":60000,"msg":"LLM 呼び出しを再試行します"}
```

`429` の直前 60 秒の呼び出しの数を `llm_calls` から数えると、4回とも 9〜10 回だった。1分に約 10 回が上限だと見ている（さくらの資料で確かめてはいない）。予算ゲートは `429` を一時的な失敗として 60 秒待って再試行し、すべて次の試行で通った。デモの job 8（実装役 10 回）で出た `429` も同じ原因と見られる。

- 1ジョブの処理時間のうち 60 秒は、この待ちによるもの（各ケースの時間の多くを占める）
- 予算ゲートは `429` の行も1回として数える。さくらが `429` を月の枠に数えるかは分かっていない（数えない場合、ゲートが少し厳しく数えるだけで、枠を超えることはない）
