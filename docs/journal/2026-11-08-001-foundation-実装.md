## pnpm 12: ビルドの許可は `allowBuilds`、しかも止めるとエラーになる

dev 依存を入れたら、インストール自体がエラーで止まった。

```
Error: ERR_PNPM_IGNORED_BUILDS
  × adding a new package
  ╰─▶ Ignored build scripts: esbuild@0.18.20, esbuild@0.25.12, esbuild@0.28.2
  help: Run "pnpm approve-builds" to pick which dependencies should be allowed
        to run scripts.
```

- pnpm 10 までは「警告して飛ばす」だったが、12 はエラーにする
- `pnpm approve-builds esbuild` を実行すると、`pnpm-workspace.yaml` に `allowBuilds: { esbuild: true }` が書かれた。設定キーは `onlyBuiltDependencies` ではなく `allowBuilds`
- esbuild が3つの版で入っているのは drizzle-kit の都合（`@esbuild-kit/*` は非推奨の警告も出る）

## better-sqlite3 13 はビルド不要だった

ネイティブモジュールなのでビルドの許可が要ると思っていたが、何もしなくても `require("better-sqlite3")` が通った。パッケージを見ると `prebuilds/` に linux-x64・linux-arm64・musl・darwin・win32 の `.node` が同梱されていて、インストールスクリプト自体がない（ダウンロードが 11.4 MB と大きいのはこのため）。SQLite のバージョンは 3.53.4。

## pnpm 12 は公開直後のパッケージを入れない

`typebox@1.4.6`（当日公開）を入れたら、pnpm が黙って `pnpm-workspace.yaml` に除外を足していた。

```
Added 1 entry to minimumReleaseAgeExclude in pnpm-workspace.yaml
(set minimumReleaseAgeStrict to true to gate these updates with a prompt):
  typebox@1.4.6
```

- サプライチェーン攻撃対策（公開直後の版を一定期間入れない）が既定で有効になっている
- 除外を残すと対策の意味がないので、除外を消して 1.4.5（2日前の公開）に下げた。除外を消すとロックファイルが方針違反で弾かれたため、ロックファイルを作り直した
- 「最新版を完全固定」より「待ち期間を満たす最新版を完全固定」が正しい

## npm を止めるのは `devEngines`

`packageManager` だけでは npm は止まらない（analyze で気づいた）。`devEngines.packageManager` に `onFail: "error"` を書いたら、npm 11.19.1 が期待どおり止まった。pnpm 12 は `packageManager` と `devEngines` の両方があっても文句を言わない。

```
npm error code EBADDEVENGINES
npm error EBADDEVENGINES Invalid name "pnpm" does not match "npm" for "packageManager"
```

## TypeScript 7 と Node 24 の型除去は問題なし

`tsc --noEmit`（Go 製の TS 7.0.2）、`node src/main.ts`（型除去）、Vitest 5、drizzle-kit の TS 設定ファイルの読み込みのどれも、追加の設定なしで動いた。`erasableSyntaxOnly` と `.ts` 付きの import で統一したのが効いている。

## TypeBox 1.x のエラーは ajv と同じ形

`Value.Errors` は `{ keyword, instancePath, params, message }` を返す。`additionalProperties: false` に違反すると、`keyword: "additionalProperties"` と `keyword: "boolean"`（"schema is false"）の2件が重なって出るので、後者は捨てた。`Value.Default` は表ごと省略された場合にも、表に `default: {}` を付けておけば中の既定値まで埋める。

## drizzle の migrator は自分でトランザクションを張っていた

失敗時に変更を残さないために自前で包むつもりだったが、`drizzle-orm/sqlite-core/dialect.js` の同期版 `migrate` を読むと、`BEGIN` → 全マイグレーション → `COMMIT`、例外なら `ROLLBACK` になっていた。壊れた SQL を2文目に入れたテストで、1文目の `CREATE TABLE` も残らないことを確かめた。管理テーブル `__drizzle_migrations` だけはトランザクションの外で作られる。

`drizzle-kit generate` は名前を自動で付ける（`0000_wealthy_maria_hill.sql`）ので、`--name foundation` で作り直した。CHECK 制約は `"budget"."monthly_limit" >= 1` のようにテーブル名付きで出力されるが、SQLite はそのまま受け付けた。

## ログの伏せ字: 計画の前提が逆だった

research では「pino の `formatters.log` はシリアライザーのあとに呼ばれる」と書いていたが、実際は**前**だった。テストで `err` の中のトークンがそのまま出た。

```
"err":{"type":"Object","message":"clone failed: ghp_aBcD…","stack":"Error: clone failed: ghp_aBcD…
```

原因は2つ重なっていた。

1. `formatters.log` の時点では `err` はまだ `Error`。そこで `pino.stdSerializers.err` で直列化してからたどるようにしたが、その戻り値は独自のプロトタイプを持つオブジェクトで、「ふつうのオブジェクトだけをたどる」判定から外れて素通りしていた
2. そのあと pino 標準の `err` シリアライザーがもう一度かかり、`type` が `Object` に上書きされていた

→ `Error` は自前で `{ type, message, stack, cause }` にしてから伏せ、標準の `err` シリアライザーは素通しにした。`logger.error({ err })` と `logger.error(err)` の両方で伏せられることを確かめた。analyze で「伏せ字が浅い」と指摘してテストを先に足していたので、ここで確実に見つかった。

## Node: `/proc` の下で `mkdirSync({ recursive: true })` が返ってこない

「DB を作れない場所なら終了コード 1 で止まる」ことを確かめるつもりで `database_path = "/proc/nope/factory.db"` にしたら、起動が止まったまま返ってこなかった。切り分けると、Node 単体の `require("fs").mkdirSync("/proc/nope", { recursive: true })` で再現した（`timeout 5` で打ち切り）。実装の問題ではないので、確認には `/dev/null/sub/factory.db` を使った（`ENOTDIR` で即座に失敗し、終了コード 1）。

## CI: `actions/setup-node@v5` が pnpm を探して落ちた

PR を出したら、最初の CI が 5 秒で落ちた。

```
##[error]Unable to locate executable file: pnpm. Please verify either the file path exists or the file can be found within a directory specified by the PATH environment variable.
```

- `setup-node@v5` は `package-manager-cache: true` が既定で、`package.json` の `packageManager` を見て pnpm のキャッシュを自動で使おうとする
- その時点ではまだ `corepack enable` を実行していないので、pnpm がない
- → `package-manager-cache: false` にした。依存のインストールは数秒なので、キャッシュはなくてよい
