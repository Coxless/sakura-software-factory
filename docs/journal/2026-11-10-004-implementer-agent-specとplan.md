# 004 implementer-agent の spec と plan

## やろうとしたこと

002（予算ゲート）と 003（作業場・4ツール・ガード）を Pi の `Agent` につなぎ、実装工程を1回実行する入口を作る。その spec・clarify・plan を書いた。

## 分かった事実: `shouldStopAfterTurn` は Pi 1.5.0 で廃止されていた

設計ドキュメント（`03` の表、`04` 2章・3章）と `docs/実装計画.md` は、停止条件のフックを `shouldStopAfterTurn` と書いていた。入っている `@earendil-works/pi-agent-core` 1.5.0 の README にはこうある。

> To migrate from the removed `shouldStopAfterTurn`, return `{ action: "end" }`.

`AgentOptions` にも `shouldStopAfterTurn` はなく、代わりに `finishTurn(turn, signal)` がある。ツールの結果がそろったあと・`turn_end` の前に呼ばれ、`{ action: "end" }` を返すと steering も follow-up も見ずに止まる。エラーと中断の応答でも呼ばれる（どのみちループは止まる）。

→ 設計ドキュメントと実装計画の名前を `finishTurn` に直した。

ついでに、003 の `src/harness/compose.ts` のコメントは「Pi 1.5.1 に合わせた」と書いているが、`package.json` と `node_modules` は 1.5.0。`BeforeToolCallResult`・`AfterToolCallResult`・`AgentToolResult` の形は 1.5.0 の `types.d.ts` でも同じだったので、コメントの数字だけ実装のときに直す。

## 分かった事実: 完了のあとの差し込みは追加の作業なしで効く

spec の FR-020「実装役が完了を告げたときに未送の差し込みがあれば、終わらずに続ける」を満たすのに何が要るかを `dist/agent-loop.js` で確かめた。内側のループの条件が

```js
while (hasMoreToolCalls || pendingMessages.length > 0) {
```

で、ツールを呼ばない応答のターンのあとも `getSteeringMessages()` を見て、溜まっていれば次の呼び出しをする。`followUp()` を使う必要はない。ただし `finishTurn` が `end` を返したとき（上限）は見ない。

ほかに読んで分かったこと:

- `transformContext` の戻り値は LLM への入力にだけ使われ、`agent.state.messages` は元のまま。圧縮しても会話の履歴は変わらない
- `stopReason: "length"`（出力の上限で切れた）の応答にツール呼び出しがあると、Pi は全部をエラーにして実行しない（引数が途中で切れているかもしれないため）
- 低レベルの `agentLoop` は「observational」で、イベントの処理を待たずに先へ進む。軌跡の順序を保証したいので `Agent` クラスを使う

## clarify で決めたこと

| 問い | 決定 | 理由 |
|---|---|---|
| やり直しは前回の会話の続きか、新しい会話か | 毎回新しい会話。前回の diff・理由・CI ログを追加のフィードバックとして渡す | 入力の大きさに上限を付けやすく、会話を保存する仕組みが要らない。`04` の「前回の diff と一緒に渡して再開」にも合う |
| 軌跡に LLM への入力をどう残すか | 増えたメッセージだけを書き、圧縮で置き換えた結果の一覧を呼び出しごとに書く | 毎回丸ごと書くと、入力がターンごとに伸びるのでファイルがターン数の2乗で大きくなる（40 ターンで数十MBもありうる）。差分でも入力は復元できる |
| 手で試すコマンドを 004 で作るか | 作る（P3） | 偽の LLM では指示文や圧縮の良し悪しが分からない。Google AI Studio で早く試す |

## plan で選んだこと

- **AGENTS.md・Issue 文・計画は最初の user メッセージに置く。** `transformContext` で毎回差し込む案もあったが、差し込みまで軌跡から再現する必要が出る。先頭に置けば「圧縮で消さない」だけで毎回の入力に必ず入る
- **AGENTS.md・Issue 文・計画は常に上限で切り詰める**（既定は各 20,000 文字、フィードバックは 30,000 文字）。spec の最初の版は「圧縮しても収まらないときだけ切り詰める」だったが、毎回同じ入力になるほうが軌跡と回帰評価で比べやすいので変えた
- **圧縮は LLM で要約しない。** 古いツールの結果を「省略しました（read_file src/a.ts、12,345 文字）」の注記に置き換えるだけにする。要約は1リクエストを使い、軌跡からの復元も難しい。古いターンを丸ごと消すと、ツール呼び出しと結果の対応が崩れて API がエラーを返す
- **入力の大きさは UTF-8 のバイト数 ÷ 3 で見積もる。** 日本語は1文字3バイトで約1トークン、英語とコードは約4文字で1トークンなので、どちらでも多めに見積もれる
- **Pi を import するのは `src/pipeline/implement.ts` だけにする**（`src/llm/` を除く）。TanStack AI へ切り替える場合に書き直すのはこのファイルだけ、をテストで確かめる

## まだ分かっていないこと

- 拒否の連続 5 回・圧縮の閾値 70%・残すターン数 4 が適切か（仮の値。`implement:dev` と 012 の回帰評価で見る）
- Kimi-K2.7-Code と Gemini で、区切りの中の指示を無視させる書き方がどこまで効くか
- さくらの実際のコンテキストの上限（今は 131,072 の仮の値）

## analyze で見つかったこと: 憲章の原則 V と軌跡の保存先が食い違っていた

`/speckit-analyze` が CRITICAL を1件出した。憲章 1.2.0 の原則 V は「軌跡（プロンプト、ツール呼び出し、結果）はジョブごとに SQLite と JSONL に保存する（MUST）」。一方、plan は SQLite に実行ごとの要約（`agent_runs`）だけを置き、詳細は JSONL にだけ書く形にして、「原則 V を満たす範囲の判断」と書いていた。analyze の規則では、原則の読み替えは許されない。

選択肢は2つだった。

- (a) 憲章を直す: 詳細は JSONL、SQLite には実行ごとの要約とファイルの場所
- (b) SQLite にもイベントの表を足し、詳細を二重に持つ

(a) にした。理由: clarify で「入力は差分だけを書く」と決めたのは大きさの問題（毎回丸ごとだとターン数の2乗）で、同じ詳細を SQLite にも持つと書き込みと容量が倍になる。011 の `/status` と記事の集計は要約で足りる。憲章は 1.2.0 → 1.3.0（MINOR: 指針の実質的な変更）にし、「軌跡から各 LLM 呼び出しの入力を復元できるようにする」も MUST に入れた。

同じ analyze で直したもの:

- spec の Edge Cases の「上限で止まるのはターン数・時間・予算だけ」が、拒否の連続（FR-011）や作業場の異常で止まることと食い違っていた → 「出力が切れたこと自体では止めない」に書き直した
- テストでコンテキストの上限を小さくする手段がなかった（上限は `provider.ts` の定数）→ `ImplementerDeps.model`（テスト専用）を足した
- ツールの実行中の中断のテストがなかった → T019 に足した
- やり直しのフィードバックと実行中の差し込みが同じ `<feedback>` タグで区別できなかった → 差し込みは `<feedback source="steering">` にした
