依存が0件でも、pnpm 12 は `pnpm-lock.yaml` を作り、`packageManagerDependencies` に pnpm 自身（各OS向けの `@pnpm/exe.*` 14件）を書いた。作業場のイメージ（`factory-sandbox:latest`）で次を確かめた:

```
docker run --rm -v <コピー>:/w -w /w -e HOME=/tmp factory-sandbox:latest sh -c "pnpm install --frozen-lockfile && pnpm run check"
# → pass 2 / fail 0
docker run --rm --network none ... pnpm run check
# → ネットワークなしでも通る
```

## 転送の方法: smee.io

App の Webhook の URL を smee.io のチャンネルにし、Workshop の中で `pnpm dlx smee-client`（5.0.0）を動かして `http://127.0.0.1:8787/webhook` に転送する。`gh webhook forward` はリポジトリの Webhook を作る仕組みで、App の Webhook（Recent Deliveries からの再送を含む）を試せないので、smee を先に試す。

### smee-client は本文を作り直すので、署名が合わないことがある

偽の秘密鍵と秘密（`dry-secret`）でファクトリーを起動し、記録したペイロード（`src/github/fixtures/issue_comment.created.agent.json`、本文に日本語を含む）に署名して smee のチャンネルへ `curl` で POST した。本文の形を3通り変えた結果:

| 送った本文 | ファクトリーの応答 |
|---|---|
| 区切りに空白なし・日本語をそのまま（`separators=(",",":")`, `ensure_ascii=False`） | `202`（`ignored` / `not_allowed`。署名は通った） |
| 区切りに空白なし・日本語を `\uXXXX` に | `401`（`webhook: 署名が正しくありません`） |
| 区切りに空白あり（Python の `json.dumps` の既定） | `401` |

smee-client は受け取った JSON を解釈してから `JSON.stringify` で送り直すので、元の本文が `JSON.stringify` の出力と1バイトでも違うと署名が合わない。GitHub の配送の本文がこの形と一致するかは、本物で確かめるまで分からない。

- 合わなければ、ファクトリーの検証を緩めるのではなく、転送の方法を変える（`gh webhook forward` か、一時的なトンネル）→ 本物の配送では合った（次の章）

### 片付けたつもりの smee-client が残っていた

1回目の試行のあと、`workshop exec dev -- sh -c 'pkill -f "node src/main.ts"; pkill -f smee-client; ...'` で止めたつもりだったが、何も出力されずに終わっていた。`pkill -f smee-client` は、自分を実行している `sh -c`（コマンド行に `smee-client` を含む）に一致し、後続を流す前にその shell を殺していた。smee-client が2つ残ったまま本番の確認を始めたので、GitHub の1回の配送が3回ずつ（3つの smee-client から）ファクトリーに届いた。2回目と3回目は `duplicate` になり、ジョブは1件のままだった（重複の防止が意図せず試された）。

- `ps` で見つけて pid で止めた。`pkill -f` をワンライナーの中で使うときは、自分のコマンド行に一致しないようにする
- 偽の秘密で試したあとに残った smee-client も、本物の配送を受け取っていた。署名は合わない（秘密が違う）が、同じファクトリーに転送するので害はなかった

## 本物の GitHub App で確認した結果（quickstart 3章）

App `coxless-sakura-factory` を作り（権限とイベントは contracts/github-app.md のとおり。`GET /app` の `permissions` で `actions:read, checks:read, contents:write, issues:write, metadata:read, pull_requests:write`、`events` で `check_suite, issue_comment, pull_request, push` を確かめた）、`factory-sandbox` だけに入れた。Webhook の URL は smee のチャンネル。`data/verify/factory.toml` で `[models].verifier` を `implementer` と同じにして、LLM を呼ばずに流した。

Issue #1 を作り、`Coxless` で `@agent README を直して` とコメントした。

| # | 期待 | 結果 |
|---|---|---|
| 1 | `eyes` のリアクション、`jobs` に1行 | ok。`coxless-sakura-factory[bot]` の `eyes`。`jobs` に `Coxless/factory-sandbox` #1 が1行。smee の転送は `202` で、**本物の配送は smee を通しても署名が合った** |
| 2 | `pipeline_failed` の報告が1回、作業場が残らない | ok。受付から報告まで約2.6秒（`job_events`: 受付 → `planning → failed`（`pipeline_failed`）→ `report_posted`）。理由は「`[models].verifier` と `[models].implementer` が同じモデル（Kimi-K2.7-Code）です」。作業ブランチ `agent/issue-1-job-1`（push なし）。`work/` は空、コンテナも残っていない。`planning` まで進んだので、インストールトークンでの clone と `pnpm install --frozen-lockfile` も通った |
| 3 | 権限のないアカウントのコメントは何も起きない | 未実施（2つ目のアカウントがない） |
| 4 | 再送で `duplicate` | ok。`POST /app/hook/deliveries/{id}/attempts`（Recent Deliveries の「Redeliver」と同じ）で再送し、`result: duplicate`。`jobs` は1行のまま |

- ファクトリー自身の報告コメントの配送は `ignored`（`reason: bot`）になった
- App の Recent Deliveries の `status_code` は、smee が返した `200` で、ファクトリーの応答ではない。本番（Caddy 経由）になると、ファクトリーの `202`・`401` が見えるようになる
