# 2026-11-10 CI を Workshop からランナーで直接動かす方式に戻した

001 で「CI もローカルと同じ Workshop の `dev` で動かす」に切り替えた（`2026-11-08-001-foundation-実装.md`）。003 の PR #3 でこれが止まったので、GitHub のランナーで直接動かす方式に戻した。

## 何が起きたか

1回目（PR #3 を出した直後、2026-11-10 11:20）: `canonical/launch-workshop` が LXD を入れる段で、57 秒で失敗した。

```
[command]/usr/bin/sudo snap install --channel=6/stable lxd
error: cannot perform the following tasks:
- Download snap "snapd" (28332) from channel "stable" (received an unexpected http response code (503) when trying to download https://canonical-bos01.cdn.snapcraftcontent.com/download-origin/canonical-lgw01/...)
##[error]The process '/usr/bin/sudo' failed with exit code 1
```

2回目（GitHub の画面から「Re-run failed jobs」、12:45）: 同じ `launch-workshop` の段に入ったまま終わらなくなった。前回成功したときはこの段が 112 秒で終わっていた。ワークフローに `timeout-minutes` がなかったので、既定の 6 時間まで待つ状態だった。

- Claude の GitHub App からの再実行は `403 Resource not accessible by integration` で拒否された（Actions を操作する権限がない）。再実行と取り消しは人が画面から行う
- 実行中のジョブのログは API から取れない（HTTP 404）ので、どこで止まっているかは見えなかった
- Snap Store が落ちているかは、開発に使っているクラウド環境からは確かめられなかった（`api.snapcraft.io` もステータスページもプロキシで拒否される）。503 のあとに同じ段で止まったので、Snap Store 側の障害の可能性が高いと判断した

## 比べたこと

| | Workshop 方式 | ランナーで直接動かす方式 |
|---|---|---|
| 外部への依存 | 毎回 Snap Store から snapd・LXD・Workshop・Node SDK を取得する | GitHub の配信（setup-node）と npm のレジストリだけ |
| 時間 | 約 2 分 6 秒（001 の実測） | 約 9 秒（001 の実測。003 からはイメージのビルドが加わる） |
| 003 の作業場のテスト | LXD の中で Docker が動くか未確認 | ランナーに Docker があるので実行できる |
| 作業場の本番イメージのビルド | 同上 | apt が通るので CI で確かめられる |
| ローカルとの一致 | 環境もコマンドも同じ | コマンドだけ同じ（`pnpm run check`） |

## 結論と理由

ランナーで直接動かす方式に戻した。

- Snap Store の障害で CI 全体が止まる。CI が通らないとマージできないので、外部の1か所への依存が重い
- 003 で、作業場のテスト（44件）と本番イメージのビルドの両方を CI で確かめたい。どちらも開発に使ったクラウド環境では確かめきれなかった（`2026-11-10-003-sandbox-tools.md`）
- 失うのは「ツールを足す場所を `setup-base` の1か所にする」こと。ランナーには Docker と git が最初からあり、CI 側で足す予定のものは gitleaks（008）だけなので、二重管理は小さい

## ci.yml の中身

- `actions/setup-node@v5`（Node 24、`package-manager-cache: false`。001 で、corepack を有効にする前に pnpm を探して失敗したため）→ `corepack enable` → `pnpm install --frozen-lockfile` → `pnpm run sandbox:build` → `pnpm run check`
- `timeout-minutes: 20`。何かが止まっても 6 時間待たない
- `pnpm run check` に `FACTORY_SANDBOX_REQUIRED=1` を渡す。Docker やイメージがないと、作業場のテストは理由を出して飛ばされるが、CI ではそれを失敗にして、黙って飛ばされたまま緑になるのを防ぐ。ローカル（クラウド環境）で `FACTORY_SANDBOX_TEST_IMAGE=nope:1` にして、2件が `FACTORY_SANDBOX_REQUIRED=1 なのに作業場のテストを実行できません: イメージ nope:1 がないため…` で失敗することを確かめた

## ついでに分かったこと

- 開発に使ったクラウド環境では、手で起動した `dockerd` がいつの間にか止まっていた。作業場のテストが「Docker デーモンに接続できない」で飛ばされて気づいた。`FACTORY_SANDBOX_REQUIRED=1` を付けて実行していたので、失敗として見えた

## 結果（PR #3、f0f337f）

- ジョブ全体が 36 秒（13:03:13〜13:03:49）で成功した。Workshop 方式の約 2 分 6 秒より速い
- `pnpm run sandbox:build`（apt で git・ripgrep、corepack で pnpm）が CI で通り、本番のイメージのビルドを初めて確かめられた
- `pnpm run check`: 16ファイル・201件が成功、8.92 秒。飛ばしたのは「飛ばした理由を出す」テスト2件だけで、作業場のテスト（`docker.docker.test.ts` 20件、`tools.docker.test.ts` 26件）はすべて実行された。ランナーのユーザー（root ではない）の uid:gid で作業場を動かして問題は出なかった
- 本番のイメージ（git 入り）なので、検証用イメージでは飛ばしていた「`.git` を読み取り専用にしても `git status` はできる」も CI で確かめられた
