# 005 local-pipeline の spec・plan・tasks

計画役・工程内テスト・検査役・やり直しのループと、ローカルで判定まで通す CLI を Spec Kit で設計した（specify → plan → tasks → analyze）。人間に確認が要る項目は、ユーザーの指示で推奨の案を採った。

## 推奨の案で決めたこと（spec の Clarifications）

| 問い | 採った案 | 退けた案と理由 |
|---|---|---|
| 工程内テストのコマンドをどこで決めるか | `factory.toml` の `[pipeline].check_commands`（既定 `pnpm run check`） | 対象リポジトリのファイルから読む → リポジトリの中身で実行内容を変えられてしまう |
| テストの失敗をどう戻すか | 実装役が完了を告げた時点で実行し、同じ会話に差し込む（1回の実装工程で3回まで）。超えたら検査役を呼ばずに不合格 | 実装工程のあとに新しい会話でやり直す → 何を変えたかの文脈を失い、毎回入力を払い直す |
| 計画役の出力の形 | JSON（概要・作業手順・受け入れ条件・作業の種類）を TypeBox で検証、再要求1回 | 自由な文章 → 受け入れ条件と作業の種類（008 の自動マージ条件）を取り出せない |
| 不合格のやり直しで変更を戻すか | 戻さない。新しい会話で、理由と今の diff を渡す | 戻して作り直す → 消費が増える |
| 検査役の出力が2回とも合わないとき | 工程全体を失敗にする | やり直しに入れる → コードの問題ではないのでリクエストの無駄 |
| `implement:dev` | `pipeline:dev` に統合して消す（`--plan` で計画役を飛ばせる） | 両方残す → 準備のコードが2つになる |

## 調べて分かったこと

- Pi 1.5.0 の `FinishTurn` は `(turn, signal) => AgentTurnDecision | Promise<...>` で、Promise を返せて signal も受け取る（`node_modules/@earendil-works/pi-agent-core/dist/types.d.ts`）。実装役の「完了を告げた」時点で await してテストを走らせ、失敗なら `steer` して `{ action: "continue" }` を返せば、同じ会話で続けられる。テストの最中も期限・中断の signal が効く
- 状態機械（`03` 3章）には `testing → implementing` がなかった。差し込みで実装に戻すので足す（007 はまだ main に入っていないので、007 の遷移表を合わせる）
- 007 の spec（`007-github-intake` ブランチ）の `PipelinePort` は `{ jobId, workdir, issue, instruction, signal, onPhase }` で、期限がない。005 の入口は期限を受け取るので、007 の plan で合わせる

## analyze で直したこと

- CLI の `--json` が diff をマスクせずに出す形になっていた（SC-009 と食い違う）→ マスクしてから出す
- 工程内テストのコマンドを起動できない（終了コード 126・127）ときに「中断」すると、実装工程が `aborted` になって FR-016（`failed`）と合わない → `onComplete` から例外を投げて `failed` にする
- 「LLM の呼び出し件数と結果のリクエスト数と軌跡の応答の件数が一致」は、ゲートの中で再試行が起きると成り立たない → 再試行がないときの条件にした

## まだ分かっていないこと

- Gemini（開発用）と Kimi・Qwen（さくら）が、プロンプトだけで JSON の形を守るか。再要求の割合は `pipeline:dev` で実測する
- 差し込みの上限（3回）・diff の上限（40,000 文字）などは仮の値。012 と AI解禁後の調整で直す
