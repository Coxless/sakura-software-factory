# 006 vps-ops と gitleaks の実装

spec・plan の段階で分かった事実は `2026-11-11-006-vps-ops-specとplan.md` にある。ここには実装中に分かったことを書く。作業はクラウドの作業環境（Claude Code on the web）で行った。

## 作業環境の Node

- `node` は v22.23.4 だった（`/opt/node22`）。`/opt/node24/bin` を PATH の先頭に置くと v24.22.1 になり、`pnpm run check` は 8.6 秒で通った（`Tests 334 passed | 47 skipped`。作業場のテストはイメージがないので飛ばした）
- 006 を入れたあとの `pnpm run check`: `Test Files 33 passed`、`Tests 363 passed | 47 skipped`

## /healthz と停止処理

- `@hono/node-server` の `serve()` は待ち受けの失敗（`EADDRINUSE`）を `listeningListener` に返さない。`createAdaptorServer()` で作って自分で `listen()` し、`error` を拾った
- `main.ts` は import しただけで `main()` が走っていた（`process.exitCode = main()`）。テストから `startFactory`・`installSignalHandlers` を読むために、`implement-dev.ts` と同じ「直接実行されたときだけ動く」形にした
- `port = 0` は設定の検証（1〜65535）で弾くので、テストでは検証済みの設定の `http.port` だけを 0 に差し替えた
- 手で確かめた値（quickstart 1章）:

```
curl -s -o /dev/null -w "%{http_code} %{time_total}\n" http://127.0.0.1:8787/healthz
200 0.001000
kill -TERM <pid> → rc=0、27ms で終了（"factory stopped"）
同じポートで2つ目 → "127.0.0.1:8787 で待ち受けられません: listen EADDRINUSE ..."、rc=1
FACTORY_CONFIG=factory.dev.toml → provider の確認で rc=1（これまでどおり）
```

## gitleaks

- `git ls-remote --tags https://github.com/gitleaks/gitleaks` で、v8.30.1 が最新のタグであることを確かめた（このセッションの git のプロキシは公開リポジトリの読み取りを通す。リリースの成果物〔tarball と checksums.txt〕は git では取れない）
- **`scripts/install-gitleaks.sh` の SHA-256 は空のまま。** 空だと「チェックサムが未設定です」で止まる。Workshop で `gitleaks_8.30.1_checksums.txt` から `linux_x64`・`linux_arm64` の値を写すまで、Workshop の作り直し・CI・VPS の `setup.sh` は gitleaks の手順で止まる
- `.gitleaks.toml` の許可（ファイルと値の組を4件、`condition = "AND"`）で、Docker Hub のイメージを使った履歴全体のスキャンは `no leaks found`（25 コミット、372ms）。偽の `ghp_` トークンを書いたファイルは `leaks found: 1`、終了コード 1

## deploy:lint

- `caddy fmt --diff` は、差があっても終了コードが 0。整形した結果と `diff -u` で比べる形にした
- shellcheck は、`lib.sh` の定数（source した側で使う）に SC2034 を出す。ファイルの先頭で止めた。`caddy fmt - <Caddyfile | diff -u Caddyfile -` には SC2094（同じファイルを読み書き）が出たので、結果を変数に入れてから比べた
- この作業環境では apt で shellcheck を入れられなかった（`E: Unable to locate package shellcheck`）。`koalaman/shellcheck:stable`（0.11.0）を呼ぶラッパーを scratch に置いて確かめた。`lint.sh` は変えていない
- わざと壊して検出することを確かめた: `NoNewPrivilege=yes`（綴りの誤り）→ `Unknown key name 'NoNewPrivilege'` で NG、Caddyfile の字下げをタブから空白に → `caddy fmt` で NG

## 予行演習

### このクラウドの作業環境で流すためにしたこと

`deploy/rehearsal/run.sh` そのものは変えず、scratch に写しを作って次を足した（本番と予行演習の手順の違いを増やさないため）。

| 制約 | 症状 | 写しでの代用 |
|---|---|---|
| TLS を差し替えるプロキシ | コンテナの中の `curl https://nodejs.org` が `SSL certificate problem: self-signed certificate in certificate chain` | `REHEARSAL_EXTRA_CA` でプロキシの CA を入れた（この変数は `run.sh` に残した。社内のプロキシの中で流す場合にも使える）。Node（corepack）には `NODE_EXTRA_CA_CERTS` |
| `dl.cloudsmith.io` に届かない | `curl: (6) Could not resolve host: dl.cloudsmith.io` で「Caddy」の手順が失敗 | `caddy:2.11.9` のイメージのバイナリと最小の `caddy.service` を入れ、`setup.sh` の写しで Caddy の手順を飛ばした |
| github.com のリリースに届かない | gitleaks のチェックサムが空 | Docker Hub のイメージのバイナリを `/usr/local/bin/gitleaks` に置いた（スクリプトは「入っています」で飛ばす） |
| Debian のミラーの名前を引けない | 作業場のイメージのビルドで `Could not resolve 'deb.debian.org'`（ホストでも同じ） | `update.sh` の写しで `node:24-slim` に `factory-sandbox:latest` の名前を付けた |

### 見つかって直したこと

1. **スクリプトに実行権限がなかった**: `bash: line 1: /opt/sakura-factory/app/deploy/scripts/setup.sh: Permission denied`。`chmod +x` してコミットした（手順書は直接実行する）
2. **`REHEARSAL_KEEP=1` で残したコンテナがあると次が起動しない**: `Conflict. The container name "/sakura-factory-rehearsal" is already in use`。起動前の片付けを `REHEARSAL_KEEP` と切り離した
3. **入れ子の Docker で overlay を重ねられない**: `failed to mount /tmp/containerd-mount...: mount source: "overlay" ... err: invalid argument`。中の Docker は 29.1.3（Ubuntu の `docker.io`）で、containerd のイメージストアを使う。`/var/lib/docker` だけでなく `/var/lib/containerd` もボリュームにした
4. **データの置き場所が 755、DB のファイルが 644 になった**: 2回目以降の `setup.sh` や再起動では 750 のままだったので、初回の作成の経路で緩くなっていた（`docker exec` の umask は 0000）。原因の経路は特定していない。`update.sh` で、マイグレーションの前に `install -d -m 0750` で置き場所の権限をそろえ、マイグレーションを `umask 0027` で動かすようにした。予行演習に確認 9b を足した

### 結果

上の代用のもとで、quickstart 4章の確認がすべて通った（2回目の実行）:

```
ok    1 setup.sh の1回目はひな形を置いて止まる
ok    2 setup.sh の2回目が通る
ok   2b 最後に deployed <HEAD> を出す
ok    3 factory・caddy・docker が active
ok    4 Caddy 経由の /healthz
ok    5 公開していないパスは Caddy が 404
ok    6 ステージングに転送する
ok    7 ステージングが止まると 502、ファクトリーは 200 のまま
ok    8 HTTP は HTTPS に 308 で転送
ok    9 秘密情報のファイルは root:factory 640
ok   9b データの置き場所と DB は factory だけが読める
ok   10 強制終了から 30 秒以内に自動で再起動する
ok   11 journald から JSON のログを読める
ok   12 2回目の setup.sh でも DB の中身が変わらない
ok   13 ufw は 22・80・443 だけ
ok   14 動いている版が HEAD と同じ
ok   15 gitleaks の版
ok   16 /healthz が 100ms 以内
17 全体の所要時間: 70 秒（15 分以内: ok）
```

- 終わったあと、ラベル `sakura-factory.rehearsal=1` のコンテナ・ボリュームは 0 件
- 所要時間の 70 秒は、代用でダウンロードを減らした分だけ短い。Workshop で代用なしに流した時間が本当の値
- この作業環境は cgroup v1 だが、`--privileged --cgroupns=host -v /sys/fs/cgroup:/sys/fs/cgroup:rw --tmpfs /run --tmpfs /run/lock` で systemd は `running` になった
- ufw はコンテナの中で `--force enable` まで通った（特権付きなので、コンテナのネットワークの名前空間の iptables に入る）

### 保護設定と Docker

ユニットと同じ保護設定（`ProtectSystem=strict`・`PrivateTmp=yes`・`NoNewPrivileges=yes` ほか）を `systemd-run -p ...` で付け、`factory` ユーザーで作業場の形のコンテナ（`--network none --read-only`、`/var/lib/sakura-factory` の下を bind mount）を起動できた。`ProtectSystem=strict` でも Docker のソケットは使える。
