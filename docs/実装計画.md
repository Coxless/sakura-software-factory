# 実装計画（Spec Kit の機能分割と順序）

ソフトウェアファクトリーを Spec Kit の機能単位に分け、実装の順序を決めた計画。
決定事項は `docs/design/` と `.specify/memory/constitution.md` を正とし、本書は進め方だけを扱う。
設計が変わったら本書も合わせて直す。

## 1. 前提にした制約

- **締切は 2026-12-16。** 記事の執筆に約1週間、徹底検証の実測と24時間稼働の実績づくりに期間が要る
- **さくらのVPS の無料期間は2週間。** 使い始めた日から数えるので、締切から逆算して **2026-12-03 に使い始める**（12-03〜12-16 の14日間）。それまでは VPS を契約しない
- **さくらのAI Engine の無償枠は月3,000リクエスト。** 準備が整うまで実機の LLM を呼ばない。開発中のテストと動作確認はすべて偽の LLM（`src/llm/testing.ts`）で行う
- **開発中の実際の LLM は Google AI Studio（Gemini API）の無償枠を使う**（constitution 1.2.0 の原則 I の例外）。送るのは公開してよいデータだけ。004・005 のハーネスの作り込みはこれで行い、さくらの枠は AI解禁まで使わない
- **実機を使い始める時点を2つに分ける。** 「AI解禁」は 005（ローカルで計画から判定まで）が偽の LLM で通ったあと（11月の枠を使う。11月の枠は月末で消えるので、解禁後は遠慮なく使ってよい）。「VPS解禁」は 12-03。どちらも、解禁の前に手順書とチェックリストを用意しておき、解禁した日にすぐ流せるようにする
- **最大のリスクは さくらのAI Engine でツール呼び出しが安定するか**（`03` 6章）。実機での確認（002 のスモークテスト）は AI解禁の最初の作業にする。それまでは、Pi から TanStack AI へ切り替える場合に書き直す範囲を `src/llm/provider.ts` と `src/llm/stream.ts` の内側、004 の Agent の組み立てに閉じ込めておく（ゲート・記録・偽の LLM・ツール・ガードは使い回せる）

### この分け方にした理由

- **005 で、GitHub なしでも計画から判定までが動く状態にする。** 一番難しく不確かな「LLM＋ハーネス」の部分を、GitHub や VPS の手間と切り離して作り込める。012 の回帰評価もこの CLI の上に乗る
- **GitHub の処理は 007〜010 に集め、`github/` 層に閉じ込める**（原則 VII）
- **レポートは 007 で失敗時の最小版を作り、008 で完成させる。** 原則 II の「失敗時も必ず報告する」を、ジョブ処理の最初の版から守れる

## 3. 時系列

```
11/08─11/12  M0 基盤              001 → 002（実機確認は除く）, 003            偽の LLM・ローカルの Docker
11/13─11/19  M1 ローカル生産ライン 004 → 005                                 ★偽の LLM で Issue 文から判定済みの diff まで
11/20─11/24  M2 Issue→PR（ローカル）007 → 008、006 の配備物（Caddyfile・systemd・手順書）を用意
                                  Webhook は記録したペイロードで試す。GitHub の API はテスト用リポジトリで実際に呼んでよい
11/25        ◆AI解禁（11月の枠）   002 のスモークテスト → Pi 続行か切り替えかを判断
11/25─12/02  M3 実機の調整とレベルB 005 の CLI を実機で回してハーネスを直す、009 → 010（ステージングはローカルの compose で試す）
                                  011, 012（偽の LLM で作る。実機の評価は12月の枠で）
12/03        ◆VPS解禁（無料2週間）  006 の手順で配備 → 24時間稼働を開始 → Issue からステージング反映までを通す
12/03─12/09  M4 運用と検証（12月の枠） デモ Issue を流し続けて実測、012 の回帰評価と検査役の比較
12/10─12/16  M5 記事               12/10 で機能凍結、記事執筆。VPS は 12/16 まで稼働を続ける
```

- **AI解禁までは、どの機能も偽の LLM でテストが通る状態で作る。** 実機の挙動に依存する値（互換フラグ、`contextWindow`・`maxTokens`、モデル名、`base_url`）は仮の値のまま進め、AI解禁の日に直す
- **AI解禁の日の流れ**: 002 の T019（スモークテスト、10リクエスト以下）→ 判断（T020）→ 切り替えるなら、ここで `provider.ts`・`stream.ts` の内側と 004 の Agent の組み立てを直す → 005 の CLI（`pnpm run pipeline:dev -- --allow-sakura`）で実機を回す
- **VPS解禁の前に、配備を手順書どおりにローカルで流しておく。** 006 の Caddyfile・systemd ユニット・配備スクリプトは、M2 で用意し、ローカル（Workshop またはローカルの Docker）で確かめる。12-03 は手順書を上から流すだけにする
- **12月の枠（3,000）の使い道**: 24時間稼働のデモ Issue、012 の回帰評価と検査役の比較。予算ゲートが月とジョブの上限で止めるので、`factory.toml` の `[budget]` で配分する
- **011 の `/status` は独立していて、いつでも挟める。** M3 で遅れが出たら後ろにずらしてよい
- **gitleaks は 006 で `.workshop/devtools/hooks/setup-project`（ローカル）・`.github/workflows/ci.yml`（CI）・VPS の `setup.sh` に入れる**（版とチェックサムは `scripts/install-gitleaks.sh` に1か所）。008 の出荷前チェックはこれを使う
- **VPS の無料期間は 12-16 で終わる。** 審査期間中も稼働させる必要があるかは、コンテストの要項で確かめる（必要なら有料で延長する）

### 遅れたときに削る順番

1. 任意機能
2. 012 の検査役比較
3. 011 の画面（データは 002 から記録されているので、記事は SQL の集計で書ける）

001〜010 は「ファクトリーと呼ぶための5条件」とレベルBに直結するので削らない。

## 4. 各機能の進め方

1. `/speckit-specify` に、2章の「範囲」と「関係する設計」の章を渡す
2. `/speckit-clarify` → `/speckit-plan`（Constitution Check を通す）→ `/speckit-tasks` → `/speckit-implement`
3. 設計と食い違う変更が要るときは、先に `docs/design/` と constitution を直す
