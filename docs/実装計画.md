# 実装計画（Spec Kit の機能分割と順序）

ソフトウェアファクトリーを Spec Kit の機能単位に分け、実装の順序を決めた計画。
決定事項は `docs/design/` と `.specify/memory/constitution.md` を正とし、本書は進め方だけを扱う。
設計が変わったら本書も合わせて直す。

## 1. 前提にした制約

- **締切は 2026-12-16。** 記事の執筆に約1週間、徹底検証の実測と24時間稼働の実績づくりに期間が要るため、レベルBの全工程を **2026-11-30 までに動かす**
- **最大のリスクは さくらのAI Engine でツール呼び出しが安定するか**（`03` 6章）。Pi を続けるか TanStack AI に切り替えるかが決まるので、最初に確かめる
- **月3,000リクエストの枠は12月に戻る。** 11月の残りは開発中の動作確認に使い、回帰評価と検査役の比較は12月に回す

### この分け方にした理由

- **005 で、GitHub なしでも計画から判定までが動く状態にする。** 一番難しく不確かな「LLM＋ハーネス」の部分を、GitHub や VPS の手間と切り離して作り込める。012 の回帰評価もこの CLI の上に乗る
- **GitHub の処理は 007〜010 に集め、`github/` 層に閉じ込める**（原則 VII）
- **レポートは 007 で失敗時の最小版を作り、008 で完成させる。** 原則 II の「失敗時も必ず報告する」を、ジョブ処理の最初の版から守れる

## 3. 時系列

```
11/08─11/11  M0 リスク潰し        001 → 002（実機でツール呼び出しを確認 → Pi 続行か切り替えかを判断）
                                  003 は 002 と並行で進められる
11/12─11/18  M1 ローカル生産ライン 004 → 005        ★ローカルで Issue 文から判定済みの diff まで
11/19─11/24  M2 Issue→PR          006 → 007 → 008  ★VPS で24時間稼働を開始（レベルA相当）
11/25─11/30  M3 レベルB完成        009 → 010        ★Issue からステージング反映まで
12/01─12/07  M4 計測と検証         011, 012（12月の新しい枠で検査役の比較、ハーネスの改善）
12/08─12/16  M5 運用と記事         デモ Issue を流し続けて実測、任意機能、記事執筆（12/10 で機能凍結）
```

- **006 の VPS 配備は早めに入れる。** Webhook を受けるには公開の受け口が要り、24時間稼働部門では稼働期間そのものが材料になる
- **011 の `/status` は独立していて、いつでも挟める。** M3 で遅れが出たら後ろにずらしてよい
- **gitleaks は 008 の前に `.workshop/devtools/hooks/setup-base` に追加する**

### 遅れたときに削る順番

1. 任意機能
2. 012 の検査役比較
3. 011 の画面（データは 002 から記録されているので、記事は SQL の集計で書ける）

001〜010 は「ファクトリーと呼ぶための5条件」とレベルBに直結するので削らない。

## 4. 各機能の進め方

1. `/speckit-specify` に、2章の「範囲」と「関係する設計」の章を渡す
2. `/speckit-clarify` → `/speckit-plan`（Constitution Check を通す）→ `/speckit-tasks` → `/speckit-implement`
3. 設計と食い違う変更が要るときは、先に `docs/design/` と constitution を直す
