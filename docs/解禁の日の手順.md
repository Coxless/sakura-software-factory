# 解禁の日の手順（AI解禁・VPS解禁）

AI解禁（さくらのAI Engine を初めて呼ぶ）と VPS解禁（VPS に配備する）を同じ日に行うための手順。上から順に流す。日程は `docs/実装計画.md` 3章。

- 各手順の詳細は、ここから参照する文書を正とする（002・005・007 の quickstart、`deploy/README.md`）
- APIキー・秘密鍵・パスワードは、チャット・リポジトリ・journal に書かない
- 結果は journal に書く（手順ごとに書き先を示す）

## 0. 前日までに用意するもの

| もの | 確かめ方 |
|---|---|
| さくらのAI Engine の APIキー | コントロールパネルで発行済み。手元に控えてある |
| VPS（Ubuntu 24.04 LTS）と SSH の鍵 | 手元から `ssh <user>@<IP>` でパスワードなしに入れる |
| ドメインの DNS | `dig +short <FACTORY_DOMAIN>`・`dig +short <STAGING_DOMAIN>` がどちらも VPS の IP |
| さくらのパケットフィルター | 22・80・443（TCP）だけを許可 |
| GitHub App（007 で作成済み） | App の ID・秘密鍵（.pem）・Webhook のシークレットが手元にある |
| 011 の PR がマージ済み | main の `deploy/Caddyfile` に `basic_auth` がある（`/status` の認証） |

## 1. AI解禁: スモークテスト（手元の Workshop、10 リクエスト以下）

詳細: `specs/002-llm-budget-gate/quickstart.md` 2〜3章（タスク T019・T020）

1. さくらのドキュメントで、OpenAI 互換の `base_url` と、実装役・検査役・退避先のモデル名を確かめ、`factory.toml` の `[llm].base_url` と `[models]` を直す（「仮の値」のコメントを消す）
2. 実行する:

   ```bash
   workshop exec dev -- bash -lc 'cd /project && read -rs SAKURA_AI_API_KEY && export SAKURA_AI_API_KEY && pnpm run smoke:llm && pnpm run smoke:llm -- --raw && pnpm run smoke:llm -- --role verifier'
   ```

3. 判断する（quickstart 3章）:
   - 全部合格 → Pi を続ける。使った互換フラグを `src/llm/provider.ts` の `DEFAULT_SAKURA_COMPAT` に、分かった `contextWindow`・`maxTokens` を定数に書く
   - 不合格 → `--compat` を変える → `--raw` と比べる → `--raw --no-stream`。素の HTTP だけ合格なら TanStack AI への切り替えを決め、**ここで止めて**設計 `03` と constitution を直す計画を立てる（VPS の配備は切り替えのあとにする）
4. `llm_calls` の増えた行数が、表示の `requests` と一致することを確かめる
5. 結果を `docs/journal/YYYY-MM-DD-sakura-tool-calling.md` に書く（コマンド、各項目の合否、互換フラグ、モデル名、使ったリクエスト数、判断と理由）

## 2. AI解禁: 計画から判定までを実機で1回（手元、20〜50 リクエスト）

詳細: `specs/005-local-pipeline/quickstart.md` 4章

1. 公開のデモ用リポジトリ（`Coxless/factory-sandbox`）を手元に clone し、小さな Issue 文（例: 「`src/text.js` の関数に、空文字列のテストを1件足す」）をファイルに書く
2. 実行する:

   ```bash
   workshop exec dev -- bash -lc 'cd /project && read -rs SAKURA_AI_API_KEY && export SAKURA_AI_API_KEY && pnpm run pipeline:dev -- --repo <clone したパス> --issue <Issue のファイル> --install "pnpm install --frozen-lockfile" --allow-sakura'
   ```

3. 計画 → 実装 → 工程内テスト → 判定まで進むこと、計画役・検査役の JSON の再要求の回数、使ったリクエスト数を見る。直すところがあれば直してから次に進む
4. 1・2 で直したもの（`factory.toml`・`provider.ts` など）を PR にして main にマージする。**VPS は main を配備するので、ここでマージしたものが本番の設定になる**
5. 手元で使ったリクエスト数を数えておく（4章で使う）:

   ```bash
   workshop exec dev -- bash -lc 'cd /project && pnpm run --silent status:dev | jq .consumption.requests'
   ```

6. 結果を journal に書く（`docs/journal/YYYY-MM-DD-sakura-pipeline.md`）

## 3. VPS解禁: 配備

詳細: `deploy/README.md` 1〜5章（この順に上から流す）

1. 1章: 事前の確認
2. 2章: リポジトリの取得と `setup.sh` の1回目（`factory.env` のひな形を置いて止まる）
3. 3章: 秘密情報とドメインを書く
   - `factory.env`: `SAKURA_AI_API_KEY`・`GITHUB_APP_ID`・`GITHUB_APP_PRIVATE_KEY_PATH`・`GITHUB_WEBHOOK_SECRET`
   - `caddy.env`: `FACTORY_DOMAIN`・`STAGING_DOMAIN`・`CADDY_TLS`（ACME の連絡先のメールアドレス）・`STATUS_USER`・`STATUS_PASSWORD_HASH`（`caddy hash-password` の出力を**単一引用符で囲む**）
4. 4章: `setup.sh` の2回目。最後に `deployed <コミット>` が出る
5. 5章: 確かめ方の表を上から確かめる（`/healthz`・`404`・`/status` の `401`・HTTP から HTTPS など）

## 4. VPS の設定を本番に合わせる

`/etc/sakura-factory/factory.toml` を直して `sudo systemctl restart factory`

| 項目 | 値 | 理由 |
|---|---|---|
| `[staging].public_url` | `https://<STAGING_DOMAIN>` | PR の本文にステージングの URL を書く（`deploy/README.md` 5章「ステージング」） |
| `[budget].monthly_requests` | 3000 − 2章5で数えた手元の件数 | 手元の DB（1・2 の記録）は VPS の予算ゲートに見えない。さくらの月の枠は1つなので、手元で使った分を引いておく |

- 手元で さくらをもう一度使ったら、そのつど VPS の上限も同じだけ下げる（予算ゲートは毎回 `factory.toml` の上限とその月の記録の件数を比べるので、直して再起動すれば月の途中でも効く）

## 5. GitHub App の Webhook を VPS に向ける

1. App の設定（Settings → Developer settings → GitHub Apps → App → General）で、Webhook の URL を smee のチャンネルから `https://<FACTORY_DOMAIN>/webhook` に変える
2. 手元で動かしていた smee-client を止める（`pgrep -af smee` で残っていないことを確かめる）
3. App の「Recent Deliveries」に、以後の配送のファクトリーの応答（`202`・`401` など）が見える

## 6. 通しの確認: Issue からステージングまで

`Coxless/factory-sandbox` で、権限のあるアカウントから小さな依頼をする。

| # | 操作 | 期待 | 詳細 |
|---|---|---|---|
| 1 | Issue を作り `@agent <小さな依頼>` とコメント | 数秒で `eyes`。`/status` の最近のジョブに1行 | 007 quickstart 3章 |
| 2 | 待つ | 計画 → 実装 → 判定 → PR。自動マージの6条件を満たせば auto-merge、満たさなければ Draft。Issue に PR へのリンク | 008 |
| 3 | CI を待つ | CI が通れば main にマージされる。落ちればやり直し（上限あり） | 009 |
| 4 | マージのあと | ステージングに出て、PR の本文のデプロイの欄に結果と `https://<STAGING_DOMAIN>` | 010 |
| 5 | `https://<FACTORY_DOMAIN>/status` を開く（Basic 認証） | 消費・成功率・CI 初回通過率・デプロイ成功率が今の記録と合う | 011 |
| 6 | App の「Recent Deliveries」から1の配送を再送 | `duplicate`。ジョブは増えない | 007 |

- 途中で止まったら、`journalctl -u factory -o cat -n 100` と `/status` の工程の実行で、どこで止まったかを見る（`deploy/README.md` 7章）
- 結果を journal に書く（`docs/journal/YYYY-MM-DD-本番で通し.md`）。1件目のジョブの所要時間・リクエスト数・CI の回数を記録する
